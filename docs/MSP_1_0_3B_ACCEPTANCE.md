### Про P99

Рост с 6,8 до 535 мс полностью объясняется шестью кейсами `qr_phishing`: декодер QR запускается
отдельным процессом, и 545 мс — это запуск интерпретатора, а не декодирование. Процесс один на
письмо, а не на изображение, поэтому стоимость ограничена сверху при любом количестве картинок.
Бюджет §43 — 5 с; CI проверяет P95 (1,9 мс). Снижать эту стоимость можно только внося декодер
обратно в воркер, то есть отдавая пиксели недоверенного письма большой C++-библиотеке без
изоляции — обмен, который этап делать не стал.

### Отступления, заявленные явно

**§48 называет `docs/MSP_1_0_3_ACCEPTANCE.md`, `RULE_RELEASE_PROCESS.md` и `ANALYST_QUEUE.md`.**
Первые два уже существуют под другими именами с содержанием той же области:
`MSP_1_0_3_ACCEPTANCE.md` — приёмка предыдущего этапа (этот этап получил свой документ, чтобы
две приёмки не смешивались), `DETECTION_RELEASE_PROCESS.md` — порядок выпуска. Дублировать
порядок выпуска во второй файл значило бы завести два источника правды о том, как выпускаются
правила; вместо этого существующий документ дополнен механикой 1.0.3B (кандидат, четыре глаза,
манифест). `ANALYST_QUEUE.md` создан, но описывает то, чего не было в `ANALYST_WORKFLOW.md`
(граф, поиск v2, курирование кампаний), и ссылается на него в части приоритета и SLA — по той
же причине.

**`msp_incident_sla_breached` — gauge, а не counter.** §41 называет метрику счётчиком. Счётчик
инкрементировался бы при каждом чтении очереди и считал бы просмотры, а не нарушения.
Отклонение намеренное, описано в коде и в `DETECTION_QUALITY.md`.

**Декодирование QR — необязательный компонент.** §17 требует извлечения QR; оно реализовано, но
требует `pip install -e '.[qr]'`. Там, где компонент не установлен, покрытие сценария
THR-PHISH-004 ниже, и это видно в `missing_evidence` письма, а не только в документации.

## Дефекты, найденные и исправленные на этапе

Этап строился по правилу «сначала тест, потом исправление». Найденное:

| Что | Чем нашлось | Исправление |
|---|---|---|
| Свёрнутый заголовок `Subject` сохранял CRLF | состязательный тест | `_unfold()` в `decode_header_value` |
| Две копии окружения оценки расходились: recall 0.904 против 0.990 | расхождение API и CLI | единственное определение в `msp_detection_eval/environment.py`; тест на тождество объектов |
| `GET /campaigns/match-quality` и `/campaigns/merge-suggestions` недостижимы с 1.0.3 | E2E §44.5 | перенесены под `/detection/campaigns/`; `tests/unit/test_route_shadowing.py` проверяет всю таблицу путей |
| Счётчик нарушений SLA считал бы просмотры очереди | разбор семантики метрики | заменён на gauge |
| 15 колонок миграции `NOT NULL` без `server_default` | проверка ДО/ПОСЛЕ/ОТКАТ на засеянных строках | backfill с последующим снятием default |
| `scripts/export_corpus.py` не проходил mypy | запуск проверки типов | манифест типизирован сквозно, два подавляющих комментария удалены |
| Снимок сообщал `unknown` о сканированиях, доступных в venv | запуск итогового снимка | поиск инструментов в окружении интерпретатора |
| Тот же снимок сообщил `vulnerabilities` о не запустившемся pip-audit | чтение вывода | `-m` вызывается по имени модуля, а не консольного скрипта |

Последние два стоят отдельного упоминания: инструмент, объявляющий уязвимости там, где он сам не
стартовал, — ровно тот класс неправды, ради предотвращения которого снимок и пишет `unknown`.

## Что осталось за границей этапа

Согласно §49 не начиналось: Postfix/MTA, SMTP listener, обработка MX, исходящая доставка,
устойчивые очереди почты, SMTP reject, inline-карантин, подпись DKIM, HA-шлюз, замена KSMG.

Открытые пробелы на момент приёмки: GAP-001 (вставка символа в короткой метке домена, принят,
MSP 1.0.4), GAP-002 (`VALIDATION`, подтверждение на реальном потоке), GAP-003 (архивы 7z и RAR,
принят, MSP 1.1), GAP-004 (QR внутри PDF, принят, MSP 1.1). **Незарегистрированных критических
пробелов нет.**

Не проверено в этом этапе и честно не заявлено как проверенное: поведение на реальном почтовом
потоке. Все метрики получены на синтетическом корпусе, все снимки консоли — на стенде с тем же
корпусом. Пробел GAP-002 остаётся в `VALIDATION` именно поэтому.

PHASE: MSP 1.0.3
DECISION: READY_FOR_GATEWAY_FOUNDATION

Условия §47:

| Условие | Состояние |
|---|---|
| regression gate green | **да** — ПРОЙДЕН, два предупреждения о зарегистрированном GAP-001 |
| нет незарегистрированных критических пробелов | **да** — четыре пробела, все с владельцем, мерой и целевым выпуском |
| replay воспроизводим | **да** — ревизия с версиями пакета, парсера, движка и контрольной суммой датасета |
| rule releases управляемы | **да** — кандидат, прогон по корпусу до ревью, четыре глаза, манифест |
| FP измеряются | **да** — с обязательной причиной и осуждением сигнала |
| FN регистрируются | **да** — с владельцем и целевым выпуском, иначе запись не принимается |
| analyst workflow эксплуатационно пригоден | **да** — проверен на стенде, снимки 13–25 |
| CI green | **да** локально, полным составом задач |
| baseline/final metrics документированы | **да** — два снимка, сгенерированные одним скриптом |

Решение принимается с оговоркой, уже сделанной выше и не меняющей его: пригодность проверена на
синтетическом корпусе и на стенде. Первый реальный поток остаётся источником ответов, которых
этот этап дать не может, — и реестр пробелов устроен так, чтобы эти ответы было куда записать.
