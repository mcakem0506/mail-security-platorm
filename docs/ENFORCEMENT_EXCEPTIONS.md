# Исключения принуждения

**Относится к:** ТЗ MSP 1.3 §38–§41

| Свойство | Правило |
|---|---|
| Срок | обязателен; по умолчанию 7 дней, не более 90; бессрочных нет |
| Владелец и причина | обязательны (причина не короче 5 символов) |
| Лимит использований | необязателен (`max_uses`); исчерпанное исключение не действует |
| Область | `SENDER`, `SENDER_DOMAIN`, `RECIPIENT`, `RECIPIENT_GROUP`, `SOURCE_IP`, `MESSAGE_ID`, `CAMPAIGN`, `CONTROL` |
| Четыре глаза | обход `MALWARE_REJECT`, `DMARC_REJECT`, `RBL_REJECT`, `PHISHING_REJECT` и любое исключение области `CONTROL`: владелец ≠ согласующий |
| Права | создаёт — `create:exception` (аналитик), согласует/отзывает — `exception:approve` (администратор ИБ) |

## Что исключение делает и чего не делает

* Меняет **применённое действие** на `BYPASS_BY_EXCEPTION`. Предложенное действие, причины и свидетельства сохраняются и видны в
  журнале решений (§41): исключение не скрывает сигналы и не подавляет их в анализе MSP.
* Для исключения по получателям в области нужно, чтобы оно покрывало **всех** получателей письма (иначе часть адресатов осталась бы без защиты).
* Каждое создание, согласование и отзыв — новая подписанная версия политики и событие аудита; истёкшее исключение узел не применяет
  (срок проверяется на узле при каждом решении, а не при публикации).

## Чего нельзя

Нельзя «временно разрешить всё»: область `CONTROL` требует второго человека и срока; аварийный сценарий ложного срабатывания
исключений-«навсегда» не создаёт ([FALSE_POSITIVE_EMERGENCY.md](FALSE_POSITIVE_EMERGENCY.md)).
