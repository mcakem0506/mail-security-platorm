# Порядок реагирования на инциденты

Соответствует §19, §20, §36 ТЗ. Документ описывает работу службы ИБ в платформе.

---

## 1. Источники инцидентов

| Источник | Как попадает | Приоритет |
|---|---|---|
| Сообщение сотрудника из Outlook | кнопка «Сообщить о фишинге» | высокий: человек уже насторожился |
| Письмо в security mailbox | пересылка как вложение | высокий |
| Вердикт `MALICIOUS` или `HIGH_RISK` | автоматически, уведомление службе ИБ | высокий |
| Обнаруженная кампания | корреляция нескольких писем | средний |
| Совпадение с подтверждённым индикатором | hard-signal | высокий |

---

## 2. Жизненный цикл инцидента

```text
NEW ──► TRIAGE ──► INVESTIGATING ──┬──► CONFIRMED_PHISHING ──┐
                                   ├──► CONFIRMED_MALWARE ───┤
                                   ├──► CONFIRMED_BEC ───────┼──► REMEDIATION_PENDING
                                   ├──► FALSE_POSITIVE       │         │
                                   └──► BENIGN               │         ▼
                                                             │    REMEDIATED
                                                             └────────┬──────► CLOSED
```

Переход в `CONFIRMED_*` автоматически помечает индикаторы инцидента как подтверждённо
вредоносные — последующие письма с теми же индикаторами получат hard-signal.

---

## 3. Триаж (цель — 15 минут)

1. Открыть инцидент или письмо в консоли.
2. Прочитать **причины вердикта**, а не только класс риска. Каждая причина содержит объяснение,
   источник и время наблюдения.
3. Проверить аутентификацию отправителя. Помнить: `SPF pass` **не означает** безопасность,
   а отсутствие DKIM **не означает** фишинг.
4. Проверить, есть ли подмена защищаемой идентичности — самый значимый признак для BEC.
5. Посмотреть `missing_evidence`: если там есть записи, вердикт неполный и может измениться.
6. Проверить, входит ли письмо в кампанию — от этого зависит масштаб.

### Быстрые решения

| Наблюдение | Решение |
|---|---|
| Подтверждённо вредоносный индикатор (hard-signal) | `CONFIRMED_PHISHING`, переход к реагированию |
| Подмена руководителя и финансовый запрос | `CONFIRMED_BEC`, немедленно предупредить получателя |
| Легитимная рассылка, сработал слабый сигнал | `FALSE_POSITIVE` и исключение с ограниченным сроком |
| Запароленный архив без иных признаков | запросить подтверждение у отправителя, `INVESTIGATING` |
| `UNKNOWN` из-за недоступности провайдера | дождаться повторной проверки, не закрывать как безвредное |

---

## 4. Расследование

Инструменты консоли:

- **безопасный просмотр** — содержимое без скриптов и без активных ссылок; факт просмотра
  фиксируется в аудите;
- **сигналы детектирования** — какие правила сработали, с какими доказательствами и версиями;
- **поиск по индикатору** — все письма организации с этим индикатором;
- **поиск по расследованиям** — фильтры по отправителю, получателю, теме, вердикту, домену,
  хешу вложения, URL, кампании и инциденту;
- **связывание писем** с инцидентом;
- **заметки аналитика** — попадают в хронологию инцидента.

Вложения скачиваются только при необходимости: опасные типы требуют явного подтверждения,
файл отдаётся как `application/octet-stream` с именем-хешем, и это записывается в аудит.

## 5. Реагирование (§20)

### Порядок

```text
1. Аналитик предлагает действие с обязательным указанием причины
2. Платформа выполняет dry-run: сколько писем, какие ящики, возможен ли откат
3. Аналитик проверяет область: не затронуты ли лишние письма
4. Администратор ИБ согласовывает (автор предложения не может согласовать сам)
5. Если затронутых ящиков больше порога — требуется второй согласующий
6. Администратор выполняет с явным подтверждением
7. Результат и токен откатa фиксируются в аудите
```

### Выбор действия

| Ситуация | Действие | Откат |
|---|---|:--:|
| Подтверждённый фишинг в нескольких ящиках | карантин | да |
| Вредоносное вложение | карантин | да |
| Кампания с одного адреса | блокировка отправителя | нет |
| Кампания с одного домена | блокировка домена | нет |
| Требуется правило транспорта | предложение правила (автоматически не применяется) | — |
| Ложное срабатывание после карантина | возврат из карантина | — |

**Карантин предпочтительнее удаления**, поскольку обратим. Удаление применяется только когда
карантин недоступен и решение подтверждено.

### Если выполнение отклонено

Платформа может работать в режиме, где реагирование только предлагается и согласовывается,
но не выполняется (`MSP_REMEDIATION_DRY_RUN_ONLY=true`). Это нормальное состояние для пилота.
В таком случае согласованное предложение передаётся администратору Exchange для выполнения
вручную, а запись в платформе остаётся как основание.

## 6. Работа с ложными срабатываниями

Исключение — это официально разрешённый обход детекта, поэтому:

- указывается **причина** (не «ложное срабатывание», а почему отправитель легитимен);
- указывается **срок**: постоянные исключения создаются только при реальной необходимости;
- владелец получает уведомление при истечении срока;
- подавленные сигналы остаются видны в карточке письма — аналитик видит, что именно подавлено;
- создание и отзыв фиксируются в аудите.

Перед созданием исключения стоит проверить, не решается ли проблема точнее: добавлением домена
в доверенную инфраструктуру (если отличается только Return-Path) или в разрешённые внешние
системы защищаемой идентичности (если сервис легитимно пишет от её имени).

---

## 7. Оповещение пользователей

Если письмо уже доставлено и опасно:

1. предупредить получателей напрямую (звонок или мессенджер — не почтой, если под угрозой почта);
2. при подозрении на ввод учётных данных — немедленная смена пароля и завершение сессий;
3. при вводе кода MFA — проверка активных сессий пользователя;
4. при выполненном платеже — немедленное обращение в банк, время критично.

Уведомления платформы **не содержат активных ссылок**: URL обезвреживаются (`http` → `hxxp`,
точки в квадратных скобках), чтобы оповещение само не стало каналом доставки.

## 8. Метрики процесса (§37)

| Метрика | Источник |
|---|---|
| Среднее время до триажа | `triaged_at - created_at` по инцидентам |
| Среднее время до реагирования | `remediated_at - created_at` |
| Доля ложных срабатываний | `msp_false_positive_total` к общему числу |
| Обращения сотрудников | `msp_employee_reports_total` |
| Размер кампаний | `msp_campaign_size` |
| Доступность провайдеров | `msp_provider_errors_total`, `msp_provider_latency_seconds` |

Рост доли ложных срабатываний означает, что пороги или правила требуют настройки.
Падение числа обращений сотрудников при росте детектов может означать потерю доверия
к платформе — это повод разобраться, а не повод для оптимизма.
