# Оценка качества детектирования

ТЗ 1.0.3 §2–§4, §7, §8, §35, §60. Как измеряется качество и почему некоторые метрики
возвращают «ничего» вместо нуля.

## Запуск

```bash
python scripts/evaluate_detection.py --gate --markdown report.md
```

| Флаг | Назначение |
|---|---|
| `--gate` | сравнить с базовой линией и порогами, выйти с кодом 1 при блокировке |
| `--update-baseline` | записать текущий результат как новую базовую линию |
| `--markdown FILE` | отчёт для человека |
| `--json FILE` | машинный результат |
| `--rules PATH` | прогнать кандидатский пакет правил вместо установленного |

## Почему метрика бывает пустой

`ratio()` возвращает `None`, а не `0.0` или `1.0`, когда знаменатель равен нулю. В отчётах это
печатается как `—`, в API возвращается как `null`, в консоли показывается как «—».

Это не аккуратность ради аккуратности. Дашборд, показывающий **0% ложных срабатываний** потому,
что аналитик ещё ничего не разметил, читается как успех — и это самое опасное число, которое
может показать продукт. Точно так же «precision 1.000» у правила, по которому не было ни одного
решения аналитика, означает «не проверялось», а не «идеально».

Разделение доведено до уровня матрицы ошибок:

| Поле | Что означает |
|---|---|
| `unknown` | вердикт UNKNOWN там, где ожидалась атака — это пропуск |
| `correctly_uncertain` | вердикт UNKNOWN там, где неопределённость и ожидалась |
| `unscannable` | письмо не удалось проверить — не детект и не чистый результат |
| `skipped` | кейс не выполнялся (например, требует обогащения, которое отключено) |

Поле `correctly_uncertain` появилось после того, как первая версия метрики засчитывала
правильную неопределённость как пропуск и давала recall 0.923 вместо 0.987. Кейс, в котором
честный ответ — «не могу сказать», не является ошибкой.

## Спам считается отдельно

Спам — нежелательная почта, а не атака. Пометить его подозрительным — не ложное срабатывание;
приравнять к атаке — ошибка. Поэтому `spam_total` и `spam_escalated` считаются отдельной парой,
а спам-кейсы не входят ни в precision, ни в recall.

## Гейт

Конфигурация — `datasets/detection_gate.yaml`:

```yaml
detection_gate:
  overall_precision_min: 0.95
  bec_recall_min: 0.85
  impersonation_recall_min: 0.90
  phishing_recall_min: 0.85
  max_regression_percent: 3
  max_benign_trigger_rate: 0.25
  high_severity_categories: [bec, phishing, impersonation, credential_theft,
                             malicious_attachment, supplier_fraud, invoice_fraud, payroll_fraud]
  critical_case_ids: [GWC-011, GWC-016, GWC-006, BEC-001, PHI-043]
```

Гейт блокирует выпуск при любом из условий:

1. precision ниже абсолютного порога;
2. recall ниже порога в категории высокой серьёзности;
3. падение метрики относительно базовой линии больше чем на `max_regression_percent`;
4. провал критического кейса (`critical_case_ids`) — такие кейсы не прощаются никогда;
5. срабатывание правил на безобидной почте чаще `max_benign_trigger_rate`;
6. активное правило без владельца.

Абсолютные пороги и относительная регрессия нужны вместе: без абсолютных можно медленно
скатиться, каждый раз теряя по 2%; без относительной — не заметить резкого ухудшения, которое
пока укладывается в порог.

**Известные пробелы становятся предупреждениями, а не блокерами.** Провал кейса, у которого
указан `known_gap` из [реестра пробелов](DETECTION_GAPS.md), гейт не блокирует: ограничение,
которое рассмотрели и записали, — не неожиданность. Провал без записи — регрессия.

## Базовая линия

`datasets/baseline.json` хранит отпечаток пакета правил, контрольную сумму датасета, сводную
матрицу, метрики по категориям и список прошедших кейсов. Последнее позволяет гейту сказать не
только «recall упал», но и «перестали проходить именно эти кейсы».

Обновление базовой линии — осознанное действие (`--update-baseline`), попадающее в коммит
рядом с изменением, которое его потребовало.

## Проверка, что гейт работает

Гейт, который никогда не блокирует, бесполезен. Проверено двумя способами:

1. Прогон с отключёнными правилами BEC (`--rules` с урезанным пакетом) → гейт блокирует с
   кодом выхода 1 по порогу `bec_recall_min`.
2. Первая попытка такой проверки **ничего не показала**: BEC-кейсы корпуса срабатывали ещё и по
   правилам имитации, поэтому отключение восьми правил BEC не меняло вердиктов. Это была
   слабость корпуса, а не гейта. Добавлены кейсы компрометации поставщика и счётного
   мошенничества, изолирующие именно содержательные правила BEC, — после чего гейт заблокировал
   прогон, как и должен был.

Вторая история важнее первой: она показывает, зачем корпус проверяется на способность
отличать, а не только на прохождение.

## Метрики по правилам

| Метрика | Смысл |
|---|---|
| `total_triggers` | сколько раз сработало |
| `true_positive` / `false_positive` | срабатывания на атаках и на безобидной почте |
| `missed_expectations` | кейсы, где правило ожидалось и не сработало |
| `forbidden_hits` | срабатывания там, где кейс их прямо запрещает |
| `precision` | `None`, если решений не было |

Отдельно выделяются:

- **Шумные правила** — доля ложных выше 30% при не менее пяти решениях.
- **Молчащие правила** — активные, не сработавшие ни разу. Не всегда дефект: правило может
  закрывать редкий сценарий. Но молчащее месяцами правило стоит либо подкрепить кейсом, либо
  вернуть в теневой режим.
- **Правила без владельца** — блокер гейта и критерий выхода §60.

## Что нашла оценка при внедрении

Фреймворк оправдал себя на первом же прогоне:

| Находка | Суть |
|---|---|
| 10 ложных срабатываний | сотрудник с двумя ящиками «имитировал сам себя» (4 × MALICIOUS); подрядчик с названием отдела, совпадающим с нашим (6 × SUSPICIOUS) |
| Дефект метрики | правильная неопределённость считалась пропуском |
| Дефект метрики | precision и recall могли вернуть 0.0 при отсутствии данных |
| Слабость корпуса | BEC-кейсы перекрывались правилами имитации |
| Ошибки в собственной разметке | домен, не являющийся опечаточным ни по одной технике; «счёт на оплату» без признаков мошенничества, неотличимый от легитимного письма |

После исправлений: precision 0.941 → 1.000, recall 0.923 → 0.990.
