# Подпись DKIM исходящей почты

**Относится к:** ТЗ MSP 1.2 §22–§24, §34
**Код:** `msp_antispam/dkim_keys.py`, `rspamd_config.py` (подпись), `overlay.py`, `node.py keygen`; проверки — `tests/spam/test_dkim_signing.py`, `tests/spam/test_panel_antispam.py`, `tests/unit/test_antispam_core.py`

> Подпись допускается **только для лабораторного или пилотного домена** (настройка `MSP_ANTISPAM_DKIM_SIGNING_DOMAINS`)
> и **только на доверенном пути Exchange → шлюз**. Внешний отправитель корпоративной подписи получить не может.

## Как устроено

Подписывает Rspamd (модуль `dkim_signing`), а не MSP. Настройки жёсткие и не изменяются из интерфейса:
`sign_inbound = false`, `sign_authenticated = false`, `allow_hdrfrom_mismatch = false`, `allow_hdrfrom_multiple = false`,
`try_fallback = false`; подписываются только письма с адресов из `sign_networks` и только домены из карты селекторов
(домены с действующим ключом). Входящее направление подпись отключает отдельным правилом настроек.

* **Сети подписи определяет узел**, а не панель: панель назначает домены и ключи, но не может расширить, кого подписывать
  (проверено: назначение с `0.0.0.0/0` отвергается, лишнее поле игнорируется).
* **Закрытый ключ не хранится в базе.** В записи — только ссылка `private_key_ref` на файл в хранилище секретов узла. Ключ
  можно создать на узле (`python3 -m msp_antispam.node keygen --domain … --selector …`: файл создаётся с запретом
  перезаписи, наружу выдаётся только запись для DNS — рекомендуемый путь) либо в панели: тогда закрытая часть
  возвращается один раз и нигде не сохраняется.
* Домен без файла ключа на узле в конфигурацию не попадает; панели сообщается `dkim_missing_keys`, возникает тревога.

## Жизненный цикл ключа

```text
GENERATED → DNS_PENDING → READY → ACTIVE → RETIRING → RETIRED          (FAILED — отдельно)
```

Ротация: создать новый селектор → опубликовать запись в DNS → **панель сама проверяет** DNS → активировать → перекрытие
(старый ключ остаётся в DNS, письма подписываются новым) → вывести старый.

Перед активацией должно быть выполнено всё: запись TXT существует; ключ в ней совпадает с созданным (пробелы внутри `p=`
допустимы); имя соответствует селектору; DNS виден панели. Несоответствие, отозванный (пустой `p=`) ключ, отсутствие записи и
недоступность DNS оставляют ключ в `DNS_PENDING`, активация запрещена. Активирует **не тот, кто создал ключ** (четыре глаза),
событие пишется в аудит (в том числе отказ). Вывод ключа сначала переводит его в `RETIRING`; полностью вывести рано, пока
не истёк период перекрытия (7 дней): получатели ещё проверяют старые подписи.

## Проверенные сценарии (§24)

Корпоративный From; псевдоним; пустой конвертный отправитель; чужой домен в From с доверенного Exchange (не подписывается);
подделанный корпоративный From из Интернета (не подписывается); недоверенный клиент на внутреннем порту (письмо не принимается);
два заголовка From (не подписывается); отсутствующий закрытый ключ (письмо доставляется без подписи); неверная запись DNS
(независимая проверка не проходит); ротация селектора (новая подпись проверяется, старая остаётся действительной при
наличии обоих ключей в DNS). Подпись проверяет независимая программа (dkimpy) по доставленным байтам.
