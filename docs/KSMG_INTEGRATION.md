# Подключение Kaspersky Secure Mail Gateway

**Относится к:** ТЗ 1.0.2 §18, §24, §27; ТЗ 1.0.1 §4.3
**Реализация:** `providers/mail-gateway/msp_mail_gateway/ksmg.py`

---

## 1. Роль KSMG в схеме

```text
Internet → KSMG → Exchange → MSP → Outlook / Security Console
```

KSMG проверяет письмо при доставке средствами, которых у платформы нет: полноценным антивирусным
движком и, в части конфигураций, песочницей. MSP работает **после** доставки и ловит то, что
шлюз пропускает штатно — подмену отправителя, BEC, социальную инженерию без вложений и ссылок.

Из этого следуют два правила, и они не симметричны:

* **обнаружение KSMG повышает** вердикт MSP, вплоть до жёсткого сигнала;
* **отсутствие обнаружения не снижает** его никогда.

Сочетание «KSMG: чисто + MSP: HIGH_RISK» — нормальное рабочее состояние, а не расхождение,
требующее исправления. Оно показывается аналитику явно, чтобы разница была объяснена, а не
выглядела ошибкой одной из систем.

## 2. Читаемые заголовки

Набор заголовков зависит от версии KSMG и политики, поэтому адаптер читает то, что присутствует,
а не требует фиксированной схемы.

| Движок | Заголовки статуса | Дополнительно |
|---|---|---|
| Антивирус | `X-KSMG-Antivirus-Status`, `X-KSMG-AV-Status`, `X-KSMG-Antivirus` | `X-KSMG-Antivirus-Method` |
| Антиспам | `X-KSMG-AntiSpam-Status`, `X-KSMG-AS-Status`, `X-KSMG-AntiSpam` | `X-KSMG-AntiSpam-Rate`, `-Info`, `-Version` |
| Антифишинг | `X-KSMG-AntiPhishing-Status`, `X-KSMG-AP-Status`, `X-KSMG-AntiPhishing` | `X-KSMG-AntiPhishing-Info` |
| Политика | `X-KSMG-Rule-Id`, `X-KSMG-Rule-Name`, `X-KSMG-Policy`, `X-KSMG-Action` | |

### Нормализация статусов

| Значение KSMG | Нормализованный вердикт |
|---|---|
| `Clean`, `Not detected`, `No threats` | `CLEAN_OBSERVED` |
| `Detected`, `Infected` (антивирус) | `MALICIOUS` |
| `Detected` (антифишинг) | `PHISHING` |
| `Detected`, `Spam` (антиспам) | `SPAM` |
| `Probable spam` | `SUSPICIOUS` |
| нераспознанное | `UNKNOWN` |

Один и тот же `Detected` означает разное в зависимости от движка, который его написал, — адаптер
это учитывает.

**Нераспознанный статус становится `UNKNOWN`, а не `CLEAN_OBSERVED`.** Если заголовки KSMG есть,
но ни один известный статус прочитать не удалось, записывается факт «шлюз обработал письмо,
вердикт прочитать не удалось» вместе со списком найденных заголовков. Вердикт, который не удалось
прочитать, — это не вердикт «чисто».

Имя угрозы извлекается из статуса (`Detected: EICAR-Test-File` → `EICAR-Test-File`), оценка
антиспама — из `X-KSMG-AntiSpam-Rate`.

## 3. Настройка

### Шаг 1. Зарегистрировать шлюз

**Настройки → Почтовые шлюзы → Добавить шлюз**

| Поле | Значение |
|---|---|
| Идентификатор | `ksmg` |
| Тип провайдера | `ksmg` |
| Отображаемое имя | `KSMG` |

Либо через API:

```bash
curl -X POST https://mail-security.corp.example/api/v1/gateways \
  -H "Content-Type: application/json" -H "X-CSRF-Token: $CSRF" -b "$COOKIE" \
  -d '{"provider_id":"ksmg","provider_type":"ksmg","display_name":"KSMG"}'
```

### Шаг 2. Описать доверенные узлы — **обязательно**

Без этого шага заголовки KSMG будут показываться аналитику и **не будут учитываться**: подтвердить
прохождение через шлюз нечем. Консоль на это явно предупреждает.

```bash
curl -X POST .../api/v1/gateways/$GATEWAY_ID/hops \
  -d '{
        "hop_type": "gateway",
        "hostname": "ksmg-01.corp.example",
        "ip_networks": ["10.20.0.0/24"],
        "authserv_ids": ["ksmg-01.corp.example"]
      }'
```

Для кластера добавьте узел на каждую ноду либо одну запись с сетью, покрывающей все ноды.

### Шаг 3. Описать почтовый сервер

Это самая частая ошибка настройки: описать шлюз и забыть Exchange. `Authentication-Results`
пишет почтовый сервер, и если он не объявлен доверенным узлом, каждое обычное письмо получит
сигнал подделки.

```bash
curl -X POST .../api/v1/gateways/hops \
  -d '{"hop_type":"exchange_mailbox","hostname":"mx.corp.example",
       "authserv_ids":["mx.corp.example"]}'
```

### Шаг 4. Проверить

```bash
docker compose exec api python scripts/probe_exchange.py --section mailflow
```

Ожидаемый результат: шлюз в списке, узлов не меньше двух, `authserv-id` заданы.

## 4. Упрощённая настройка без топологии

`MSP_TRUSTED_GATEWAYS=ksmg` поддерживается как сокращение для развёртывания, которое ещё не
описало свою топологию в консоли. Такой шлюз **зарегистрирован, но не имеет доверенных узлов**:
его заголовки разбираются и показываются, но не учитываются.

Это ровно то состояние, которое описывает ТЗ 1.0.1 §4.3: назвать продукт — не доказать, что
письмо через него прошло. Проверка готовности сообщает об этом предупреждением.

## 5. Как это выглядит аналитику

Карточка письма, блок **Upstream Protection**:

```text
KSMG
  Антивирус:    Обнаружений нет      подтверждено цепочкой доставки
  Антиспам:     Обнаружений нет      подтверждено цепочкой доставки
  Антифишинг:   Обнаружений нет      подтверждено цепочкой доставки

MSP
  HIGH_RISK

Причины:
  - подмена имени руководителя
  - внешний Reply-To
  - домен, похожий на корпоративный
  - просьба изменить банковские реквизиты

Расхождения источников:
  Шлюз ничего не нашёл, платформа считает письмо опасным.
  Это штатная ситуация: атаки без вложений и ссылок шлюз пропускает.
```

Неподтверждённый вердикт рисуется зачёркнутым, рядом — причина, по которой он не учтён.

## 6. Правила детектирования

| Правило | Условие | Вес |
|---|---|---|
| `GW-001` | подтверждённое обнаружение вредоносного | **жёсткий сигнал**, critical |
| `GW-004` | подтверждённое обнаружение фишинга | high, 60 |
| `GW-002` | подтверждённый спам | low |
| `GW-003` | промежуточная оценка | medium |
| `GW-011` | подтверждённое «чисто» | **вес 0**, только для полноты картины |
| `GW-012` | заголовки KSMG не подтверждены цепочкой | high, 45 |
| `GW-010` | заголовки шлюза, который организация не использует | medium |

`GW-001` — единственное место, где внешний источник может сам по себе поднять вердикт до
`MALICIOUS`. Это оправдано: у KSMG есть антивирусный движок, которого у платформы нет
(ТЗ 1.0.2 §27).

## 7. API KSMG

Если конкретная версия и конфигурация KSMG предоставляет подходящий API, он выносится в
**отдельный адаптер** на базе `msp_mail_gateway.api_base` и не смешивается с разбором заголовков
(ТЗ 1.0.2 §18). Смешивать их нельзя: иначе доверие к заголовкам стало бы зависеть от доступности
API.

Требования к такому адаптеру — в [`MAIL_GATEWAY_PROVIDER.md`](MAIL_GATEWAY_PROVIDER.md) §10 и
[`MULTI_GATEWAY_SECURITY_MODEL.md`](MULTI_GATEWAY_SECURITY_MODEL.md) §4. На этапе 1.0.2 API
KSMG не реализован.

## 8. Что делать при срабатывании GW-012

`GW-012` означает: письмо содержит заголовки KSMG, но цепочка `Received` прохождение через
зарегистрированный шлюз не подтверждает.

Два объяснения, и различить их можно:

1. **Подделка.** Отправитель скопировал заголовки, чтобы письмо выглядело проверенным. Оцените
   письмо по остальным признакам; отметку о проверке не учитывайте.
2. **Ошибка настройки.** Имя или сеть узла заданы неверно, либо изменилась маршрутизация. Сверьте
   `hostname` и `ip_networks` с фактической цепочкой из карточки письма (блок «Заголовки»).

Если `GW-012` срабатывает на **всех** письмах — это настройка, а не атака.
