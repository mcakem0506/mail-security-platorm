# Классификация данных и хранение

Соответствует §2.4, §26.1, §27 ТЗ.

---

## 1. Классы данных

| Класс | Что относится | Где хранится | Кто имеет доступ |
|---|---|---|---|
| **K1 — критичный** | исходные EML, вложения, тело письма, темы | object storage (EML, вложения), PostgreSQL (нормализованное тело) | Viewer и выше, с записью в аудит |
| **K2 — чувствительный** | адреса отправителей и получателей, заголовки, индикаторы, результаты анализа | PostgreSQL | Viewer и выше |
| **K3 — внутренний** | правила детектирования, политики, защищаемые идентичности, конфигурация провайдеров | PostgreSQL, файлы правил | Security Admin |
| **K4 — служебный** | аудит, метрики, health, журналы задач | PostgreSQL, логи | Security Admin, Platform Admin |
| **K5 — секреты** | пароли, ключи API, ключ подписи сессий | файлы секретов, вне БД и вне Git | только операционный процесс |

## 2. Разделение хранения (§26.1)

Содержимое писем намеренно разделено на категории с независимым сроком хранения. Благодаря этому
можно удалить исходные письма, сохранив метаданные и результаты для статистики и корреляции.

| Категория | Где | Срок по умолчанию | Что остаётся после удаления |
|---|---|---|---|
| Метаданные письма | PostgreSQL, `mail_messages` | 180 дней | — |
| Нормализованный текст и санитизированный HTML | PostgreSQL, `mail_contents` | 180 дней | запись `normalized_purged_at` |
| Исходный EML | object storage | 30 дней | запись `raw_eml_purged_at`, хеш содержимого |
| Вложения | object storage | 30 дней | запись `purged_at`, хеш, размер, признаки, результат сканирования |
| Вредоносные образцы | object storage | 365 дней (отдельная политика) | — |
| Результаты анализа и сигналы | PostgreSQL | 365 дней | — |
| Ответы провайдеров | PostgreSQL, `provider_lookups` | 365 дней | — |
| Аудит | PostgreSQL, `audit_events` | 400 дней | — |

Сроки задаются переменными `MSP_RETENTION_*` и **подлежат утверждению организацией** —
значения по умолчанию являются предложением из §27, а не готовым решением.

## 3. Что удаляется и что сохраняется

Retention удаляет **содержимое**, сохраняя технический факт удаления (§27):

```text
До retention:
  mail_messages     тема, отправитель, получатели, хеш, признаки
  mail_contents     нормализованный текст, санитизированный HTML, ключ EML
  attachments       имя, тип, размер, хеш, признаки, ключ в хранилище
  object storage    сам EML, сами вложения

После retention (раздел raw_eml, 30 дней):
  mail_messages     без изменений
  mail_contents     raw_eml_key = NULL, raw_eml_purged_at = <дата>
  attachments       storage_key = NULL, purged_at = <дата>
  object storage    объекты удалены
```

Это позволяет ответить на вопрос «было ли письмо и что о нём известно» даже после удаления
содержимого, и одновременно ограничить срок хранения самой переписки.

Каждый запуск retention оставляет запись в `retention_runs` (категория, количество, граница
по дате) и событие в аудите.

### Вредоносные образцы

Вложение с подтверждённым обнаружением локального сканера хранится по отдельной, более длинной
политике (`MSP_RETENTION_MALICIOUS_SAMPLE_DAYS`), поскольку нужно для расследований и повторного
анализа. Количество сохранённых образцов фиксируется в `retention_runs.detail`.

## 4. Данные, передаваемые за пределы организации

По умолчанию платформа **не передаёт наружу** содержимое писем ни в каком виде.

| Данные | Передаются наружу | Условие |
|---|:--:|---|
| SHA-256 вложения | да | разрешено по умолчанию; не раскрывает содержимое |
| Домен из письма | да | кроме корпоративных домено́в |
| IP-адрес | да | разрешено по умолчанию |
| URL (только хост) | нет | требует `MSP_TI_ALLOW_URL=true` |
| URL с путём и параметрами | нет | требует дополнительно `MSP_TI_ALLOW_URL_PATH=true`; чувствительные параметры блокируются всегда |
| Адрес отправителя | нет | требует `MSP_TI_ALLOW_SENDER_EMAIL=true` |
| Корпоративные домены | нет | требует `MSP_TI_ALLOW_INTERNAL_DOMAINS=true` |
| Тема письма | нет | не передаётся никогда |
| Тело письма | нет | не передаётся никогда |
| Файл вложения | нет | только Private Scanning после отдельного согласования |
| Текст для семантического анализа | нет | только при включении; текст проходит редактирование адресов, URL, IBAN, карт, телефонов и сумм |

Каждая блокировка политикой записывается со статусом `POLICY_BLOCKED` и причиной. Этот статус
**не равен** «чисто» и не понижает риск.

## 5. Персональные данные

| Данные | Источник | Минимизация |
|---|---|---|
| Адрес электронной почты | письмо, AD | необходим для работы |
| Отображаемое имя | письмо, AD | необходимо для детектирования подмены |
| Подразделение | AD | используется для оценки контекста запроса |
| Должность | AD | **опционально**, `MSP_AD_INCLUDE_OPTIONAL_ATTRIBUTES` |
| Руководитель | AD | **опционально**, по умолчанию не синхронизируется |
| Телефон, адрес, фотография | — | **не синхронизируются вообще** |

Из AD читается минимальный набор атрибутов (§10). Расширение списка — решение в области
приватности, а не техническое.

В журналы не попадают: тела писем, полные URL с параметрами, секреты, токены, cookie.
В access-логах nginx query string не пишется, поскольку может содержать значения индикаторов.

## 6. Права доступа к содержимому

| Роль | Метаданные | Содержимое письма | Вложения |
|---|:--:|:--:|:--:|
| Employee | только свои | только свои | нет |
| Security Viewer | все | да, с аудитом | нет |
| Security Analyst | все | да, с аудитом | да, с подтверждением и аудитом |
| Security Admin | все | да, с аудитом | да |
| Platform Admin | **нет** | **нет** | **нет** |

Разделение администрирования платформы и доступа к переписке — требование §23 и заложено
в матрицу прав.

---

## 7. Legal hold

В v1 механизм legal hold отсутствует. Retention-воркер спроектирован под его добавление:
удаление выполняется выборками с проверкой условий, поэтому добавление флага удержания
на сообщение не потребует изменения структуры данных (§27).

До появления механизма: при необходимости сохранить данные по запросу — снять резервную копию
и увеличить соответствующие сроки хранения.
