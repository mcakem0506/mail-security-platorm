# Проверка анти-спама на реальном потоке

**Относится к:** ТЗ MSP 1.2 §29, §39, §43
**Код:** `msp_antispam/validation.py`, `apps/api/msp_api/services/antispam.py`; API — `/gateway/spam/review-queue`, `/spam/messages/{id}/review`, `/spam/validation`, блок `antispam` в `/detection/real-flow/summary`

Цель — измерить, насколько можно доверять предложениям сканера, **до** того как этап 1.3 заговорит об отказе. Синтетический
корпус (`datasets/spam`) защищает от регрессий, но качества на настоящей почте не измеряет.

## Что сохраняется по каждому письму

Класс спама, оценка Rspamd, результаты SPF/DKIM/DMARC/ARC, репутация, предложенное действие, версии сканера, конфигурации и
отображения символов. В сводку реального потока добавлен блок `antispam`.

## Обязательные выборки для просмотра

Аналитик просматривает и выносит решение (`HAM` / `SPAM` / `BULK`) по:

1. **всем** письмам с предложенным отказом (`SUGGESTED_REJECT`);
2. **всем** провалам DMARC при политике `reject` (`DMARC_REJECT_FAILURE`);
3. **всем** письмам из списков репутации (`RBL_LISTED`);
4. **всем** письмам с высокой оценкой (`HIGH_SCORE`);
5. случайной воспроизводимой выборке писем с **низкой** оценкой (`LOW_SCORE_SAMPLE`) — это единственное место, где
   измеряются пропуски;
6. **всем** расхождениям результатов аутентификации с вышестоящим шлюзом (`AUTH_CONFLICT`).

Решение аналитика — единственный источник исхода: только оно изменяет счётчики репутации и порождает метрики. Решение
пишется в аудит.

## Метрики (определения)

| Метрика | Определение | Оговорка |
|---|---|---|
| `spam_fp_per_1000` | письма, признанные спамом, а по решению аналитика легитимные, на 1000 просканированных | **нижняя граница**, пока просмотрена не вся выборка; рядом всегда `reviewed_fraction` |
| `auth_fp_per_1000` | провалы DMARC с политикой reject, признанные легитимными, на 1000 | то же |
| `rbl_fp_per_1000` | совпадения со списками, признанные легитимными, на 1000 | то же |
| `suggested_reject_fp_rate` | доля легитимных среди *просмотренных* писем с предложенным отказом | с верхней границей доверительного интервала Вильсона |
| `spam_fn`, `score_at_fn`, `symbols_at_fn` | пропущенный спам (по низкой выборке), оценка и символы при пропуске | перечень символов показывает, что сканеру не хватило |
| `spam_precision`, `spam_recall`, `bulk_precision` | по просмотренным письмам | recall — оценка, не измерение |

Доля без знаменателя — `null`, а не ноль: ноль читался бы как «ложных нет».

## Условие допуска к разговору об отказе (этап 1.3)

`reject_safety` возвращает `ready_for_discussion = true` только если одновременно: просмотрено не меньше 300 писем с предложенным
отказом, **верхняя** граница доли ложных не выше 1 %, и измерялись пропуски (есть случайная выборка низкой оценки). Иначе
перечисляются причины (`INSUFFICIENT_SAMPLE`, `FP_NOT_PROVEN_LOW`, `NO_LOW_SCORE_SAMPLE`). Малая выборка без ошибок ничего не доказывает,
поэтому количество проверяется отдельно. Эта проверка ничего не включает: принуждения в 1.2 нет, а готовность — лишь
основание для отдельного решения.

Известные отличия сканера от RFC 9989 ([DMARC_RFC9989.md](DMARC_RFC9989.md)) учитываются при просмотре `DMARC_REJECT_FAILURE`.

## Состояние на момент приёмки этапа

Реальных данных нет: боевое переключение MX не выполнялось, шлюз получает только лабораторную почту. Поэтому все метрики
выше — `null` или нули на лабораторной выборке, `ready_for_discussion = false`, а решение приёмки — `READY_WITH_WARNINGS`
([MSP_1_2_ACCEPTANCE.md](MSP_1_2_ACCEPTANCE.md)).
