# Репутация: провайдеры, локальная история, HELO/PTR

**Относится к:** ТЗ MSP 1.2 §14–§18, §32
**Код:** `msp_antispam/providers.py`, `rbl_render.py`, `reputation.py`, `rates.py`, `helo.py`; API — `/api/v1/gateway/spam/providers`, `/reputation/*`

## 1. Каркас провайдеров (DNSBL)

`ReputationProvider`: идентификатор, тип (`DNSBL`, `DNSWL`, `URIBL`), название, включён ли, режим лицензии, типы запросов,
класс приватности, статус. Лицензионный допуск и четыре глаза — в [RBL_LICENSING.md](RBL_LICENSING.md).

**Типы запросов включаются по одному**: `CLIENT_IP`, `HELO`, `RDNS`, `SENDER_DOMAIN`, `DKIM_DOMAIN`, `URL_HOST`,
`REPLY_TO_DOMAIN`. Каждый уносит из письма свой кусок данных; «включить все» не существует. Проверено на стенде:
при включённом только `CLIENT_IP` в зону провайдера уходит запрос по адресу клиента и не уходят ни домен отправителя, ни HELO.

**Результат запроса:** `LISTED`, `NOT_LISTED`, `TEMPERROR`, `NXDOMAIN`, `PROVIDER_ERROR`, `DISABLED`. Ответы
`127.255.255.x` (ошибка использования у многих провайдеров) листингом не считаются — код возврата перечисляется явно
(`return_codes`, по умолчанию `127.0.0.2`). `NOT_LISTED` **не снижает** риск. Тайм-аут и SERVFAIL провайдера не мешают
почте (проверено): запрос ограничен временем и не блокирует поток.

Правила провайдеров в сканере создаёт модуль `rbl` целиком из проверяемой модели: пакетный список публичных зон
в работе не остаётся (секция заменяется), а не просто выключается.

### Секретные зоны

Если зона провайдера содержит секрет, её имя в базе, интерфейсе, журналах, выпуске конфигурации и результатах MSP **не
появляется**. В хранилище секретов узла лежит файл из одной строки `rbl = "<зона>";`; правило генерирует MSP и подключает
файл внутрь. Параметры символов такого провайдера отбрасываются при разборе записи сканера. Проверено: ни выпуск, ни
запись, ни журнал сканера секрет не содержат.

## 2. Локальная репутация

Для адреса источника и домена отправителя ведутся: первое и последнее наблюдение, число писем, из них угроз, спама,
легитимных, различные отправители и домены, доля писем с пройденной аутентификацией (для домена), подтверждение
аналитика.

* **Затухание.** Счётчики уменьшаются вдвое за 30 дней; наблюдение старше окна (180 дней) не учитывается.
* **Исход письма узнаёт только человек.** Автоматически счётчики растут по числу писем; спам и легитимность добавляются
  решением аналитика при просмотре.
* **Хорошая история не отключает жёсткие сигналы.** Вредоносное вложение, BEC, имитация домена и совпадение с TI
  не подавляются положительной репутацией (`suppresses_hard_signals` — всегда `false`, проверяется тестом).
* **Нет оценки без объяснения.** Консоль показывает уровень, число и причины словами.

## 3. Зрелость истории организации и аномалии частоты

«Отправитель не наблюдался» информативно только при зрелой истории организации (урок MSP 1.0.4): организация считается
зрелой при возрасте от 30 дней и от 500 писем. Аномалии частоты — только свидетельства: много получателей у одного
отправителя, много отправителей с одного адреса, всплеск объёма домена, пачка писем многим получателям, а для
исходящей почты — `OUTBOUND_ACCOUNT_ANOMALY`. Даже высокая степень — наблюдение и тревога, не блокировка.

## 4. HELO и PTR

Сигналы HELO: отсутствует, IP-литерал, неверный синтаксис, не соответствует обратному имени, имитация защищаемого домена,
внутреннее имя от внешнего источника. Состояние PTR: `NONE`, `PTR_PRESENT`, `FCrDNS_PASS`, `FCrDNS_FAIL`, `TEMPERROR`.
Источник подтверждённого имени — заголовок `Received`, добавленный самим шлюзом: Postfix записывает обратное имя только
если прямая проверка подтвердила адрес. Если поиск имени в Postfix выключен, подтверждённость неизвестна (`PTR_PRESENT`), а не
провалена. Это свидетельства о репутации, не вердикт: письма не отклоняются ни при каком сочетании.
