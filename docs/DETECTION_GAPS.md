# Известные пробелы детектирования

ТЗ 1.0.3 §27, §60. Чего платформа не умеет — и почему этот документ существует.

## Зачем публиковать пробелы

Пробел, которого нет в списке, ничем не отличается от пробела, о котором никто не знает. Второй
и есть то, от чего страдают организации. Реестр существует, чтобы «мы про это знали» нельзя
было сказать задним числом.

Практические следствия:

- **Гейт прощает зарегистрированный пробел и блокирует незарегистрированный.** Кейс корпуса со
  ссылкой `known_gap` при провале даёт предупреждение; провал без записи — регрессия и блокер.
- **У пробела есть владелец и целевой релиз.** Запись без них — не пробел, а жалоба.
- **У пробела есть компенсирующая мера.** Если ограничение нельзя закрыть сейчас, должно быть
  понятно, что защищает в это время.

Источник истины — `datasets/detection_gaps.yaml`, рядом с кодом и в том же ревью. Таблица в
базе существует для консоли (`GET /api/v1/detection/gaps`), чтобы пробелы были видны рядом с
пропусками, которые в них попадают.

## Текущий реестр

### GAP-001 — вставка символа в короткой метке домена

| | |
|---|---|
| Категория | имитация |
| Серьёзность | средняя |
| Статус | **принят** (осознанное ограничение) |
| Владелец | detection-sender@corp.example |
| Целевой релиз | MSP 1.0.4 |
| Кейсы | IMP-017, IMP-018 |

Домены вида `coorp.example` или `corpp.example` для `corp.example` не распознаются как
опечаточные.

**Причина.** Проверка опечаточных доменов не применяется к меткам короче шести символов. Для
четырёхбуквенной метки расстояние в один символ даёт десятки обычных слов (`card`, `core`,
`cork`, `corn`), и снижение порога дало бы поток ложных срабатываний на легитимной почте. Здесь
цена ложного срабатывания выше цены пропуска — ограничение принято сознательно.

**Что защищает пока.** Такие письма ловятся остальными признаками: отсутствие истории
отправителя, провал DMARC, платёжная тематика. Организациям с короткими корпоративными доменами
рекомендуется зарегистрировать очевидные варианты написания.

**Как планируется закрыть.** Проверять вставку символа для коротких меток только при совпадении
по skeleton и наличии дополнительного признака (первое письмо от отправителя, провал
аутентификации).

### GAP-002 — содержимое QR-кода читается только с необязательным компонентом

| | |
|---|---|
| Категория | квишинг |
| Серьёзность | низкая (была средняя) |
| Статус | **на подтверждении** (`VALIDATION`) |
| Владелец | detection-core@corp.example |
| Целевой релиз | MSP 1.0.3B |
| Кейсы | QRD-001, QRD-002 |

Декодер появился в MSP 1.0.3B (§31). Ссылка из QR-кода читается, если установлен необязательный
компонент `qr` (`pip install -e '.[qr]'`); без него определяется только наличие кода.

**Почему компонент необязательный.** Декодер разбирает пиксели изображений из недоверенных
писем. Он вынесен из основного рабочего процесса и запускается отдельным процессом
(`python -m msp_mail_parser.qr_worker`) с лимитами: 10 секунд, 40 млн пикселей, 8 МБ на
изображение, 2048 байт на полезную нагрузку. Держать такую зависимость внутри воркера означало
бы отдавать ей байты злоумышленника без изоляции.

**Что защищает при установленном декодере.** Ссылка из кода идёт обычным конвейером URL, и
правило URL-032 переведено в `ACTIVE` (версия 2, `change_reason` ссылается на кейсы QRD-001 и
QRD-002).

**Что защищает без декодера.** URL-030 и URL-031 по форме изображения и формулировкам письма.
Непрочитанный код фиксируется как `QR_NOT_DECODED` и попадает в `missing_evidence`: письмо не
получает чистый вердикт за счёт того, чего никто не прочитал. Истечение таймаута декодера —
`DECODE_TIMEOUT`, и это тоже непрочитанный код, а не отсутствие кода.

**Чего это стоит.** Запуск отдельного процесса — около 545 мс на письмо с изображениями, и это
запуск интерпретатора, а не декодирование. Процесс один на письмо, а не на изображение, поэтому
стоимость ограничена сверху при любом их количестве. Бюджет анализа — 5 с. Снизить эту цену
можно только вернув декодер в основной воркер, то есть отдав ему пиксели недоверенного письма
без изоляции; обмен сознательно не сделан.

**Почему статус `VALIDATION`, а не `RESOLVED`.** Пробел закрывается не изменением кода, а
кейсом, который раньше падал, а теперь проходит, — и подтверждением на реальном потоке. До
подтверждения запись остаётся в реестре.

### GAP-003 — архивы 7z и RAR не разбираются

| | |
|---|---|
| Категория | опасные вложения |
| Серьёзность | средняя |
| Статус | **принят** |
| Владелец | detection-attachment@corp.example |
| Целевой релиз | MSP 1.1 |

**Причина.** В составе v1 нет безопасной внутрипроцессной библиотеки для этих форматов. Внешний
распаковщик означал бы исполнение стороннего кода над содержимым недоверенного письма.

**Что защищает пока.** Такие вложения помечаются как непроверенные, вердикт не опускается до
LOW_RISK, факт попадает в `missing_evidence`.

**Как планируется закрыть.** Оценить безопасные библиотеки либо разбор в изолированном контуре.

### GAP-004 — QR-коды внутри PDF-вложений не извлекаются

| | |
|---|---|
| Категория | квишинг |
| Серьёзность | средняя |
| Статус | **принят** |
| Владелец | detection-attachment@corp.example |
| Целевой релиз | MSP 1.1 |
| Кейсы | — |

Открыт в MSP 1.0.3B вместе с декодером QR. Декодер работает по изображениям письма; изображения
внутри PDF до него не доходят.

**Причина.** Извлечение изображений из PDF требует разбора самого PDF — формата с собственной
историей уязвимостей разбора. Безопасный конвейер для него в 1.0.3B не строился: это отдельная
работа, а не побочный результат добавления декодера.

**Что защищает пока.** PDF с изображениями помечается как разобранный не полностью, вердикт не
опускается до `LOW_RISK`, факт попадает в `missing_evidence`. Формулировки письма о сканировании
кода по-прежнему дают URL-030.

**Как планируется закрыть.** Извлечение изображений из PDF в том же изолированном процессе, что
и декодирование QR, с теми же лимитами по времени и памяти.

## Статусы

| Статус | Значение |
|---|---|
| `OPEN` | обнаружен, решение не принято |
| `ACCEPTED` | ограничение принято осознанно, с компенсирующей мерой |
| `IN_PROGRESS` | закрывается в текущем или следующем релизе |
| `VALIDATION` | код изменён, закрытие ещё не подтверждено |
| `RESOLVED` | закрыт и подтверждён |
| `WONT_FIX` | решено не закрывать |

`RESOLVED` и `WONT_FIX` — завершающие. `WONT_FIX` сделан завершающим намеренно: принятый риск,
навсегда остающийся в списке открытых, приучает всех игнорировать список.

`VALIDATION` добавлен в MSP 1.0.3B и стоит между «исправлено» и «закрыто». Он нужен потому, что
изменение кода — не доказательство закрытия: пробел закрывает кейс, который раньше падал, а
теперь проходит, плюс подтверждение на реальном потоке. Без этого состояния единственным
честным вариантом было бы держать закрытый пробел в `IN_PROGRESS`, и тогда «в работе» перестало
бы что-либо значить.

## Как добавить пробел

1. Записать в `datasets/detection_gaps.yaml`: описание, причину, серьёзность, владельца,
   целевой релиз, компенсирующую меру, план закрытия.
2. Связать с кейсами корпуса через `known_gap`, если они есть. Пробел без кейсов не измеряется —
   и день его закрытия никто не заметит.
3. Загрузить в базу: `POST /api/v1/detection/rules/sync`.

Пропуски, которые аналитики относят к пробелу, видны в поле `reported_misses`: это и есть
основание повысить приоритет закрытия.

MSP 1.0.3B добавил к записи три поля:

| Поле | Зачем |
|---|---|
| `discovered_from` | откуда пробел известен: аналитик, red team, учения, внешний отчёт |
| `example_analysis_ids` | настоящие письма, на которых он проявился, а не только кейсы корпуса |
| `compensating_controls` | что именно защищает, пока пробел открыт, перечнем, а не абзацем |

Последнее поле существует потому, что компенсирующая мера, описанная прозой, не проверяема.
Перечень можно сопоставить с действующими правилами и увидеть, что мера исчезла вместе с
правилом, которое её обеспечивало.

## Чего в реестре быть не должно

Реестр — не список идей и не бэклог. В него не попадают:

- возможности, которых никогда не обещали (например, анализ голосовых вложений);
- ограничения, не влияющие на детектирование;
- «правило могло бы быть точнее» без конкретного приёма, который оно пропускает.

Пробел — это **конкретный приём, который платформа не поймает**, с примером.
