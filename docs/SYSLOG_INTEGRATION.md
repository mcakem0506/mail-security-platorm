# Приём событий шлюза по syslog

**Относится к:** ТЗ 1.0.2 §20, §23, §34, §35
**Реализация:** `providers/mail-gateway/msp_mail_gateway/syslog.py`

---

## 1. Когда это нужно

Многие шлюзы не пишут вердикт в заголовки письма, но охотно отдают почтовый журнал. Syslog —
полноценный путь приёма evidence, но **опасный**: у обычного syslog нет никакой аутентификации.
Всё, что может достучаться до порта, может выдать себя за шлюз.

Поэтому приём устроен так, чтобы **отказывать по умолчанию**: без списка разрешённых источников
не принимается ничего.

---

## 2. Четыре защиты

Реализованы в `SyslogIngestor`, то есть применяются независимо от транспорта.

### Список разрешённых источников

Событие с адреса, не входящего в список зарегистрированных узлов шлюза, **отклоняется**, а не
помечается. Пустой список означает, что не принимается ничего.

```text
MSP_GATEWAY_SYSLOG_ALLOWED_SOURCES=10.20.0.11,10.20.0.12
```

Принимаются и отдельные адреса, и сети CIDR.

### Защита от повтора

Событие, чья отметка времени выходит за окно приёма, отклоняется. Захваченная строка журнала не
может быть отправлена повторно, чтобы переоткрыть закрытый вердикт.

```text
MSP_GATEWAY_SYSLOG_MAX_AGE_SECONDS   по умолчанию 900
```

Событие **без отметки времени** отклоняется тоже: без неё повтор неотличим от нового события.
Отметка из будущего дальше допустимого расхождения часов — тоже отказ.

### Дедупликация

Одно и то же событие, доставленное дважды (переотправка UDP, два коллектора), даёт одно
evidence, а не два. Ключ дедупликации собирается из источника, узла, приложения, идентификаторов
события и очереди, Message-ID, отметки времени и начала текста.

Повтор считается **ожидаемым трафиком**, а не пробелом интеграции: он учитывается счётчиком и не
попадает в dead-letter.

### Dead-letter

Строка, которую не удалось разобрать или принять, сохраняется вместе с причиной — она не
отбрасывается молча. Неизвестный формат означает пробел в интеграции, а не отсутствие событий, и
разница видна только если отказы где-то записаны.

```bash
curl .../api/v1/gateways/dead-letters | jq '.[] | {reason, source_ip, raw}'
```

Причины отказа: `source_not_allowed`, `replay_too_old`, `timestamp_in_future`, `missing_timestamp`,
`unparseable_format`, `oversized_event`, `unauthenticated_transport`.

## 3. Транспорт

| Транспорт | Пригодность |
|---|---|
| `tls` | предпочтительно; при поддержке шлюзом — с клиентским сертификатом |
| `tcp` | приемлемо |
| `udp` | **отклоняется в production**; поддерживается только потому, что часть устройств не умеет иного |

Источник UDP записывается как таковой, чтобы аналитик видел: это evidence, полученное по
неаутентифицированному каналу.

Клиентский сертификат даёт источнику **идентичность**, которой список адресов дать не может:
адрес можно подделать, сертификат — нет.

## 4. Настройка

```text
MSP_GATEWAY_SYSLOG_ENABLED=true
# Loopback по умолчанию. Задайте адрес явно, если события приходят с другого узла.
MSP_GATEWAY_SYSLOG_HOST=0.0.0.0
MSP_GATEWAY_SYSLOG_PORT=6514
MSP_GATEWAY_SYSLOG_TRANSPORT=tls
MSP_GATEWAY_SYSLOG_ALLOWED_SOURCES=10.20.0.11,10.20.0.12
MSP_GATEWAY_SYSLOG_TLS_CERTFILE=/etc/ssl/certs/syslog.pem
MSP_GATEWAY_SYSLOG_TLS_KEYFILE=/run/secrets/syslog_key
MSP_GATEWAY_SYSLOG_TLS_CLIENT_CA=/etc/ssl/certs/internal-ca.pem
```

Конфигурация отклоняется при запуске, если:

* приём включён, а список источников пуст;
* в production выбран UDP;
* выбран TLS без сертификата.

Прослушивание на всех интерфейсах (`0.0.0.0`) возможно, но это **осознанный выбор**, а не
значение по умолчанию, и в production он записывается предупреждением в журнал.

Затем зарегистрируйте шлюз типа `syslog`:

```bash
curl -X POST .../api/v1/gateways \
  -d '{"provider_id":"ksmg-syslog","provider_type":"syslog","display_name":"KSMG (syslog)",
       "settings":{"allowed_sources":["10.20.0.0/24"],"require_authenticated_transport":true}}'
```

## 5. Разбор и нормализация

Поддерживаются оба формата обрамления:

* **RFC 5424** — `<PRI>VERSION TIMESTAMP HOSTNAME APP PROCID MSGID [SD] MSG`
* **RFC 3164** — `<PRI>MMM dd hh:mm:ss HOSTNAME TAG: MSG`

Из текста извлекаются пары `ключ=значение`, а также `Message-ID` и `queue-id` по отдельным
шаблонам. Вердикт ищется в полях `verdict`, `action`, `result`, `disposition`, `status`,
`scan_result`, имя угрозы — в `threat`, `virus`, `malware`, `signature`, `rule`, оценка — в
`score`, `spam_score`, `rate`, `rating`.

Пример:

```text
<134>1 2025-09-01T10:00:00+03:00 ksmg-01 ksmg 1234 ID47 verdict=detected
  threat="EICAR-Test-File" message_id=<x@sender.example> queue_id=ab12
```

становится

```json
{
  "provider_id": "ksmg-syslog",
  "verdict": "MALICIOUS",
  "category": "antivirus",
  "threat_name": "EICAR-Test-File",
  "trusted": true,
  "trust_reason": "событие получено от разрешённого источника 10.20.0.11 (tls)",
  "source": "syslog",
  "normalized_detail": {"queue_id": "ab12", "hostname": "ksmg-01", "transport": "tls"}
}
```

Событие, прошедшее список источников, считается доверенным: в отличие от заголовка, оно не
путешествовало внутри письма, которое контролирует отправитель.

---

## 6. Корреляция с письмом

События сопоставляются с письмами по (в порядке предпочтения):

1. RFC `Message-ID`;
2. `queue-id`;
3. идентификатору сообщения на шлюзе.

Когда для одного письма накопилось несколько событий, приоритет отдаётся **отрицательному**
вердикту: обнаружение важнее последующей записи о доставке.

Ключи корреляции хранятся в `message_traces` (ТЗ 1.0.2 §23).

---

## 7. Ограничения по ресурсам

| Ограничение | Значение | Зачем |
|---|---|---|
| размер события | 32 КиБ | отказ до разбора: крупное событие — проблема ресурсов, а не сообщение |
| окно дедупликации | 20 000 событий | ограничивает память |
| dead-letter | 500 записей | кольцевой буфер |
| корреляция | 10 000 писем | LRU |

## 8. Метрики и оповещения

```text
msp_gateway_events_total{provider,source}
msp_gateway_event_parse_errors_total{provider,reason}
msp_gateway_last_event_timestamp{provider}
msp_gateway_health{provider}
```

Оповещения, которые стоит настроить:

| Условие | Что означает |
|---|---|
| события прекратились | шлюз перестал слать журнал либо изменилась маршрутизация |
| всплеск `source_not_allowed` | кто-то пытается подать события, либо добавлен узел, который не зарегистрировали |
| всплеск `unparseable_format` | шлюз обновили и формат изменился |
| рост `duplicate_event` | два коллектора шлют одно и то же |

**Пустой список dead-letter не означает, что шлюз работает.** Он означает, что платформа ничего
не отклоняла. Молчание шлюза видно по `msp_gateway_last_event_timestamp`.

## 9. Проверка

```bash
# С разрешённого адреса
logger -n 127.0.0.1 -P 6514 -T "<134>1 $(date -Is) ksmg-01 ksmg 1 ID1 verdict=clean"

# Что принято и что отклонено
curl .../api/v1/gateways | jq '.gateways[] | {provider_id, health}'
curl .../api/v1/gateways/dead-letters | jq 'length'
```
