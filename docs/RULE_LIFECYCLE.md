# Жизненный цикл правила

ТЗ 1.0.3 §9–§14, §24, §25. Как правило появляется, попадает в production, портится и уходит.

## Статусы

| Статус | Срабатывает | Влияет на вердикт | Назначение |
|---|---|---|---|
| `EXPERIMENTAL` | нет | нет | черновик, не загружается в production |
| `SHADOW` | да | **нет** | измеряется на реальной почте |
| `ACTIVE` | да | да | рабочее состояние |
| `DEGRADED` | да | нет | начало шуметь, владелец разбирается |
| `DISABLED` | нет | нет | выключено |
| `DEPRECATED` | нет | нет | заменено, оставлено для истории |

Ключевое свойство реализовано в коде, а не в инструкции:

```python
@property
def effective_weight(self) -> float:
    """A SHADOW rule contributes nothing by construction, not by configuration."""
    if self.status not in RULE_SCORING:
        return 0.0
    return self.weight if self.weight is not None else float(SEVERITY_BASE_WEIGHT[self.severity])
```

Теневое правило не даёт баллов **по построению**. Нельзя забыть поставить вес в ноль: статус
сам определяет, участвует ли правило в оценке. То же для `DEGRADED` — правило продолжает
измеряться, но перестаёт решать.

## Разрешённые переходы

```
EXPERIMENTAL → SHADOW → ACTIVE
                 ↑         ↓
                 └──── DEGRADED → DEPRECATED
                           ↓
                       DISABLED
```

- **В `ACTIVE` можно попасть только из `SHADOW`.** Правило не начинает влиять на вердикты, пока
  его не измерили на реальной почте. Переход `EXPERIMENTAL → ACTIVE` отклоняется API.
- **`ACTIVE` без владельца запрещён.** Активное правило без владельца некому настраивать в тот
  день, когда оно начнёт шуметь. Проверяется и при переходе, и гейтом детектирования.
- **`DEGRADED` не снимается по таймауту.** Возврат в `ACTIVE` — это решение владельца после
  разбора, а не истечение срока.

Матрица переходов — `_TRANSITIONS` в `apps/api/msp_api/routers/detection.py`.

## Теневой режим: зачем он измеряется

Теневое правило бесполезно, если его нельзя измерить. Поэтому флаг `shadow` и статус правила
на момент срабатывания **сохраняются в базе** вместе с сигналом:

```python
#: A shadow rule fired but contributed nothing to the score (ТЗ 1.0.3 §11).
#: Persisted because the only way to decide whether a candidate rule is ready to go ACTIVE
#: is to measure it against real mail.
shadow: Mapped[bool] = mapped_column(Boolean, default=False, index=True)
rule_status: Mapped[str] = mapped_column(String(16), default="ACTIVE")
```

`rule_status` хранится отдельно от текущего статуса правила: позднее изменение статуса не
должно задним числом менять то, как читается исторический вердикт.

Отчёт `GET /api/v1/detection/shadow` показывает по каждому теневому правилу: сколько раз
сработало, когда последний раз, сколько баллов дало бы. Это и есть материал для решения о
переводе в `ACTIVE`.

## Как меняется правило

1. **Правка в Git.** Файл правила меняется коммитом и проходит ревью. Это источник истины.
2. **Запрос в консоли.** `POST /api/v1/detection/rules/{id}/status` фиксирует намерение:
   статус, причину (минимум 10 символов), автора и ревьюера, плюс метрики правила на момент
   запроса. Ответ честно говорит, что текущий статус не изменился — он применится после ревью
   и деплоя.
3. **Гейт.** CI прогоняет золотой корпус и сравнивает с базовой линией.
4. **Деплой.** Пакет правил подхватывается из `rules/`; отпечаток пакета попадает в каждый
   последующий вердикт.

Разделение шагов 1 и 2 сделано сознательно: право менять статус через API без ревью означало бы,
что детектирование можно переконфигурировать в обход истории изменений.

Журнал изменений: `GET /api/v1/detection/rules/changes`, аудит — `rule.status_changed`.

## Симулятор

Перед изменением правила его можно прогнать на сохранённом письме:
`POST /api/v1/detection/simulate` с `message_id` и, при необходимости, `rule_id`.

Два свойства:

- **Симуляция ничего не меняет.** Вопрос «что сказали бы правила» не должен менять то, что они
  сказали.
- **Сужение вида не сужает вычисление.** При указании `rule_id` в ответе остаются сигналы
  только этого правила, но вердикт считается по всему пакету: эффект правила зависит от того,
  что сработало рядом.

Сравнение «до/после» (§14) — `detection_ops.compare()`: текущий пакет против
кандидата, с перечислением правил, которые начали и перестали срабатывать, и указанием,
изменился ли вердикт в сторону повышения или понижения.

## Повторный анализ и переоценка истории

| Операция | Что делает | По умолчанию |
|---|---|---|
| `POST /api/v1/analysis/{job_id}/replay` | повторяет один анализ как новую ревизию | dry-run |
| `POST /api/v1/detection/reevaluate` | отвечает, что сказали бы правила о почте за N дней | dry-run |

Ни одна из них не перезаписывает исходный результат. Новая ревизия хранит оба вердикта,
изменившиеся правила и версии движков. Перезапись уничтожила бы единственное свидетельство
того, что платформа сказала людям в тот момент, — именно то, что нужно расследованию через
полгода.

Переоценка истории нужна потому, что правило, написанное под живую кампанию, почти бесполезно,
если применяется только к завтрашней почте. Но её результат — предложение, пока человек не
решит применить.

Права: `detection:replay` — только у администратора ИБ. Симуляция (`detection:simulate`) — у
аналитика: она ничего не меняет.

## Исключения

Исключение — единственный механизм, который делает платформу сознательно слепой. Поэтому:

- **Четыре глаза (§24).** Автор исключения не может утвердить его сам —
  `can_approve_exception()` в `security/rbac.py`. Иначе «два утверждения» — формальность,
  которую один аналитик выполняет в одиночку.
- **Неутверждённое исключение инертно.** Свойство `active` возвращает `False`, пока нет второго
  утверждения: создание исключения не должно само по себе гасить сигнал о вредоносном вложении
  или имитации руководителя.
- **Срок и пересмотр.** У исключения есть `expires_at` и отдельное `review_at`: когда на него
  надо посмотреть, не дожидаясь истечения.
- **Учёт попаданий.** `hit_count` и `last_hit_at` показывают, работает ли исключение до сих
  пор. Исключение, не сработавшее ни разу за год, — кандидат на удаление.

Аудит: `exception.created`, `exception.approved`, `exception.revoked`, `exception.review_due`.
