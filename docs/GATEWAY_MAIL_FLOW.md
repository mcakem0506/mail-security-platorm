# Путь письма через шлюз

**Относится к:** ТЗ MSP 1.1 §9–§13, §18–§19, §22, §29–§30, §49, §53, §63
**Проверяется тестами:** `tests/gateway/test_open_relay.py`, `test_protocol.py`, `test_smoke.py`

> **MSP 1.1 IS NOT APPROVED FOR PRODUCTION MX CUTOVER.** Описан путь на тестовом домене.

---

## 1. Входящее письмо

```text
отправитель (Интернет) ─► :25 публичный слушатель ─► проверки ─► очередь ─► Exchange
                                                          │
                                                          └──► копия в журнал (для анализа)
```

Проверки публичного слушателя выполняются по порядку; первое сработавшее решает:

| Этап | Что проверяется | Ответ при отказе |
|---|---|---|
| `RCPT TO` | не включён ли режим слива (Postfix откладывает клиентские ограничения до `RCPT`) | `450 4.3.2` (временный) |
| соединение | лимиты на клиента: не более 20 одновременных, не более 60 новых в минуту | `421` |
| `HELO` | обязателен | `503` |
| `MAIL FROM` | пустой отправитель допустим (так приходят уведомления о недоставке) | — |
| `RCPT TO` | домен — один из принимаемых доменов организации | `554 5.7.1 Relay access denied` |
| `RCPT TO` | справочник получателей не безнадёжно устарел | `451 4.3.0` (временный) |
| `RCPT TO` | получатель или его псевдоним есть в справочнике | `550 5.1.1` |
| `DATA` | одиночный перевод строки (`bare LF`) | отказ и разрыв сессии |
| `DATA` | размер не больше 50 МиБ (настраивается), заголовки не больше 100 КиБ | `552` |
| конец данных | число переходов (`Received`) не больше 20 | `554 5.4.6` |

Получатель, не прошедший проверку, отвергается **на этапе `RCPT`, до приёма письма**. Письмо для
несуществующего адреса не попадает в очередь, и шлюзу не приходится потом возвращать его отправителю
(иначе по подделанным адресам отправителей шлюз рассылал бы чужим людям уведомления — «обратное
рассеяние», backscatter).

После ответа `250` письмо лежит в устойчивой очереди Postfix; всё, что происходит дальше, может его
задержать, но не потерять ([GATEWAY_QUEUE.md](GATEWAY_QUEUE.md)).

## 2. Исходящее письмо

```text
Exchange ─► :2525 внутренний слушатель ─► проверки ─► очередь ─► приёмник / вышестоящий сервер
```

* Принимается только с **доверенных подсетей** (`internal.trusted_networks`); остальные получают отказ ещё
  при соединении.
* **STARTTLS обязателен** (`smtpd_tls_security_level = encrypt`): незашифрованная сессия между Exchange и
  шлюзом — это переписка организации в открытом виде внутри сети.
* Письмо на **собственный** домен с этого порта по умолчанию отвергается (`REJECT_LOOP`): единственная
  ситуация, в которой Exchange отдаёт шлюзу письмо для нашего же домена, — неверная маршрутизация, и
  возврат такого письма замкнул бы петлю.
* Куда уходит исходящая почта, определяет `outbound.mode`: `DISABLED` (по умолчанию), `SINK` (тестовый
  приёмник), `UPSTREAM` (вышестоящий сервер), `INTERNET` (прямая доставка; требует явного подтверждения
  `internet_delivery_acknowledged`). В MSP 1.1 боевая доставка в Интернет выключена, приёмка идёт на
  приёмник или управляемый вышестоящий сервер.

## 3. Маршрутизация к Exchange

Каждому принимаемому домену назначен **маршрут** — упорядоченный список целей:

```text
corp.example  ─►  msp-r-exchange: [exchange-1]:25, запасной [exchange-2]:25
```

Первая цель — основная; остальные Postfix использует **как запасные MX-серверы**: следующая цель пробуется при
**любом временном отказе** предыдущей — и когда соединение не удалось, и когда сервер ответил `4xx`
(в том числе после `DATA`). Постоянный отказ (`5xx`) на следующую цель **не передаётся**: письмо
возвращается отправителю.

Практическое следствие: цели маршрута должны быть **равноценны** (пул серверов Exchange с теми же
ящиками). Письмо, временно отвергнутое одним сервером, получит другой. Если нужен именно «основной с
резервом, который включается только при полной недоступности», это отдельная схема (внешний
балансировщик), и в MSP 1.1 она не реализована.

Проверка TLS к Exchange строгая, если маршруту задана политика `VERIFY`: сертификат проверяется по
цепочке и по имени. Сертификат, который не прошёл проверку, — это **отложенная** почта, а не доставка по
открытому каналу ([GATEWAY_TLS.md](GATEWAY_TLS.md)).

## 4. Определение направления

Направление письма определяет **слушатель, принявший его**, а не домен отправителя и не заголовки:

| Принято на | Направление | Копия в журнал |
|---|---|---|
| публичный `:25` | `INBOUND` | адресат `journal-in@journal.msp.invalid` |
| внутренний `:2525` | `OUTBOUND` | адресат `journal-out@journal.msp.invalid` |

Заголовки пишет отправитель, поэтому «письмо от нашего домена» не означает «исходящее»: поддельное письмо
с нашим адресом отправителя, пришедшее из Интернета, остаётся входящим.

---

## 5. Защита от петель

* Предел числа пересылок (`hopcount_limit`, по умолчанию 20) считается по заголовкам `Received`, которые
  добавляет сам Postfix. Письмо, превысившее предел, отвергается — проверено письмом с 40 заголовками.
* Письмо Exchange на наш домен через внутренний порт отвергается (`REJECT_LOOP`).
* Копия для анализа адресована несуществующему домену `journal.msp.invalid`, который не может выйти за
  пределы узла.

---

## 6. Что на пути письма отсутствует

Нет оценки содержимого, спам-фильтра, антивируса, обращения к панели и к базе. Единственное, что делает
шлюз с содержимым, — **записывает копию** в локальный журнал. Если панель, база, Redis или анализ недоступны,
почта идёт как шла.
