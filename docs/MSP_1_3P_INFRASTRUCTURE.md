# MSP 1.3P — инфраструктура пилота

**Относится к:** ТЗ MSP 1.3P §7–§9, §23

> Цифры ниже — **начальный лабораторный профиль для десятков почтовых пользователей**, а не подтверждённая производительность.
> Окончательные ресурсы определяются после измерения реального среднего и максимального объёма писем, вложений, срока хранения и
> задержек. Повторяемая нагрузка на целевой Linux-инфраструктуре — условие `linux_load_profile` и сейчас `NOT_TESTED`.

## Роли и ресурсы (начальная оценка)

| Роль | vCPU | RAM | Диск | Примечание |
|---|---:|---:|---:|---|
| Ядро MSP: API, БД, Redis, воркер, консоль | 4–8 | 16–32 ГБ | 150–250 ГБ SSD | отдельный том для БД и хранилища объектов |
| Узел шлюза A | 2–4 | 8 ГБ | 80–150 ГБ SSD | своя постоянная очередь Postfix, свой адрес |
| Узел шлюза B | 2–4 | 8 ГБ | 80–150 ГБ SSD | **независимая** очередь и том; общей очереди нет |
| Воркер анализа вложений | 2–4 | 4–8 ГБ | 40–80 ГБ SSD | без сети, лимиты CPU/RAM/времени |
| Мониторинг и резервные копии | по среде | по среде | по retention | не на том же единственном диске |

Для P2 активные узлы шлюза не нужны: поток идёт по журналу. Для P4 нужны два независимых узла; само наличие двух узлов HA не доказывает —
нужны проверенные сценарии отказа (`two_node_failover`). Объём диска считают по фактическим P50/P95 размерам, выбросам, времени
накопления очереди при отказе Exchange и срокам хранения исходных писем, журнала и карантина.

## Сетевые потоки

Заполняется таблица `источник → получатель → протокол/порт → назначение → TLS → владелец`. Базовые потоки:

| Поток | Условие |
|---|---|
| Журнальный ящик / сборщик → вход MSP | закрытый внутренний адрес; приём журнального отчёта — `POST /api/v1/pilot/intake/journal` (сессия, право `pilot:manage`) |
| Ядро MSP → EWS/IMAP (чтение) | только согласованные ящики; чтение без `\Seen` до надёжной записи |
| Узлы A/B → Receive Connector Exchange | SMTP с проверкой сертификата; коннектор ограничен адресами узлов |
| Управляющая сеть → консоль/API | HTTPS через VPN/бастион |
| Узлы → политика и метрики | токены **своих** областей |
| Rspamd, Redis, БД | только частные сети служб; публичного контроллера нет |
| Анализ вложений | без внешней сети |
| Публичный SMTP/25 | только на согласованном пилотном адресе (P4) |

Запрещено: `0.0.0.0/0` в списке доверенной пересылки, открытый ретранслятор, публичный контроллер Rspamd, прямой доступ к БД/Redis.

## Учётные записи и секреты

Минимум: чтение Exchange на пилотные ящики; отдельный журнальный ящик; чтение AD (при необходимости); оператор, аналитик, Security Admin
MSP; пять токенов компонентов (`MSP_GATEWAY_AGENT_TOKEN`, `MSP_RECIPIENT_SYNC_TOKEN`, `MSP_SHADOW_COLLECTOR_TOKEN`,
`MSP_ENFORCEMENT_POLICY_TOKEN`, `MSP_METRICS_TOKEN`).

Перед P4 обязательно:

```text
MSP_GATEWAY_SHARED_TOKEN_ALLOWED=false
```

Платформа сама проверяет это условие (`shared_token_disabled` в гейте P4). Тестовые и стандартные пароли, самоподписанный TLS вне
изолированного стенда — убрать.

### Ключ карантина

Потеря ключа делает хранимые письма нечитаемыми. До реальных карантинных писем:

1. Создать резервную копию в изолированном хранилище (escrow), записать идентификатор и владельца ключа в реестр.
2. Проверить копию: `python scripts/quarantine_key_check.py --backup-file <файл копии>`; при наличии объекта —
   `--blob <объект из хранилища> --item-id <id письма> --sha256 <контрольная сумма>`. Скрипт расшифровывает пробу и (по желанию)
   настоящий объект копией, **не печатает ключ** и возвращает 0 только при исходе `OK`.
3. Приложить отчёт к подтверждению `quarantine_key_restore` (`POST /api/v1/pilot/attestations/quarantine_key_restore`).

Без проверенного восстановления вход в P4 закрыт.

### Подпись политики

Подпись политики **симметрична** (общий ключ у панели и узла): компрометация узла позволяет подделать политику для самого узла.
Для P4 нужно либо внедрить асимметричную подпись, либо записать компенсирующие меры и принять риск только для строго изолированного
пилотного домена (`policy_signing_risk_accept`). Для глобального принуждения такое исключение неприемлемо.

## Что проверяет платформа сама

| Условие | Где |
|---|---|
| Общий токен выключен | гейт P4: `shared_token_disabled` |
| Ключ карантина задан (≥ 32 символов) | гейт P4: `quarantine_key_configured` |
| Не менее двух боевых узлов сообщают состояние за 10 минут, политика совпадает | гейт P4: `two_nodes_in_sync` |
| Контроль не заблокирован открытым пробелом | гейт P4 и `GET /api/v1/pilot/readiness` |
| Ни один контроль не действует на почту до решения по P4 | гейты P1–P3 и итог |

Остальное (независимость очередей, отказ узла, TTL политики на узле, выключатель, обход, откат, Receive Connector, открытый
ретранслятор, нагрузка) проверяется в среде организации и записывается подтверждением с ссылкой на документ. Это
`BLOCKED_EXTERNAL`, пока нет самой среды.

## Нагрузочный профиль (цель)

Целевой профиль для безопасного стенда: 50 параллельных SMTP-сессий и 1000 писем в час, средние и крупные вложения, без заявлений о
пропускной способности боевой установки по лабораторным цифрам. Лабораторная проверка 1.3 (60 писем, 18 сессий с каждого из двух
адресов) этот профиль **не заменяет**.
