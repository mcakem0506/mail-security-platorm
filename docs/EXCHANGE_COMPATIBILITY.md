# Совместимость с Exchange и Outlook

Документ фиксирует, что известно о целевой среде, что проверено, и что остаётся блокером.
Соответствует §6.5, §7, §44, §51 ТЗ.

> **Продукт универсальный.** Заказчик не привязан к одной конфигурации: платформа должна
> работать в Exchange 2016 и 2019, с любым Outlook начиная с 2016, в произвольной топологии AD
> и при наличии существующего шлюза. Поэтому нигде не зашиты версии, DN каталога и адреса —
> всё определяется в runtime либо настраивается.

## 2. Что следует из полученных ответов

### Exchange 2016 и 2019 одновременно

Обе версии поддерживают EWS и централизованное развёртывание надстроек. Различия существенны
только в наборах Office.js requirement set, доступных через них, поэтому платформа **не
определяет версию Exchange** и не ветвится по ней: надстройка спрашивает клиента, что он умеет,
и подстраивается.

### Outlook 2016 и новее

| Клиент | Requirement set | Режим надстройки |
|---|---|---|
| Outlook 2016 (MSI, ранние сборки) | Mailbox 1.4–1.5 | `fallback`: передача письма через security mailbox |
| Outlook 2016 (Click-to-Run, обновлённый) | Mailbox 1.5–1.6 | `fallback` |
| Outlook 2019 | Mailbox 1.6–1.8 | `full` при 1.8 |
| Outlook 2021 / Microsoft 365 Apps | Mailbox 1.8+ | `full` |
| **OWA (доступен)** | Mailbox 1.8+ | `full` |

Минимальная планка манифеста — Mailbox 1.5. Это покрывает весь парк начиная с Outlook 2016,
а конкретные возможности проверяются вызовом `isSetSupported` (см. `compatibility.js`).
Пользователь всегда видит список ограничений своего клиента.

**Практическое следствие:** часть парка на Outlook 2016 будет работать в режиме fallback.
Это не ухудшает защиту — письмо всё равно проходит полный серверный анализ, просто путь передачи
другой. Через OWA тот же сотрудник получит полный режим.

### KSMG уже установлен

Платформа **не заменяет KSMG и не конкурирует с ним**. KSMG стоит в потоке доставки и имеет
полноценный антивирусный движок, которого у платформы намеренно нет. Разделение такое:

| Задача | KSMG | Платформа |
|---|:--:|:--:|
| Антивирусная проверка вложений | ● основной | вспомогательный сигнал |
| Антиспам | ● основной | — |
| Блокировка до доставки | ● | нет (не inline) |
| Подмена отправителя и идентичности | частично | ● основной |
| Lookalike-домены и омоглифы | частично | ● основной |
| BEC без вложений и ссылок | проходит насквозь | ● основной |
| Объяснение вердикта сотруднику | нет | ● |
| Расследования, кампании, инциденты | нет | ● |
| Кнопка «Сообщить о фишинге» | нет | ● |

Реализовано чтение вердиктов KSMG из заголовков `X-KSMG-*` (`msp_detection/gateway.py`):

- **обнаружение KSMG** → hard-signal, класс риска поднимается напрямую;
- **«чисто» от KSMG** → фиксируется для аналитика, но **никогда не снижает риск**. Именно
  BEC и подмена личности проходят шлюз штатно — если бы «чисто» снижало оценку, платформа
  теряла бы смысл;
- заголовки учитываются, только если шлюз указан в `MSP_TRUSTED_GATEWAYS`. Заголовок от чужого
  шлюза сам становится признаком: отправитель мог добавить его, чтобы письмо выглядело проверенным.

Настройка: `MSP_TRUSTED_GATEWAYS=ksmg`.

Поддерживаются также Exchange Online Protection (SCL/BCL), SpamAssassin и generic
`X-Virus-Status` — для универсальности продукта.

### Аутентификация через AD без MFA

Реализован backend `MSP_AUTH_BACKEND=ldap`:

- аутентификация — **bind от имени пользователя**: пароль проверяет контроллер домена, платформа
  его не хранит и не пересылает;
- **локальный хеш пароля для AD-учётных записей не создаётся** никогда, даже при rehash;
- роль назначается по членству в группах AD (`MSP_AD_GROUP_ROLE_MAP`), управление доступом
  остаётся там, где организация им уже управляет;
- база поиска определяется из RootDSE, если не задана — топология AD не зашивается;
- значения логина экранируются перед подстановкой в LDAP-фильтр (защита от filter injection);
- LDAP без TLS отклоняется конфигурацией: пароль не может уйти в открытом виде;
- недоступность каталога — **отказ во входе (503)**, а не разрешение;
- отключённая, заблокированная или с истёкшим паролем учётная запись распознаётся и до bind,
  и по коду ошибки AD (`data 533`, `775`, `532`);
- локальная учётная запись (bootstrap, аварийная) продолжает работать при недоступности AD.

Пример:

```text
MSP_AUTH_BACKEND=ldap
MSP_AD_SERVER=dc01.corp.example
MSP_AD_BIND_DN=CN=svc-msp,OU=Service,DC=corp,DC=example
MSP_AD_BIND_PASSWORD_FILE=/run/secrets/ad_bind_password
MSP_AD_GROUP_ROLE_MAP=SOC Admins=security_admin;SOC Analysts=security_analyst;IT Support=security_viewer
MSP_AD_DEFAULT_ROLE=employee
```

**Отсутствие MFA — принятый риск, а не пробел.** Компенсации: короткие сессии для привилегированных
ролей (30 мин), простой 20 мин, блокировка при переборе, немедленный отзыв всех сессий, аудит
каждого действия. Зафиксировано в `SECURITY_MODEL.md`. При появлении IdP включается
`MSP_REQUIRE_MFA_FOR_PRIVILEGED=true`.

### Универсальность вместо тестовой зоны

Поскольку AD-топология заказчика — тестовая, а продукт нужен универсальный, нигде не зашиты:
базовый DN (определяется из RootDSE), фильтр поиска пользователя (настраивается), имена групп
(настраиваются), домены организации (настраиваются), почтовый шлюз (настраивается), версия
Exchange (не используется), возможности Outlook (определяются в runtime).

## 3. Что нужно предоставить для EWS

EWS нужен только для двух возможностей: **поиск связанных писем по всем ящикам** и **выполнение
действий реагирования**. Всё остальное работает без него.

| Требуется | Пример | Как узнать |
|---|---|---|
| URL EWS | `https://mail.corp.example/EWS/Exchange.asmx` | в EMS: `Get-WebServicesVirtualDirectory \| fl InternalUrl,ExternalUrl` |
| Метод аутентификации | NTLM (обычно), Kerberos или Basic поверх TLS | `Get-WebServicesVirtualDirectory \| fl *Authentication*` |
| Учётная запись | логин и пароль выделенного служебного аккаунта | создаётся администратором |
| Способ доступа к чужим ящикам | роль `ApplicationImpersonation` **либо** делегирование на конкретные ящики | решение администратора |
| Область действия | список ящиков или OU, к которым разрешён доступ | решение ИБ |

**Рекомендация:** на первом этапе дать учётной записи доступ **только к ящикам пилотной группы**
через management scope, а не `ApplicationImpersonation` на всю организацию. Расширение — после
приёмки.

Отдельная учётная запись для реагирования создаётся позже и отдельно (§7.1 ТЗ): аккаунт чтения
не должен уметь удалять письма.

Если EWS не предоставляется — платформа работает полностью, кроме сквозного поиска и выполнения
реагирования. Согласованные действия в этом случае передаются администратору Exchange для
выполнения вручную, а запись в платформе остаётся как основание.

## 4. Что такое mail flow topology и Edge Transport

### Mail flow topology

Это маршрут письма от интернета до ящика. Нужно, чтобы понять, **где стоит KSMG** и **куда можно
подключить копию потока** для shadow-режима.

Типичные варианты:

```text
A)  Интернет → KSMG → Exchange Mailbox → ящик
B)  Интернет → Edge Transport → KSMG → Exchange Mailbox → ящик
C)  Интернет → MX-релей провайдера → KSMG → Exchange → ящик
```

Что ответить: перечислить узлы по порядку, включая KSMG и любые релеи, и указать, какой узел
первым принимает почту из интернета.

Почему важно: если KSMG стоит **до** Exchange, его заголовки уже есть в письме к моменту анализа —
это реализовано. Если **после** или параллельно, поведение другое.

### Edge Transport

Отдельная роль Exchange, которая ставится в DMZ и принимает почту из интернета до попадания во
внутреннюю сеть. Вопрос сводится к: **есть ли в организации сервер Exchange с ролью Edge
Transport, или эту задачу выполняет KSMG?**

Проверить: `Get-ExchangeServer | fl Name,ServerRole` — роль будет указана как `Edge`.

В большинстве случаев при наличии KSMG Edge Transport не используется. Для v1 ответ ни на что
не влияет — он нужен только при переходе к inline-режиму (MSP 1.1+).

## 5. Что такое outbound proxy

Может ли сервер платформы обращаться в интернет напрямую, или исходящие соединения идут через
прокси-сервер.

Нужно, чтобы решить, как обращаться к Threat Intelligence (VirusTotal и другим). Наружу идут
только воркеры `worker-ti` и `worker-maintenance`.

Что ответить:

| Вариант | Что указать |
|---|---|
| Прямой доступ | «прямой», и открыть исходящий 443 к провайдерам |
| Через прокси | адрес и порт, нужна ли аутентификация, есть ли allowlist доменов |
| Интернета нет | так и указать |

Если интернета нет — платформа работает полностью на локальных проверках. Внешние источники
просто отключаются (`MSP_VT_MODE=disabled`), а неполнота обогащения отражается в вердикте как
`missing_evidence`. Это штатный режим, а не деградация.

## 6. Отсутствие внутреннего CA

TLS-сертификат нужен в трёх местах:

| Соединение | Без внутреннего CA |
|---|---|
| Пользователи → платформа (HTTPS) | самоподписанный сертификат вызовет предупреждение в браузере у всех. **Рекомендация:** выпустить сертификат хотя бы для одного имени, либо развернуть минимальный CA |
| Платформа → Exchange (IMAPS/EWS) | сертификат Exchange, вероятно, самоподписанный. Экспортировать его и указать в `MSP_SECURITY_MAILBOX_CA_FILE` — так проверка остаётся включённой |
| Платформа → AD (LDAPS) | аналогично, `MSP_AD_CA_FILE` |

Отключение проверки TLS (`verify_tls=false`) поддерживается **только для стенда** и отклоняется
конфигурацией в production: соединение с отключённой проверкой уязвимо к перехвату, а по нему
передаётся пароль пользователя.

Практический путь без развёртывания CA: экспортировать самоподписанные сертификаты Exchange и
контроллера домена в PEM и передать их платформе как доверенные. Проверка при этом работает.

## 7. Требования к security mailbox (§7.2)

Единственная интеграция с почтой, необходимая для полноценной работы Mode A/B.

| Параметр | Требование |
|---|---|
| Адрес | `security-phishing@<corporate-domain>` или согласованный аналог |
| Протокол | IMAP over TLS (993) либо STARTTLS |
| Права | чтение и установка флага `\Seen` **в своём ящике**; больше ничего |
| Impersonation | **не требуется** |
| Сертификат | путь к CA в `MSP_SECURITY_MAILBOX_CA_FILE` |
| Пароль | только через файл секрета |

Платформа никогда не отправляет письма из этого ящика и не удаляет из него сообщения.

**Для пользователей:** письмо пересылается **как вложение** (Главная → Дополнительно → Переслать
как вложение). При обычной пересылке теряются заголовки. Надстройка показывает это в инструкции,
а платформа помечает такие сообщения предупреждением.

## 8. Сервисные аккаунты (§7.1)

| Аккаунт | Права | Обязателен |
|---|---|:--:|
| Mailbox intake | чтение своего ящика по IMAP | да |
| AD read/auth | чтение атрибутов §10 и поиск пользователя (LDAP, только чтение) | да, при AD-аутентификации |
| EWS read | чтение писем в согласованной области | нет |
| Remediation | операции над письмами | нет, **по умолчанию отключён** |

Запрещено использовать `Organization Management`, `Domain Admins` или эквивалент (§49.7).

## 10. Оставшиеся блокеры

1. **EWS** — параметры из раздела 3. Следствие: нет сквозного поиска и выполнения реагирования.
2. **Топология mail flow и Edge Transport** — раздел 4. Следствие: нельзя подключить shadow-режим.
3. **Outbound proxy** — раздел 5. Следствие: неизвестно, будет ли доступен Threat Intelligence.
4. **TLS-сертификаты** — раздел 6. Следствие: для пилота нужен хотя бы экспорт самоподписанных
   сертификатов Exchange и контроллера домена.
5. **Служебные учётные записи** — раздел 8.

Ни один из них не мешает запустить платформу и начать пилот через security mailbox.
