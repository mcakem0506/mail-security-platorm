# ADR: изолированный разбор вложений

**Статус:** принято к проработке, не реализовано в MSP 1.0.4
**Контекст этапа:** MSP 1.0.4 §15
**Затрагивает:** GAP-003 (архивы 7z и RAR), GAP-004 (QR-коды внутри PDF)

## Решение в одном предложении

Любой разбор, требующий чужого кода над содержимым недоверенного письма, выполняется в
отдельном процессе с собственными лимитами, без сети и без права писать куда-либо, кроме своего
временного каталога, — либо не выполняется вовсе.

## Зачем это записано сейчас, когда не реализовано

Потому что два пробела в реестре — GAP-003 и GAP-004 — закрываются одним и тем же способом, и
без общего решения каждый из них закрывался бы своим. Первый, кто возьмётся за архивы, добавил
бы распаковщик в основной worker, потому что так быстрее; второй, кто возьмётся за PDF, добавил
бы туда же разбор PDF. После этого «изоляция» стала бы невозможной задним числом: её нельзя
добавить к коду, который уже исполняется в том же процессе, что и всё остальное.

Решение записано до работы ровно для того, чтобы работа началась с правильного места.

## Что уже сделано правильно и служит образцом

Декодер QR в MSP 1.0.4 §6-§7 построен именно так, и его устройство — не эксперимент, а готовый
образец:

| Свойство | Как сделано |
|---|---|
| Отдельный процесс | `msp_mail_parser.qr_worker`, запускается на одно изображение |
| Лимит процессорного времени | `RLIMIT_CPU`, 15 секунд |
| Лимит памяти | `RLIMIT_AS`, 1 ГиБ |
| Запрет записи | `RLIMIT_FSIZE = 0` — процесс физически не может создать файл |
| Нет сети | проверяется тестом по AST: модуль не импортирует ничего сетевого |
| Нет чтения файлов | тот же тест: ни `open`, ни `imread`, ни `VideoCapture` |
| Данные через stdin/stdout | байты изображения приходят на вход, результат уходит на выход |
| Лимиты ставит сам процесс | не `preexec_fn` родителя, а первое, что делает ребёнок |

Последняя строка важнее, чем кажется. Лимиты, выставленные родителем через `preexec_fn`,
выставляются между `fork` и `exec` — в состоянии, где сбой трудно заметить и нечем сообщить.
Процесс, который ставит лимиты себе сам и только потом берётся за данные, либо ограничен, либо
не начал работу.

## Что остаётся сделать для GAP-003 и GAP-004

### Архивы 7z и RAR

Безопасной внутрипроцессной библиотеки для этих форматов в составе v1 нет. Варианты, в порядке
убывания предпочтительности:

1. **Разбор в изолированном процессе по образцу QR.** Распаковщик всё равно остаётся чужим
   кодом над недоверенными данными, но его отказ не уносит с собой worker, а его аппетиты
   ограничены. Добавляется лимит на суммарный объём распакованного и на число элементов — без
   него архив на три килобайта разворачивается в терабайт.
2. **Разбор без распаковки.** Прочитать только оглавление: имена, размеры, признак пароля.
   Этого достаточно для значительной части решений — опасное расширение внутри архива видно по
   имени, — и не требует исполнять код над содержимым.
3. **Не разбирать.** Текущее состояние: вложение помечается непроверенным, вердикт не
   опускается до `LOW_RISK`, факт попадает в `missing_evidence`.

Третий вариант — не отсутствие решения, а решение. Отказ от разбора, названный вслух и видимый в
вердикте, честнее разбора, которому нельзя доверять.

### QR-коды внутри PDF

PDF — формат с собственной историей уязвимостей разбора, и извлечение изображений из него
требует именно разбора PDF. Конвейер: тот же отдельный процесс, те же лимиты, на вход байты
PDF, на выход — только изображения, без текста, без ссылок, без вложенных объектов. Изображения
затем идут в уже существующий декодер QR, то есть во **второй** изолированный процесс, а не в
тот же: процесс, разбирающий PDF, не должен ещё и декодировать.

## Чего это решение не разрешает

* **Исполнять вложения.** Ни в основном worker, ни в изолированном процессе. Изоляция — про
  разбор, не про запуск: запуск вложения требует другой защиты и другого обоснования, и в v1
  его нет.
* **Обращаться в сеть из разбора.** Ни за обновлениями формата, ни за словарями, ни за
  чем-либо ещё. Процесс, который может выйти в сеть, может и вынести содержимое письма.
* **Считать отсутствие находки безопасностью.** Изолированный разбор, который ничего не нашёл,
  даёт ровно то же, что и неизолированный: отсутствие находки. Вердикт от этого не улучшается.
* **Снижать `scan_completeness` молча.** Если разбор не состоялся — по таймауту, по лимиту, по
  отказу — это отражается в вердикте, а не теряется.

## Как будет видно, что решение соблюдается

Теми же средствами, которыми это проверяется для QR сейчас:

* тест по AST, что модуль разбора не импортирует сетевое и файловое;
* тест, что лимиты выставлены до чтения данных;
* тест на враждебном входе: обрезанный файл, файл-бомба, файл не того формата;
* тест, что отказ разбора изолирован — остальное письмо анализируется, а не теряется целиком;
* тест, что неполный разбор виден в `scan_completeness` и в `missing_evidence`.

Перечень не новый: это то, что уже написано в `tests/security/test_qr_isolation.py`. Для архивов
и PDF он повторяется, а не изобретается.

## Последствия

**Хорошие.** Два пробела закрываются одним механизмом. Цена отказа любого разборщика ограничена
заранее. Появление третьего такого формата не требует нового решения.

**Плохие.** Процесс на каждое вложение дороже вызова функции: запуск, передача данных, ожидание.
Для писем с десятками вложений это заметно, и потребуется ограничение на число разборов на
письмо — то есть ещё одно место, где анализ может оказаться неполным, и ещё одна причина, по
которой это должно быть видно в вердикте.

**Отложенные.** Пока решение не реализовано, GAP-003 и GAP-004 остаются в реестре со статусом
«принят». Это не формальность: принятый пробел — известное ограничение с компенсирующей мерой, и
организация, читающая реестр, знает, чего платформа не делает.
