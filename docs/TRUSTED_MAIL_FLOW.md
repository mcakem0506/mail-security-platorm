# Описание доверенного почтового потока

**Относится к:** ТЗ 1.0.1 §4.3, §4.4; ТЗ 1.0.2 §22, §32
**Реализация:** таблицы `trusted_mail_hops`, `mail_gateways`, `mail_gateway_nodes`, `mail_routes`

---

## 1. Что нужно описать и зачем

Платформа должна уметь ответить на вопрос: **прошло ли это письмо через инфраструктуру
организации, и через какую именно?** Без ответа заголовки, которые оставляет шлюз, и результаты
проверки подлинности отправителя остаются ничем не подтверждёнными заявлениями.

Описание топологии — это не документация, а конфигурация: она непосредственно меняет, каким
заголовкам платформа верит.

---

## 2. Три типовые схемы

### Mode A — Exchange без стороннего шлюза

```text
Internet
   ↓
EXCH-EDGE-01  (если развёрнут Edge Transport)
   ↓
MX-01 / EXCH-MBX-01
   ↓
ящик пользователя → MSP
```

Описываются почтовые серверы Exchange. Шлюзов нет — это нормальное состояние,
`gateway_state=NOT_PRESENT`. Доверенные узлы всё равно нужны: `Authentication-Results` пишет
Exchange, и без объявленного узла их источник не подтверждается.

### Mode B — Exchange за шлюзом

```text
Internet
   ↓
KSMG-01 / KSMG-02      ← шлюз, пишет X-KSMG-*
   ↓
EXCH-EDGE-01           ← если есть
   ↓
MX-01                  ← пишет Authentication-Results
   ↓
ящик → MSP
```

Описываются и шлюз, и серверы Exchange. **Описать только шлюз — самая частая ошибка**: тогда
заголовки от почтового сервера окажутся от объявленного, но не подтверждённого источника.

### Несколько шлюзов и направлений

Поддерживается произвольное число шлюзов, каждый со своим направлением:

| `direction` | Смысл |
|---|---|
| `inbound` | входящая почта |
| `outbound` | исходящая |
| `both` | оба |

## 3. Модель

```text
MailGateway            интеграция со шлюзом (provider_id, provider_type, direction)
  └─ MailGatewayNode   физический узел кластера (hostname, ip_networks)
  └─ TrustedHop        правило доверия: что подтверждает прохождение

TrustedHop             может существовать и без шлюза — серверы Exchange
MailRoute              ожидаемая последовательность узлов
GatewayCredential      ссылка на секрет API, никогда само значение
GatewayCapabilityState что узел, по результатам проверки, действительно умеет
```

`MailGatewayNode` и `TrustedHop` различаются намеренно: первый описывает **машину**, второй —
**правило доверия**. Почтовый сервер Exchange — доверенный узел, не являющийся частью шлюза.

---

## 4. Поля доверенного узла

| Поле | Назначение | Замечание |
|---|---|---|
| `hop_type` | `gateway`, `exchange_edge`, `exchange_mailbox`, `relay` | влияет только на отображение |
| `hostname` | имя узла | совпадение по границе метки; поддомен подходит |
| `ip_networks[]` | адреса и сети | надёжнее имени: не зависит от DNS |
| `expected_headers[]` | какие заголовки пишет узел | справочно, для консоли |
| `authserv_ids[]` | чьи `Authentication-Results` разрешено читать | **ключевое поле** |
| `position_in_chain` | место в цепочке от конца доставки, либо `null` | задавайте только при стабильной маршрутизации |
| `direction` | направление | |
| `enabled` | | |

Указать нужно **хотя бы одно** из `hostname` и `ip_networks`: узел без того и другого не с чем
сопоставить, и API такую запись отклоняет.

### О позиции

Позиция считается от конца доставки: hop 0 — верхний заголовок `Received`. Узел присутствует в
цепочке дважды — в заголовке, который написал сам (`by`), и в заголовке следующей машины
(`from`); позицией считается первая.

Задавать `position_in_chain` стоит только там, где маршрутизация стабильна. Иначе легитимное
изменение маршрута начнёт помечаться как несоответствие. Значение `null` (по умолчанию) означает
«в любом месте цепочки» и остаётся полностью безопасным: подтверждение соседом требуется в любом
случае.

## 5. Пример настройки

Топология:

```text
Internet → ksmg-01.corp.example (10.20.0.11) → mx.corp.example → ящик
```

```bash
# 1. Шлюз
GATEWAY=$(curl -s -X POST .../api/v1/gateways \
  -d '{"provider_id":"ksmg","provider_type":"ksmg","display_name":"KSMG"}' | jq -r .gateway_id)

# 2. Узел шлюза
curl -X POST .../api/v1/gateways/$GATEWAY/hops -d '{
  "hop_type": "gateway",
  "hostname": "ksmg-01.corp.example",
  "ip_networks": ["10.20.0.0/24"],
  "authserv_ids": ["ksmg-01.corp.example"],
  "expected_headers": ["X-KSMG-Antivirus-Status", "X-KSMG-AntiSpam-Status"]
}'

# 3. Почтовый сервер — не забыть
curl -X POST .../api/v1/gateways/hops -d '{
  "hop_type": "exchange_mailbox",
  "hostname": "mx.corp.example",
  "authserv_ids": ["mx.corp.example"]
}'
```

Внутренние сети задаются отдельно — они нужны, чтобы определить, где письмо вошло в организацию:

```text
MSP_INTERNAL_MAIL_NETWORKS=10.20.0.0/16,192.168.10.0/24
```

## 6. Как определить фактическую топологию

Если схема неизвестна, её видно из самих писем.

```bash
# Цепочка Received настоящего письма
curl .../api/v1/investigations/messages/$MESSAGE_ID | jq -r '.headers[] | select(.name=="Received") | .value'
```

Читать сверху вниз: верхний заголовок написан последней машиной. Имена и адреса в `by` — это
узлы организации, и именно их нужно описать.

Второй источник — `Authentication-Results`: имя перед первой `;` и есть `authserv-id`, который
надо внести в узел, который его пишет.

## 7. Проверка

```bash
docker compose exec api python scripts/probe_exchange.py --section mailflow
```

| Результат | Значение |
|---|---|
| `Внешний почтовый шлюз — не настроен` | Mode A, всё в порядке |
| `Доверенные узлы — N узлов` | топология описана |
| `ПРЕД: шлюз настроен, но ни один узел не описан` | заголовки шлюза учитываться не будут |
| `ПРЕД: доверенные authserv-id не заданы` | `Authentication-Results` читаются без проверки источника |

Затем на реальном письме:

```bash
curl .../api/v1/gateways/messages/$MESSAGE_ID | jq '.evidence[] | {provider_id, trusted, trust_reason}'
```

## 8. Что должна предоставить организация

Чтобы описать поток, нужны:

1. **имена и адреса шлюзов**, включая все ноды кластера;
2. **имена и адреса почтовых серверов**, участвующих в приёме извне;
3. **`authserv-id`** каждого сервера, который пишет `Authentication-Results` (виден в самих
   письмах);
4. **внутренние сети** почтового потока;
5. при наличии нескольких путей — их перечень, чтобы не задавать `position_in_chain` там, где
   маршрут непостоянен.

Ничего из этого не является секретом и всё это видно в заголовках собственных писем организации.

---

## 9. Влияние на детектирование

| Состояние | Последствие |
|---|---|
| топология описана полностью | заголовки шлюза учитываются; `Authentication-Results` читаются; подделка распознаётся |
| описан только шлюз | сигнал подделки на обычной почте — **ошибка настройки** |
| описаны только серверы Exchange | заголовки шлюза не учитываются; подлинность отправителя проверяется нормально |
| не описано ничего | заголовки шлюза не учитываются; `Authentication-Results` читаются без проверки (запасной режим); проверка готовности сообщает предупреждение |

Последняя строка — рабочее состояние на старте пилота. Оно хуже полного описания, но лучше
отказа читать результаты проверки подлинности вовсе.
