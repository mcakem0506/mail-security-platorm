# Совместимость с Exchange и Outlook

Документ фиксирует, что известно о целевой среде, что проверено, и что является **блокером**
до получения фактических данных. Соответствует §6.5, §7, §44, §51 ТЗ.

> **Главное правило:** §51 ТЗ прямо запрещает выдумывать конфигурацию. Пока фактические данные
> о среде не получены, Exchange и AD реализованы как adapter boundary с mock-провайдерами.
> Платформа при этом полностью работоспособна через security mailbox и Outlook Add-in.

## 2. Что работает без этих данных

| Возможность | Механизм | Требует Exchange API |
|---|---|:--:|
| Сообщение о фишинге сотрудником | Outlook Add-in → HTTPS → API | нет |
| Проверка письма сотрудником | Add-in читает заголовки и тело через Office.js | нет |
| Приём письма с сохранением заголовков | security mailbox по IMAP | нет |
| Полный серверный анализ | локальный пайплайн | нет |
| Threat Intelligence | отдельный egress | нет |
| Кампании, инциденты, аудит | внутренние | нет |
| Консоль безопасности | внутренняя | нет |
| Предложение и согласование реагирования | workflow с dry-run | нет |
| **Выполнение** реагирования в Exchange | EWS / PowerShell adapter | **да** |
| Поиск связанных писем по всем ящикам | EWS / eDiscovery | **да** |
| Shadow-копия всего потока почты | mail flow rule / transport | **да** |

Иначе говоря: **всё, кроме фактического изменения ящиков и сквозного поиска по ним, работает
уже сейчас.**

## 3. Требования к security mailbox (§7.2)

Единственная интеграция с почтой, необходимая для полноценной работы Mode A/B.

| Параметр | Требование |
|---|---|
| Адрес | `security-phishing@<corporate-domain>` или согласованный аналог |
| Протокол | IMAP over TLS (порт 993), либо STARTTLS |
| Права аккаунта | чтение и установка флага `\Seen` **в своём ящике**; больше ничего |
| Impersonation | **не требуется** |
| Сертификат | сертификат внутреннего PKI; путь к CA задаётся `MSP_SECURITY_MAILBOX_CA_FILE` |
| Пароль | только через файл секрета (`MSP_SECURITY_MAILBOX_PASSWORD_FILE`) |

Платформа никогда не отправляет письма из этого ящика и не удаляет из него сообщения.

**Важно для пользователей:** письмо нужно пересылать **как вложение** (Outlook: Главная →
Дополнительно → Переслать как вложение). При обычной пересылке оригинальные заголовки теряются,
и часть проверок становится невозможной. Add-in показывает это требование в инструкции fallback,
а платформа помечает такие сообщения предупреждением
`original message was not attached as message/rfc822`.

## 4. Матрица возможностей Outlook Add-in

Возможности определяются в runtime и не предполагаются (§6.5). Логика — в
`apps/outlook-addin/src/compatibility.js`.

| Requirement set | Что даёт | Что делает платформа |
|---|---|---|
| Mailbox 1.1–1.4 | базовое чтение темы, отправителя | режим `fallback`: только передача письма в ИБ |
| **Mailbox 1.5** | минимальный поддерживаемый набор | полный интерфейс панели, режим `fallback` для получения письма |
| Mailbox 1.8+ | `getAllInternetHeadersAsync` | режим `full`: заголовки и тело передаются на анализ напрямую |
| EWS callback token | доступ к полному MIME с вложениями | только после проверки среды (блокер 5) |

| Клиент | Ожидаемое поведение |
|---|---|
| Outlook for Windows (современные сборки) | полный режим при Mailbox 1.8+ |
| Outlook on the web | работает; набор возможностей может отличаться, о чём сообщается в панели |
| Outlook for Mac | работает в объёме поддерживаемого requirement set |
| Мобильный Outlook (iOS/Android) | только передача письма в ИБ; в панели явно указано, что полный анализ на устройстве не выполняется (§6.6) |

Панель **всегда** показывает сотруднику список фактических ограничений его клиента — платформа
не утверждает возможностей, которых у неё нет.

### Чего add-in не делает и не будет утверждать (§6.6)

- не перехватывает переходы по ссылкам;
- не работает в мобильном Outlook идентично настольному;
- не блокирует доставку письма;
- не изменяет содержимое ящика;
- не содержит ключей API и иных секретов.

## 5. Сервисные аккаунты (§7.1)

Принцип least privilege. Права **никогда** не объединяются в один аккаунт.

| Аккаунт | Права | Обязателен |
|---|---|:--:|
| Mailbox intake | чтение своего ящика `security-phishing@…` по IMAP | да |
| AD read | чтение атрибутов из §10 (LDAP, только чтение) | нет |
| Remediation | операции над письмами в согласованной области | нет, **по умолчанию отключён** |

Запрещено использовать для runtime-сервиса роли `Organization Management`, `Domain Admins` или
эквивалентные (§49.7). Remediation-аккаунт создаётся только на этапе MSP 0.9 и только после
отдельной приёмки.

## 6. Порядок ввода интеграции с Exchange

```text
Этап 1 (выполнено)   mock-провайдер: разработка и тестирование без Exchange
Этап 2               security mailbox: приём писем, сохранение заголовков
Этап 3               инвентаризация среды: пункты 1–13 раздела 1
Этап 4               EWS read-only на тестовом стенде: чтение письма, поиск
Этап 5               shadow-режим: копия потока писем без влияния на доставку
Этап 6               remediation в dry-run на тестовом стенде
Этап 7               remediation с выполнением, отдельная приёмка по §20 и §44
```

Переходить к этапу 4 без данных этапа 3 нельзя: код, написанный под предполагаемую конфигурацию,
выглядит готовым и отказывает в production.

## 7. Мнение о будущем inline-режиме (§21)

Transport Agent **не устанавливается** на production Exchange до отдельной приёмки по
безопасности и доступности (§49.12). Причина простая: агент в транспортном конвейере становится
точкой отказа доставки почты. До inline-режима требуется:

- минимум два узла шлюза;
- персистентные SMTP-очереди;
- backpressure и корректные SMTP-повторы;
- мониторинг, режим обслуживания и план обхода;
- проверенный откат;
- нагрузочное тестирование.

Это отдельная программа MSP 1.1+, которая не начинается до успешного завершения MSP 1.0.
