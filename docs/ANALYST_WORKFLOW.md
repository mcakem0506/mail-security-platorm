# Рабочий процесс аналитика

ТЗ 1.0.3 §15–§26, §30–§34. Что видит аналитик, в каком порядке и почему.

## Очередь

`GET /api/v1/investigations/queue` → страница «Очередь» в консоли.

Очередь отвечает на один вопрос: **что смотреть дальше**. Порядок задаётся приоритетом, затем
возрастом: среди равно срочного первым идёт то, что дольше ждёт, — это и не даёт ровному потоку
P2 заморозить старый P3.

### Приоритет — это не уровень риска

Главное свойство приоритизации (§18). Приоритет складывается из последствий и охвата, а не из
того, насколько письмо опасно само по себе:

| Ситуация | Вердикт | Приоритет |
|---|---|---|
| MALICIOUS одному адресату, письма уже удалены | MALICIOUS | **P3** |
| HIGH_RISK, кампания на 14 писем в финансовый отдел | HIGH_RISK | **P1** |
| SUSPICIOUS руководителю с признаками кражи учётных данных | SUSPICIOUS | **P2** |
| SUSPICIOUS обычному получателю | SUSPICIOUS | P4 |

Вредоносное письмо, которое уже никому не навредит, менее срочно, чем подозрительная рассылка,
способная навредить сейчас многим. Аналитик, не видящий причины порядка, переопределит его —
поэтому каждая строка очереди несёт факторы, из которых сложился балл:

```
P1  score=114  [verdict_high_risk:20, protected_recipient:12, finance_recipient:15,
                payment_fraud:20, multiple_recipients:10 (8), campaign_large:25 (14 писем),
                employee_report:12]
```

### SLA

Цель есть только у **принятия в работу** (§19):

| Приоритет | Срок принятия |
|---|---|
| P1 | 10 минут |
| P2 | 30 минут |
| P3 | 4 часа |
| P4 | 24 часа |

Значения по умолчанию (`DEFAULT_SLA` в `services/triage.py`) и переопределяются при
развёртывании: платформа универсальна, а дежурная смена у каждой организации своя.

Остальные этапы измеряются, но не ограничиваются. Сложное расследование, занявшее два дня, —
не нарушение; P1, на который два часа никто не посмотрел, — нарушение. Таймеры
(`time_to_ack`, `time_to_triage`, `time_to_remediate`, `time_to_close`) хранятся и показываются,
чтобы было видно, где именно уходит время.

### Назначение

Вручную (кнопка «Взять») или автоматически — наименее загруженному из переданного списка
(`auto_assign`). Выбор по загрузке, а не по кругу: строгая ротация отдаёт работу тому, кто уже
завален, пока коллега свободен.

## Карточка инцидента

| Блок | Что отвечает | ТЗ |
|---|---|---|
| Вердикт и причины | почему платформа так решила | §15 |
| Сигналы с условиями правил | что именно спросило правило и что оказалось верным | §15 |
| Граф доказательств | письмо → факты → правила → вердикт, плюс непроверенное | §16 |
| Хронология | что происходило, собрано из записей, а не из рассказа | §21 |
| Связанные письма | что ещё связано и чем именно | §30 |
| Кампания | масштаб, получатели, предложения объединения | §31, §32 |
| Классификация | решение аналитика | §22 |
| Формулировка для сотрудника | что ответить сообщившему | §34 |

Хронология собирается из фактических записей, а не из поля, которое надо не забыть заполнить:
хронология, которую пишут вручную, перестаёт писаться в первую же загруженную неделю.

## Классификация

`POST /api/v1/incidents/{id}/classification`

| Решение | Значение |
|---|---|
| `CONFIRMED_PHISHING` / `CONFIRMED_BEC` / `CONFIRMED_MALWARE` | подтверждённая угроза |
| `SPAM` | нежелательная почта, не атака |
| `LEGITIMATE` | письмо нормальное, платформа не ошиблась (например, предупреждение было уместным) |
| `FALSE_POSITIVE` | платформа ошиблась |
| `BENIGN_SIMULATION` | учебная рассылка |
| `UNKNOWN` | подтвердить или опровергнуть не удалось |

Правила обращения с классификацией:

1. **Из неё считаются все метрики качества.** Инцидент, закрытый без классификации, выпадает
   из статистики молча и портит её.
2. **Закрытие как безобидного требует комментария.** API отклоняет `LEGITIMATE`,
   `FALSE_POSITIVE` и `BENIGN_SIMULATION` без обоснования: это решение чаще других
   перечитывают после инцидента.
3. **История сохраняется.** Переклассификация создаёт новую запись с `previous_classification`;
   изменение мнения — это информация, а не ошибка, которую надо затереть.
4. **Указание виновных правил необязательно, но ценно.** Именно оно превращает «платформа
   ошиблась» в задачу владельцу правила. Без него ложное срабатывание относится ко всем
   сработавшим правилам.

Аудит: `incident.classified`, дополнительно `detection.false_positive_marked`.

## Пропущенный детект

`POST /api/v1/detection/missed`

Платформа не может обнаружить собственные пропуски, поэтому такая запись — **единственный след**
того, что пропуск был. Обязательны два поля:

- **источник**: аналитик, сообщение сотрудника, шлюз, разбор после инцидента, внешний TI;
- **причина**: какой слой не сработал.

| Причина | Где исправлять |
|---|---|
| `MISSING_FACT` | парсер или извлечение фактов |
| `MISSING_RULE` | пакет правил |
| `PARSER_FAILURE` | разбор MIME, вложений, документов |
| `PROVIDER_FAILURE` | внешний источник или политика обращений |
| `RULE_FAILURE` | условие существующего правила |
| `RISK_AGGREGATION_FAILURE` | агрегация: признаков хватало, баллов нет |

Причина указывается потому, что пропуск из-за лимита разбора исправляется совсем не там, где
пропуск из-за не сработавшего правила. Если пропуск попадает в известный пробел, указывается
`gap_id`; неизвестный идентификатор пробела API отклоняет.

## Ответ сотруднику

`GET /api/v1/incidents/{id}/employee-feedback` возвращает текст **для проверки аналитиком**, а
не отправляет его.

Формулировки не обещают безопасности ни в одном из вариантов. Платформа может сообщить, что
угроз не обнаружено, но не может утверждать, что их нет. Проверено тестом: текст не содержит
«100%», «полностью безопасно», «гарантированно безопасно».

Пример для `FALSE_POSITIVE`:

> Письмо проверено службой информационной безопасности. Признаков угрозы не подтверждено,
> предупреждение было излишним.

## Связанный поиск

`GET /api/v1/investigations/messages/{id}/related` — всё, что связано с письмом, с обязательным
указанием причины:

| Связь | Сила |
|---|---|
| тот же отправитель | сильная |
| то же вложение (по хешу) | сильная |
| та же кампания | сильная |
| тот же адрес для ответа | сильная |
| тот же домен в ссылках | средняя |
| тот же домен отправителя | средняя |
| та же тема | **слабая** |

Связь по теме оставлена — аналитики её просят, — но никогда не опережает остальные: «Счёт на
оплату» составляет половину корпоративной почты. Письмо, связанное тремя способами, идёт выше
письма, совпавшего только темой.

## Кампании

- `GET /api/v1/campaigns/merge-suggestions` — что похоже на одну волну, с причинами.
- `POST /api/v1/campaigns/{id}/merge` — объединить (требует причину).
- `POST /api/v1/campaigns/{id}/split` — выделить письма в отдельную кампанию.

Корреляция **предлагает**, решает аналитик. Разделение важнее объединения: корреляция,
слепившая две волны, скрывает меньшую, а кампанию, которой не видно, никто не расследует.
Выделение всех писем сразу отклоняется — это переименование, а не разделение.

## Качество сообщений сотрудников

`GET /api/v1/detection/reporting-quality`

Это **не рейтинг людей**. Сотрудник, сообщивший о десяти безобидных письмах и одной настоящей
атаке, окупил остальные девять. Числа нужны, чтобы понять, где помогает обучение и чьи
сообщения открывать первыми.

Отдельно считается `reports_that_found_something_new` — сколько раз сотрудник заметил то, чего
платформа не заметила (её собственный вердикт был LOW_RISK или UNKNOWN). Это и есть число,
оправдывающее существование кнопки «сообщить».

Доля подтверждений возвращается как `null`, пока ничего не размечено: неразобранная очередь не
должна выглядеть как 0% подтверждений.

## Права

| Действие | Право | Роль |
|---|---|---|
| смотреть очередь и инциденты | `view:incidents` | наблюдатель |
| читать метрики качества | `quality:read` | наблюдатель |
| классифицировать | `incident:classify` | аналитик |
| сообщать о пропуске | `detection:report_miss` | аналитик |
| симулировать правила | `detection:simulate` | аналитик |
| менять статус правила | `detection:manage` | администратор ИБ |
| повторный анализ и переоценка | `detection:replay` | администратор ИБ |
| утверждать исключение | `exception:approve` | администратор ИБ (не автор) |

Симуляция у аналитика, а повторный анализ — у администратора, потому что первая ничего не
меняет, а вторая может перезаписать сохранённые вердикты.
