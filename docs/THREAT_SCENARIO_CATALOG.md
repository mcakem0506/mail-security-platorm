# Каталог сценариев угроз

ТЗ 1.0.3 §28, §37. От чего платформа защищает — и как это проверяется.

## Зачем отдельный каталог

Список правил отвечает на вопрос «как», но не на вопрос «от чего». Руководитель ИБ,
аудитор и новый аналитик задают второй. Соответствие между сценариями и правилами не взаимно
однозначно: один сценарий закрывается несколькими правилами, одно правило участвует в
нескольких сценариях — поэтому вывести одно из другого нельзя, и каталог ведётся отдельно.

Источник истины — `datasets/threat_scenarios.yaml`.

## Главное свойство: покрытие вычисляется, а не хранится

Поле «покрыт» в каталоге отсутствует. Покрытие считается из действующего пакета правил при
каждом чтении (`GET /api/v1/detection/scenarios`).

Причина простая: запись «покрыто», пережившая удаление правила, утверждает защиту, которой уже
нет. Это хуже отсутствия записи, потому что карта покрытия при этом остаётся зелёной. Сценарий,
у которого удалили все активные правила, становится непокрытым в консоли в тот же момент.

решение принимает человек, а не платформа.

## Структура записи

```yaml
- id: THR-ATT-003
  title: Документ, обращающийся наружу при открытии
  category: suspicious_attachment
  severity: high
  description: >-
    Документ без макросов подгружает удалённый шаблон, обращается к сетевому ресурсу по
    UNC-пути или содержит поле DDE. Проверки, рассчитанные на макросы, его пропускают.
  rules: [ATT-040, ATT-041, ATT-042, ATT-043]
  fixtures: [DOC-001, DOC-002, DOC-003]
  playbook: PB-MALICIOUS-ATTACHMENT
```

Поле `fixtures` обязательно. **Сценарий без кейсов непроверяем**: заявление о покрытии ничем не
подтверждено, и день, когда покрытие исчезнет, никто не заметит. Тест
`tests/unit/test_threat_scenarios.py` проверяет, что:

- все названные правила существуют в пакете;
- все названные кейсы существуют в корпусе;
- у каждого сценария есть описание, правила, кейсы и **написанный** плейбук;
- у каждого сценария есть хотя бы одно активное правило.

## Что нашла проверка каталога

При первой проверке два сценария ссылались на кейсы, которых в корпусе нет (`MAL-001`,
`MLF-001` — идентификаторы, которых я ожидал по аналогии, а не посмотрел). Для каталога,
который должен подтверждать покрытие, это ровно тот дефект, от которого он защищает, — поэтому
проверка ссылок и стала тестом, а не разовой вычиткой.

## Карта покрытия

`GET /api/v1/detection/scenarios` возвращает по каждому сценарию:

| Поле | Смысл |
|---|---|
| `covered` | есть ли хотя бы одно активное правило |
| `active_rules` | сколько активных правил его закрывают |
| `shadow_rules` | сколько ещё измеряется в теневом режиме |
| `fixtures` | сколько кейсов его проверяют |

Сценарий, покрытый только теневыми правилами, показывается как непокрытый: теневое правило по
построению не влияет на вердикт.

## Как добавить сценарий

1. Описать приём так, чтобы было понятно, **почему обычные проверки его пропускают**. Если
   этого в описании нет, сценарий, скорее всего, уже покрыт существующим.
2. Перечислить правила, которые его закрывают. Если их нет — сценарий добавляется вместе с
   правилом либо вместе с записью в [реестре пробелов](DETECTION_GAPS.md).
3. Добавить кейсы в корпус и указать их в `fixtures`.
4. Написать или указать плейбук в [ANALYST_PLAYBOOKS.md](ANALYST_PLAYBOOKS.md).
5. Загрузить: `POST /api/v1/detection/rules/sync`.
