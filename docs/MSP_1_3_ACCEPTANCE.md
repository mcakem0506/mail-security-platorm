# Приёмка MSP 1.3 — контролируемое принуждение

> **MSP 1.3 IS NOT APPROVED FOR GLOBAL PRODUCTION MX CUTOVER.**
> Этап впервые даёт платформе власть над почтой, но только для ограниченной области, по контролю отдельно и по согласованию двух людей.
> Глобального включения нет, пилотный домен допускается лишь по отдельному плану ([ENFORCEMENT_PILOT_PLAN.md](ENFORCEMENT_PILOT_PLAN.md)).

## Решение

**READY_WITH_WARNINGS.** Этап выполнен на лабораторном стенде с настоящими Postfix и Rspamd, но без выборки реального потока:
по ТЗ §83 приёмка только на синтетике не выше `READY_WITH_WARNINGS`. Для `READY_FOR_MSP_1_4` нужны доказательства реального
или пилотного потока (раздел «Что нужно для READY_FOR_MSP_1_4»).

## Найденные и исправленные дефекты этапа

1. **Принуждение, которое 1.2 считала выключенным, существовало.** Milter исполняет родные действия Rspamd: шаблон GTUBE давал `554`, а
   пороги, достижимые по оценке, — отказы и откладывание. Пометка `OBSERVE_ONLY` в панели этого не отражала. Исправлено в конце 1.2
   (недостижимые пороги, GTUBE выключен) и закреплено в 1.3 аудитом итоговой конфигурации: неизвестный источник отказа блокирует выпуск.
   Включённый greylisting теперь тоже блокируется этим аудитом (до отдельного решения).
2. **Служебный получатель копии.** `always_bcc` добавляет в письмо получателя журнала; он попадал в область проверки «все получатели» и срывал
   канарейку. Служебные получатели исключены из решений и карантина.
3. **Одиночный LF** при повторной подаче (Postfix 3.10 отвергает): повторная подача приводит письмо к виду SMTP (CRLF).
4. **Поведение под нагрузкой панели.** При длинной очереди теневых копий полный анализ мог не уложиться в тайм-аут шлюза — письмо
   (штатно) доставлялось. Это свойство однопоточного хранилища стенда (SQLite); проверки карантина ждут «тихой» панели.

## Предупреждения и честные отклонения

1. **Реального потока нет.** Все выборки лабораторные; пилот не включался; ни одна доля ложных на настоящей почте не измерена.
2. **GAP-005, GAP-006 открыты** (`VALIDATION`); `DMARC_REJECT` заблокирован до закрытия GAP-006 (обновление Rspamd или отдельный
   проверяющий модуль и полный набор RFC 9989).
3. **Не проверялись вживую:** `RBL_REJECT`, `MALWARE_REJECT`, `PHISHING_REJECT`, `TEMPFAIL_ABUSE`, исходящее принуждение (`OUTBOUND_BLOCK`,
   удержание) — только модульно; безопасный режим по сроку — только модульно; две независимые ноды не поднимались.
4. **Подпись политики симметрична** (общий ключ у панели и узла): компрометация узла позволяет подделать политику для самого узла.
5. **Нагрузка** — лабораторная: 60 писем двумя группами, до 18 одновременных сессий с каждого из двух адресов (предел узла — 20
   соединений на клиента); профиль «50 сессий, 1000 писем в час» не воспроизводился. Пропускная способность боевой установки не заявляется.
6. **Общий токен 1.1** по умолчанию допустим (`MSP_GATEWAY_SHARED_TOKEN_ALLOWED=true`) ради обратной совместимости; в рабочей установке его отключают.
7. **Нестабильный тест 1.2** (§78): единичный таймаут обогащения теневой копии. Установленная причина — запись сканирования, удалявшаяся после
   отправки в панель до того, как тест её увидит (исправлено хранением отправленных записей). После исправления модуль проходит стабильно
   (см. «Результаты прогона»). Повторов до зелёного в CI нет.
8. Ключ шифрования карантина: смена ключа не автоматизирована; потеря ключа делает хранимые письма нечитаемыми.

## Не реализовано намеренно (§91)

Глобальный переход MX, пользовательский портал карантина, ссылки выпуска для сотрудников, дайджест, полная высокая доступность, репликация
очереди между узлами, SLA пропускной способности, DLP, исходящий комплаенс, автоматическое изменение DNS.

## Что нужно для READY_FOR_MSP_1_4

Выборка реального потока ([ENFORCEMENT_PILOT_PLAN.md](ENFORCEMENT_PILOT_PLAN.md)): ≥ 1000 проанализированных, ≥ 200 просмотренных, ≥ 100
просмотренных кандидатов на отказ; все применённые отказы и карантины просмотрены; критических ложных = 0; закрытый GAP-006 для
`DMARC_REJECT`; живые проверки остальных контролей; отключённый общий токен; две независимые ноды; повторяемость нагрузочной проверки.
