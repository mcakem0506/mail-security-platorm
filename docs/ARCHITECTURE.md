# Архитектура

Документ описывает компоненты платформы, потоки данных и границы ответственности.
Соответствует §4, §5 ТЗ.

---

## 1. Режимы работы

Платформа спроектирована так, чтобы последовательно проходить три режима, не переписываясь:

| Режим | Что делает | Статус |
|---|---|---|
| **Mode A** — User-assisted protection | Outlook Add-in, ручная проверка письма сотрудником | реализован |
| **Mode B** — Mail Threat Detection & Response | серверный анализ, корреляция, инциденты, AD, контролируемое реагирование | реализован |
| **Mode C** — Inline Secure Email Gateway | автоматическая SMTP-фильтрация до доставки | **не входит в v1** (MSP 1.1+) |

В v1 платформа **не является точкой доставки почты**. Её отказ не останавливает почту:
Outlook продолжает работать, а серверный анализ работает в shadow-режиме.

### Почему две стадии

Локальный анализ и внешнее обогащение разделены намеренно (§2.3, §35):

- сотрудник получает объяснимый вердикт за время локального анализа, не ожидая внешних API;
- недоступность Threat Intelligence не превращается в отказ проверки;
- обогащение **только повышает** класс риска, поэтому задержка второй стадии не может привести
  к ложному «всё в порядке».

Пока вторая стадия не завершена, задание имеет состояние `PARTIAL`, а `ti_state = PENDING` —
и это видно сотруднику в панели.

## 3. Компоненты

### MSP-CORE-01 — API (`apps/api`)

FastAPI, Python 3.12. 41 эндпоинт: аутентификация, RBAC, постановка анализа, результаты,
расследования, инциденты, кампании, политики, исключения, провайдеры, реагирование, аудит,
health, метрики.

Ответственность: приём запроса, авторизация (в том числе объектного уровня), запуск локального
анализа, постановка задач в очередь, отдача проекций данных по роли.

### MSP-CORE-02 — Worker (`apps/worker`)

Celery. Очереди разделены так, чтобы зависание одного внешнего провайдера не блокировало
остальное:

| Очередь | Задачи | Egress |
|---|---|---|
| `mail_parse` | приём из security mailbox, разбор | **нет** |
| `attachment_analysis` | статический анализ, локальный сканер | нет |
| `ti_lookup` | обогащение Threat Intelligence | да |
| `campaign` | пересчёт агрегатов кампаний | нет |
| `notifications` | уведомления | да (SMTP) |
| `maintenance` | AD-синхронизация, retention, re-check | да |

Периодические задачи: опрос security mailbox (1 мин), AD-синхронизация (по настройке),
retention (6 ч), re-check индикаторов (12 ч), проверка истёкших исключений (1 ч).

### MSP-CORE-03 — Frontend

- **Security Console** (`apps/security-console`) — React + TypeScript. Интерфейсы аналитика
  и администратора, безопасный просмотр писем.
- **Outlook Add-in** (`apps/outlook-addin`) — Office.js. Интерфейс сотрудника.

### MSP-CORE-04 — Storage

**PostgreSQL 16** — метаданные, индикаторы, результаты, сигналы, инциденты, политики, аудит
(35 таблиц).

**Object storage** — исходные EML, вложения, экспортированные отчёты. Хранится отдельно от
метаданных с более жёстким доступом. Ключи вычисляются из хеша содержимого, а не из имени файла.
Для пилота достаточно файлового backend'а; S3-совместимый MinIO включается профилем.

**Redis** — кэш Threat Intelligence, серверные сессии, брокер очередей, rate limiting.
Не является авторитетным хранилищем: его потеря не теряет данные.

## 4. Пакеты и границы

```text
msp_contracts      ← общие типы. Не зависит ни от чего.
msp_mail_parser    ← разбор MIME/URL/архивов. Без БД и без сети.
msp_detection      ← факты и правила. Без БД и без сети; контекст передаётся снаружи.
msp_risk           ← агрегация вердикта. Чистая функция от набора сигналов.
msp_ti             ← интерфейс провайдеров, privacy gate, кэш, Hub.
providers/*        ← все внешние интеграции, каждая за своим Protocol.
msp_api            ← БД, HTTP, авторизация, сборка контекста.
msp_worker         ← фоновые задачи.
```

Правило: пакеты анализа (`msp_mail_parser`, `msp_detection`, `msp_risk`) не знают про базу
данных, HTTP и сеть. Благодаря этому их можно тестировать без инфраструктуры, а движок
детектирования нельзя случайно заставить сделать сетевой запрос при разборе письма.

Все внешние интеграции спрятаны за `Protocol` (§46.6), поэтому каждая имеет mock-реализацию,
и платформа запускается и тестируется без Exchange, AD и VirusTotal.

## 5. Сетевые границы

```text
Пользователи
   │ HTTPS
   ▼
nginx (edge)          единственная точка входа
   │
   ▼
api, frontend (app)   внутренняя сеть, без выхода в интернет
   │
   ▼
postgres, redis,      internal: true — недоступны извне
object storage (data)
   
worker-ti,            единственные компоненты с egress,
worker-maintenance    только к разрешённым провайдерам
```

Парсер писем работает в `worker-mail`, который **не имеет исходящего доступа** — недоверенный
контент обрабатывается там, где его нельзя использовать для запроса наружу.

## 6. Модель вердикта

Вердикт не является числом. Он состоит из:

| Поле | Назначение |
|---|---|
| `classification` | `LOW_RISK`, `SUSPICIOUS`, `HIGH_RISK`, `MALICIOUS`, `UNKNOWN` |
| `score` | внутренний 0–99, для сортировки и порогов |
| `confidence` | `low` / `medium` / `high` |
| `reasons` | причины: заголовок, объяснение, важность, источник, время |
| `sources` | какие источники участвовали |
| `missing_evidence` | чего не хватило: шифрование, недоступность провайдера, лимиты |
| `hard_signals` | сигналы, поднявшие класс напрямую, с источником и временем |
| `suppressed` | сигналы, подавленные исключениями, и каким именно |

Агрегация насыщающая: множество слабых сигналов не складывается в `MALICIOUS`. Один критичный
сигнал даёт примерно `HIGH_RISK`, два — `MALICIOUS`.

`UNKNOWN` возвращается, когда доказательств недостаточно. Это осознанно сделано, чтобы
отсутствие обнаружения нельзя было прочитать как «безопасно» (§17.3, §49.9).

## 7. Технологические решения и их причины

| Решение | Причина |
|---|---|
| `nh3` для санитизации HTML | реализация на Rust (ammonia), allowlist-модель; `url_schemes=set()` удаляет ссылки целиком, поэтому в просмотре они физически не могут быть кликабельны |
| Собственное определение типов файлов | не тянет `libmagic` в образ, не исполняет содержимое, и определяет ровно то, что нужно детектам (макросы, OLE, OOXML, HTML smuggling) |
| Офлайн Public Suffix List | разбор домена не должен требовать сети; `tldextract` с `suffix_list_urls=()` |
| Собственный интерпретатор условий правил | правила приходят из YAML, который редактирует администратор — `eval` здесь недопустим |
| Серверные сессии в Redis вместо JWT | нужна возможность немедленно отозвать сессию (смена пароля, инцидент) |
| Argon2id | устойчив к GPU-перебору, параметры по рекомендациям OWASP |
| Celery с разделением очередей | требование §5: зависание провайдера не блокирует остальные очереди |
| Alembic с `render_item` | миграции не импортируют код приложения, поэтому применимы на любой версии |

## 8. Что осознанно не сделано в v1

| Не реализовано | Причина |
|---|---|
| Inline SMTP-фильтрация | требует HA, персистентных очередей, backpressure и отдельной приёмки (§21, §49.13) |
| Собственный AV-движок и sandbox | вне области v1 (§3.2); предусмотрены интерфейсы `MalwareScannerProvider` и `SandboxProvider` |
| Открытие URL из писем | по умолчанию запрещено; включение требует изолированной egress-зоны (§11.4) |
| Загрузка файлов в VirusTotal | запрещена в v1, требует отдельного пути Private Scanning (§14.5) |
| EWS-операции | нет фактических данных о среде (§51); реализован adapter boundary с перечнем blocker'ов |
| Запись в Active Directory | запрещена (§49.8); в модуле нет ни одной операции записи |
| Извлечение URL из QR-кодов и office-документов | отдельные поздние этапы (§11.1) |

## Дополнения этапов MSP 1.0.1 и 1.0.2

### Пакет `providers/mail-gateway`

Вся работа с внешними почтовыми шлюзами вынесена в отдельный пакет `msp_mail_gateway`:

```text
msp_mail_gateway/
  received.py        разбор цепочки Received без обращений к DNS
  trust.py           доказательство прохождения через узел; доверие к Authentication-Results
  base.py            Protocol MailGatewayProvider и безопасные отказы по умолчанию
  headers.py         общая нормализация статусов, оценок и имён угроз
  ksmg.py            адаптер KSMG
  generic_header.py  настраиваемый провайдер заголовков
  builtin.py         EOP, SpamAssassin, generic AV
  syslog.py          приём событий: allowlist, защита от повтора, дедупликация, dead-letter
  api_base.py        каркас адаптера API: SSRF-шлюз, предохранитель, секреты
  registry.py        реестр провайдеров, единое решение о доверии на сообщение
  conflict.py        расхождения между источниками
  skeletons.py       вендоры с реализованным разбором заголовков и объявленным API
```

### Направление зависимостей

Движок детектирования **не зависит** ни от одного провайдера шлюза. Реестр собирается в
сервисном слое API, результат приводится к `GatewayFindings` — структуре из типов
`msp_contracts` — и передаётся в контекст анализа:

```text
БД (MailGateway, TrustedHop)
      ↓
services/gateways.build_registry()
      ↓
GatewayRegistry.analyze_message()   ← одно решение о доверии на сообщение
      ↓
GatewayFindings                      ← только типы msp_contracts
      ↓
msp_detection.build_facts()
```

Провайдер не вычисляет доверие сам: иначе адаптер мог бы доверять собственным заголовкам.

### Устойчивый приём

```text
FETCH → IntakeRecord → содержимое в объектное хранилище → AnalysisJob → COMMIT → ack/Processed
```

Подтверждение выполняется вне транзакции намеренно: перемещение по IMAP не может входить в
транзакцию БД, поэтому одно из двух неизбежно идёт вторым. Порядок выбран так, что худший исход —
повторное чтение, а не потеря письма.
