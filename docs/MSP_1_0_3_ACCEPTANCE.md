## 1. §2–§4, §7, §8 Оценка детектирования

Пакет `packages/detection-eval/` реализует оценку целиком: датасет с версией и контрольной
суммой, метрики, гейт, отчёты.

Главное свойство — **метрика, которую не на чем посчитать, возвращает `None`, а не ноль**.
Дашборд, показывающий 0% ложных срабатываний потому, что никто ничего не разметил, читался бы
как успех; это самое опасное число, которое мог бы показать продукт.

Отдельно различаются `unknown` (вердикт UNKNOWN там, где ожидалась атака — пропуск) и
`correctly_uncertain` (неопределённость ожидалась). Без этого различия recall занижался до
0.923 вместо 0.987: кейс, где честный ответ «не могу сказать», не является ошибкой.

Подробно: [DETECTION_EVALUATION.md](DETECTION_EVALUATION.md).

## 2. §5, §58 Золотой корпус

340 кейсов, минимальные количества §58 выполнены. Корпус генерируется кодом, а не собирается из
почты: живого вредоносного ПО, персональных данных, реальных учётных данных и секретов
организации в нём нет конструктивно (§5.1).

У каждого опасного приёма есть легитимный двойник, отличающийся ровно тем признаком, который
должен решать. Две такие пары добавлены после того, как оценка нашла на них 10 ложных
срабатываний.

Подробно: [GOLDEN_DATASET.md](GOLDEN_DATASET.md).

## 3. §6, §12, §15, §16, §48 Движок и объяснимость

Четыре слоя разделены: разбор → факты → правила → агрегация. Правила — данные; `eval`,
произвольный код и динамические импорты в файлах правил запрещены.

Словарь фактов извлекается из исходного кода движка (`msp_detection/vocabulary.py`), и тест
проверяет, что каждое условие и каждый ключ доказательств из пакета правил в нём есть. Правило
с опечаткой в условии загружается без ошибок и не срабатывает никогда — оно занимает строку в
карте покрытия и не защищает ни от чего.

С каждым вердиктом сохраняются четыре версии (пакет правил, движок риска, парсер, политика
обогащения). Политика входит в список потому, что вердикт при выключенных внешних обращениях
несопоставим с вердиктом после их включения.

Граф доказательств (§16) строится из сохранённого результата: `письмо → факты → правила →
вердикт`, плюс узлы того, что проверить не удалось.

Подробно: [DETECTION_ENGINE.md](DETECTION_ENGINE.md).

## 4. §9–§14, §24, §25 Жизненный цикл правил

Шесть статусов. Теневое правило не даёт баллов **по построению** (`effective_weight`
возвращает 0 для нескорящих статусов), а не из-за настройки веса.

В `ACTIVE` можно попасть только из `SHADOW`; `ACTIVE` без владельца запрещён и проверяется
гейтом. Флаг `shadow` и статус правила на момент срабатывания сохраняются в БД — без этого
теневой режим невозможно измерить, а неизмеримый теневой режим бессмыслен.

Симуляция ничего не меняет; повторный анализ и переоценка истории создают новую ревизию и по
умолчанию работают в режиме предложения.

Исключения: четыре глаза (автор не утверждает сам), неутверждённое исключение инертно.

Подробно: [RULE_LIFECYCLE.md](RULE_LIFECYCLE.md).

## 5. §17–§26, §30–§34 Рабочий процесс аналитика

Очередь, приоритизация, SLA, назначение, хронология, классификация, обратная связь, связанный
поиск, кураторство кампаний, качество сообщений сотрудников — реализованы и выведены в консоль.

**Приоритет не равен риску** (§18). Проверено на стенде и тестами:

| Ситуация | Вердикт | Приоритет |
|---|---|---|
| MALICIOUS одному, письма удалены | MALICIOUS | P3 |
| HIGH_RISK кампания на финансовый отдел | HIGH_RISK | P1 |
| SUSPICIOUS руководителю, кража учётных данных | SUSPICIOUS | P2 |
| MALICIOUS платёжное мошенничество, один адресат | MALICIOUS | P2 (понижено, причина показана) |
| MALICIOUS с вложением, один адресат | MALICIOUS | P1 (последствие необратимо) |

P1 требует второй оси — охвата или необратимого последствия. Без этого условия на реальных
данных 16 из 19 инцидентов оказывались P1, то есть очередь переставала иметь приоритет.

Формулировки для сотрудника не обещают безопасности ни в одном варианте; это проверяется
тестом.

Подробно: [ANALYST_WORKFLOW.md](ANALYST_WORKFLOW.md), [ANALYST_PLAYBOOKS.md](ANALYST_PLAYBOOKS.md).

## 6. §27 Реестр пробелов

Три записи, у каждой — причина, серьёзность, владелец, целевой релиз, компенсирующая мера и
план закрытия. Гейт прощает провал кейса с зарегистрированным пробелом и блокирует
незарегистрированный.

Подробно: [DETECTION_GAPS.md](DETECTION_GAPS.md).

## 7. §28, §29, §37 Каталог сценариев и покрытие

15 сценариев, 74 правила, у каждого сценария есть кейсы корпуса и написанный плейбук. Покрытие
**вычисляется** из действующего пакета правил, а не хранится: запись «покрыто», пережившая
удаление правила, утверждает защиту, которой уже нет.

Подробно: [THREAT_SCENARIO_CATALOG.md](THREAT_SCENARIO_CATALOG.md).

## 8. §35, §36 Дашборды качества

Дашборд качества детектирования: метрики (с «—» там, где считать не на чем), шумные и молчащие
правила, правила без владельца, открытые пробелы, непроверенные письма, версии движков.

Дашборд качества внешних источников отвечает на вопрос, на который не отвечает доступность:
был ли ответ полезен. Источник с доступностью 100% и покрытием 5% никого не защищает.

## 9. §38–§40 Новые классы детектирования

| Приём | Как детектируется |
|---|---|
| QR-код | наличие — по заголовку изображения и формулировкам письма, без зависимостей; содержимое — только с необязательным декодером (GAP-002) |
| Ссылки в Office-документах | разбор relationship-частей OOXML ограниченными регулярными выражениями, без XML-парсера |
| Удалённый шаблон, UNC-путь, DDE | отдельные признаки с разными последствиями |
| HTML smuggling | полезная нагрузка + декодер + конструктор + триггер сохранения, по отдельности не являющиеся сигналом |

Нераспознанный QR-код делает проверку неполной: отсутствие детекта не является безопасностью.

## 10. §41, §42 Семантический анализ

Полностью локальный, 16 намерений на регулярных выражениях. Внешние языковые модели не
используются. Условия, при которых они допустимы, записаны заранее — чтобы решение принималось
по правилам, а не в момент, когда очень хочется.

Подробно: [SEMANTIC_ANALYSIS_POLICY.md](SEMANTIC_ANALYSIS_POLICY.md).

## 11. §43–§47 Производительность и устойчивость

34 теста: бюджет локального анализа, безопасность 140+ регулярных выражений на 12 входах под
вложенные квантификаторы, фаззинг (произвольные байты в парсер, анализатор smuggling, чтение
заголовков изображений, разбор документов), состязательные входы.

Везде проверяется не только время, но и то, что достигнутый лимит виден в `limits_hit`:
молчаливый пропуск хуже отказа.

## 12. §49–§52 Воспроизводимость и выпуск

Повторный анализ и переоценка истории — новые ревизии, оригинал не перезаписывается.

**Канареечный выпуск (§52) реализован как механизм платформы**, а не только как порядок
действий. Правило со статусом `ACTIVE` ограничивается областью (список ящиков, отделы или доля
ящиков по устойчивому хешу адреса), и вне этой области оно **удержано, а не выключено**: сигнал
записывается и измеряется, но не даёт баллов и не ставит нижнюю границу вердикта, даже если
правило объявлено жёстким. Благодаря этому остальная часть организации становится контрольной
группой, и сравнение «в области против вне её» не требует отдельного учёта.

Срок решения обязателен и по истечении ничего не меняет сам: область сохраняется, а
незавершённый выпуск становится видимым на дашборде. Снять область автоматически означало бы
выпустить непроверенное правило на всех; снять правило — молча отключить детектирование.

Порядок: [DETECTION_RELEASE_PROCESS.md](DETECTION_RELEASE_PROCESS.md).

## 13. §53 Готовность к нескольким организациям

Вся модель данных и все запросы 1.0.3 ограничены `organization_id`; проверено тестом, что
связанный поиск не возвращает письма другой организации. Правила, пробелы и сценарии
загружаются из файлов в таблицы, ключами которых является организация, поэтому две организации
на одном экземпляре могут иметь разный состав без пересборки.

Не реализовано и не требуется в 1.0.3: разделение хранилища объектов по организациям и
отдельные ключи шифрования. Это условие полноценной мультиарендности, а не готовности к ней.

## Дефекты, найденные при сборке этапа

Ни один из них не был найден обычным прогоном тестов — каждый нашёлся при проверке на
работающей системе, при чтении метрик или при попытке измерить собственную проверку.

| Где | Дефект | Как найден |
|---|---|---|
| БД | флаг `shadow` не сохранялся — теневые правила невозможно измерить | при написании отчёта по теневым правилам |
| Миграции | NOT NULL без `server_default` — падение на БД с данными | при прогоне на БД, где уже были строки |
| Celery | 20 попыток переподключения: проверка письма висела 80 с вместо быстрого отказа | медленный тест |
| Гейт | правило с владельцем помечалось как бесхозное | гейт заблокировал выпуск без причины |
| Правила | URL-031 ссылалось на несуществующие факты и не могло сработать | проверка словаря фактов |
| Очередь | инцидент с двумя кампаниями ронял очередь целиком (500) | скриншоты стенда |
| Приоритет | 16 из 19 инцидентов — P1; три фактора срабатывали на 19 из 19 | скриншоты стенда |
| Дашборд | все письма считались непроверенными (сравнение с несуществующим значением) | скриншоты стенда |
| Консоль | новые коды факторов показывались без перевода | скриншоты стенда |
| Консоль | хронология инцидента бралась из старого поля, а не из §21 | скриншоты стенда |

Все исправлены, на каждый добавлен тест.

## Продолжение: MSP 1.0.3B

Этап MSP 1.0.3B — операции детектирования и работа аналитика — принят отдельным документом:
[MSP_1_0_3B_ACCEPTANCE.md](MSP_1_0_3B_ACCEPTANCE.md). Он не переписывает настоящую приёмку:
то, что было подтверждено здесь, там помечено как `ALREADY IMPLEMENTED` со ссылкой на код и
тест, а не проверено заново.

Два дефекта, найденных в 1.0.3B, относятся к коду этого этапа: эндпоинты
`GET /campaigns/match-quality` и `GET /campaigns/merge-suggestions` были недостижимы с момента
появления (перекрыты `GET /campaigns/{campaign_id}`), и консоль показывала на их месте пустую
панель. Исправлено переносом под `/detection/campaigns/`; вся таблица путей проверяется тестом.
