# DMARC и RFC 9989

**Относится к:** ТЗ MSP 1.2 §10, §38, §50
**Код:** `msp_antispam/auth.py` (`dmarc_evidence`); проверки — `tests/spam/test_dmarc.py`, `tests/unit/test_antispam_auth.py`

> **Честное состояние.** DMARC проверяет Rspamd 3.12.1; MSP не пишет собственный поиск политики (ТЗ §3). Эта версия
> сканера реализует поиск политики и выравнивание по RFC 7489 (организационный домен по списку публичных суффиксов) и
> **не** реализует часть новшеств RFC 9989. Каждое отличие проверено на настоящем сканере, закреплено тестом и
> записано в реестр пробелов (**GAP-006**). На этапе 1.2 отличия влияют только на `suggested_disposition`, которое
> ничего не исполняет.

## Нормализованный результат

`PASS`, `FAIL`, `NONE`, `TEMPERROR`, `PERMERROR`. Сохраняются политика (`p`), домен политики, домен из From,
выровненность SPF и DKIM, метаданные (символ сканера, причина) и **предложенное решение** (`suggested_disposition`:
`NONE` / `QUARANTINE` / `REJECT`).

Даже `DMARC FAIL` при `p=reject` на этапе 1.2 даёт **только** `suggested_disposition = REJECT`. Доставка продолжается,
применённое действие — `OBSERVE_ONLY` (проверено на стенде: письмо с таким результатом доставлено Exchange).

## Сверка с RFC 9989

| Требование | Rspamd 3.12.1 | Проверка |
|---|---|---|
| Выравнивание по SPF (relaxed / strict `aspf`) | реализовано | `test_relaxed_spf_alignment…`, `test_strict_spf_alignment…` |
| Выравнивание по DKIM (relaxed / strict `adkim`) | реализовано | `test_relaxed_dkim_alignment…`, `test_strict_dkim_alignment…` |
| Достаточно одного выровненного механизма | реализовано | `test_spf_aligned_pass…`, `test_dkim_aligned_pass…` |
| Оба провалены → политика домена | реализовано (`reject`, `quarantine`, `none`) | `test_both_fail…`, `test_quarantine…`, `test_policy_none…` |
| Политика поддомена `sp` | реализовано | `test_the_subdomain_policy_applies…` |
| Несколько записей DMARC — политики нет | реализовано | `test_two_dmarc_records…` |
| Неверная запись не применяется | реализовано | `test_an_invalid_record…` |
| Сбой DNS — временная ошибка, не провал | реализовано | `test_a_dns_failure_is_temperror…` |
| Пересылка (подпись цела — DMARC проходит) | реализовано | `test_forwarding_keeps_dmarc_alive…` |
| ARC не отменяет DMARC автоматически | подтверждено | `test_arc_does_not_rescue…` |
| **Поиск политики обходом дерева DNS** (RFC 9989 §4) | **не реализовано**: проверяются имя автора и организационный домен по PSL; запись на промежуточном уровне пропускается | `TestRfc9989::test_tree_walk…` |
| **Тег `np`** (политика для несуществующих поддоменов) | **не применяется** | `TestRfc9989::test_deviation_np_tag…` |
| **Тег `t`** (режим проверки) | **не учитывается**: политика сообщается как обычно | `TestRfc9989::test_deviation_testing_flag…` |
| Тег `psd` (домены публичных суффиксов) | не поддержан (не проверялся) | — |

## Последствия и меры

* Для организации, чья политика лежит на промежуточном уровне или использует `np`, MSP увидит `NONE` либо менее строгую
  политику: предложение отказа не появится там, где по RFC 9989 оно должно. Это ошибка в сторону *пропуска* предложения,
  а не ложного отказа.
* Домен с `t=y` может получить `suggested_disposition = REJECT` для письма, которое по RFC 9989 не следует отклонять. Это
  важно для этапа 1.3 (принуждение) и поэтому входит в условия допуска: пока отличие не закрыто, `REJECT` от DMARC
  допускается только как предложение, проходящее ручной просмотр ([SPAM_REAL_FLOW_VALIDATION.md](SPAM_REAL_FLOW_VALIDATION.md)).
* Закрытие: обновление сканера до версии с DMARCbis либо отдельное решение о собственной реализации поиска политики
  (она запрещена ТЗ 1.2 §3 и потребует отдельной приёмки). Тесты `test_deviation_*` и `TestRfc9989` сообщат, когда поведение изменится
  (они пропускаются с пояснением, если установленная версия начала поддерживать новшество).
