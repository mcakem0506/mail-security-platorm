# Транспортный слой шлюза: архитектура

**Относится к:** ТЗ MSP 1.1 §2–§8, §38, §59, §61
**Читать вместе с:** [GATEWAY_MAIL_FLOW.md](GATEWAY_MAIL_FLOW.md), [GATEWAY_SECURITY_MODEL.md](GATEWAY_SECURITY_MODEL.md), [GATEWAY_OPERATIONS.md](GATEWAY_OPERATIONS.md)

> **MSP 1.1 IS NOT APPROVED FOR PRODUCTION MX CUTOVER.**
> Этап строит надёжный транспортный фундамент. Он не заменяет почтовый шлюз организации, не
> принимает боевую почту и не меняет DNS. См. §8 этого документа.

---

## 1. Что построено и что нет

MSP 1.1 добавляет платформе собственный SMTP-транспорт на Postfix, который можно поставить в разрыв
почтового пути:

```text
Интернет (или тестовый источник) ─► Шлюз ─► Exchange        (входящая почта)
Exchange ─► Шлюз ─► приёмник / вышестоящий сервер          (исходящая почта)
```

Построено: приём и доставка почты с постоянной очередью, защита от открытого релея, проверка
получателей, TLS с проверкой сертификата, режим слива, версии конфигурации с откатом, наблюдаемость,
теневая копия писем для анализа, изолированный разбор вложений, пакет сценариев для Exchange.

**Не построено намеренно** (ТЗ §58, §74): оценка спама, чёрные списки (RBL), отказ по SPF, принуждение DKIM
и DMARC, подпись DKIM, блокировка по репутации, блокировка по результатам VirusTotal, карантин
пользователя, автоматическое переключение MX, полноценная высокая доступность. Даже вердикт
`MALICIOUS` не отклоняет, не удаляет и не задерживает письмо: детектирование не стоит на пути доставки.

## 2. Две плоскости

| Плоскость | Что делает | Где живёт | Что будет, если её не станет |
|---|---|---|---|
| **Транспортная** | принимает, ставит в очередь, доставляет почту | Postfix на узле | почты нет |
| **Управляющая** | хранит конфигурацию, справочник, историю, показывает состояние | API, база, консоль | **почта идёт как шла**; пропадают управление и наблюдение |

Это главное архитектурное решение: плоскость управления не стоит на пути письма. Узел продолжает
принимать и доставлять почту без панели, на последней применённой конфигурации. Проверяется
сквозным тестом `tests/gateway/test_panel_integration.py` (панель остановлена — письмо доставлено, копия
для анализа ждёт в журнале и уходит после возвращения панели).

Очередь Postfix — **единственный источник истины** о принятой почте (ТЗ §6). Ни база, ни Redis не
хранят принятое письмо, и перезапуск любого из них не может его потерять.

## 3. Компоненты

```text
┌───────────────────────────── узел шлюза (контейнер) ─────────────────────────────┐
│                                                                                  │
│  Postfix (root, мастер)                                                          │
│    ├─ слушатель :25   публичный: только релей на свои домены, только известным   │
│    ├─ слушатель :2525 внутренний: доверенные сети, STARTTLS обязателен           │
│    ├─ очередь /var/spool/postfix (том, не общий между узлами)                    │
│    └─ транспорт msp-journal ──► копия письма в журнал (пользователь mspjournal)  │
│                                                                                  │
│  msp_gateway.node sync     (root)        забирает конфигурацию и команды панели  │
│  msp_gateway.node agent    (mspagent)    метрики, пробы, события                 │
│  msp_gateway.node collector(mspjournal)  копии писем ─► панель                   │
└──────────────────────────────────────────────────────────────────────────────────┘
                   │ HTTPS + токен узла                     │ запись копий
                   ▼                                        ▼
┌──────────── панель управления ────────────┐     ┌──────── песочница вложений ────────┐
│ API: /gateway, /gateway-agent             │     │ контейнер без сети, не от root     │
│ база: узлы, версии, справочник, события   │     │ 7z/RAR по оглавлению, PDF в страницы│
│ воркер: анализ копии                      │     │ вход/выход — каталог-очередь        │
│ консоль: раздел «Транспорт почты»         │     └────────────────────────────────────┘
└───────────────────────────────────────────┘
```

Каждый процесс узла работает от **своего** пользователя с минимальными правами:

| Процесс | Пользователь | Что вправе | Чего не вправе |
|---|---|---|---|
| Postfix | root/postfix | принимать и доставлять почту | — |
| синхронизация | root | применять конфигурацию, сливать узел, `postfix reload` | выполнять что-либо, чего не прошла проверка узла |
| агент | `mspagent` (10003) | читать журнал Postfix, снимок очереди, отдавать метрики | писать в состояние Postfix, читать журнал копий |
| писатель копий | `mspjournal` (10002) | писать копию письма | трогать очередь |
| сборщик | `mspjournal` (10002) | читать журнал копий, отправлять в панель | менять доставку |

## 4. Путь конфигурации

```text
GatewaySpec (проверяемая модель) ─► render ─► пакет (файлы + manifest + контрольная сумма)
   ─► проверка узла ─► postmap ─► postfix check ─► переключение ссылки active ─► reload
   ─► проверка здоровья ─► ACTIVE   (иначе откат на прежнюю версию)
```

* Все значения, попадающие в конфигурацию Postfix, проходят схему: адреса, домены, сети, порты и пути
  проверяются форматом, перевод строки и подстановки командной оболочки невозможны. «Сырых директив»
  в API и консоли нет (ТЗ §64).
* **Узел проверяет пакет сам**, независимо от того, кто и как его собрал: белые списки параметров
  `main.cf` и `master.cf`, транспорт `pipe` ограничен одним исполняемым файлом и пользователем, пустой
  справочник при настроенных доменах не применяется. Контрольная сумма защищает от порчи, но не от
  подмены, поэтому ей не доверяют.
* **Дрейф**: узел пересчитывает контрольную сумму файлов на диске и сравнивает с принятым описанием.
  Расхождение — критичная тревога `CONFIG_DRIFT`.
* Откат возвращает **сохранённый** пакет, а не пересобранный (см. [GATEWAY_ROLLBACK.md](GATEWAY_ROLLBACK.md)).

## 5. Границы доверия

1. **Интернет → публичный слушатель.** Недоверенная сторона. Релей разрешён только на домены организации и
   только известным получателям. Доверенных сетей на публичном слушателе нет вообще (`mynetworks` пуст).
2. **Exchange → внутренний слушатель.** Доверие определяется **подсетью источника**, а не заявлением клиента
   (HELO и адрес отправителя пишет клиент). Поля «доверять по имени» в модели нет.
3. **Узел → панель.** Общий токен узла в заголовке, HTTPS в боевой установке. Панель может *предложить*
   конфигурацию, но не обойти проверку узла.
4. **Панель → песочница.** Только данные через каталог-очередь; песочница не имеет сети.
5. **Копия письма → анализ.** Односторонне: анализ ничего не возвращает транспорту.

## 6. Режимы развёртывания

| Режим | Назначение |
|---|---|
| `COMPANION_ONLY` | платформа работает как раньше, транспорт не используется |
| `GATEWAY_LAB` | лабораторный стенд, тестовый домен, допустимы упрощённые TLS |
| `GATEWAY_PILOT` | узкий пилот на отдельном тестовом домене; требует профиль TLS `REQUIRED`, срок жизни очереди не менее суток |

`GATEWAY_PRODUCTION` намеренно отсутствует в модели: значения, которого нет, нельзя выставить по ошибке.

---

## 7. Высокая доступность: что заложено

Каждый узел имеет **собственную** очередь; общий записываемый `/var/spool/postfix` между активными узлами
запрещён (ТЗ §61), и модель этого не допускает. Узлы независимы и взаимозаменяемы:

```text
вывести из нового трафика ─► слить очередь ─► проверить ─► обслуживание ─► проверка здоровья ─► вернуть трафик
```

Режим слива и проверка очереди реализованы; автоматическое переключение трафика между узлами (балансировщик,
виртуальный адрес) в этот этап **не входит**.

## 8. Гарантия против случайного боевого использования

* В манифесте каждой версии, в консоли (на каждой вкладке), в ответе `GET /api/v1/gateway/queue/summary`, в
  каждом сценарии Exchange и в этом документе стоит надпись **MSP 1.1 IS NOT APPROVED FOR PRODUCTION MX CUTOVER**.
* Нет ни одной операции, меняющей DNS или MX-записи; сценарии Exchange только читают или печатают план
  (проверяется тестом: изменяющих командлетов в исполняемом коде нет).
* Доставка наружу выключена по умолчанию; прямая доставка в Интернет требует явного подтверждения в описании.

Результат приёмки этапа не означает «готовый к эксплуатации почтовый шлюз». Он означает, что транспортный
фундамент достаточно надёжен, чтобы строить поверх него следующие уровни.
