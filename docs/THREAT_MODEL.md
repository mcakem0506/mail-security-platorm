# Модель угроз платформы

Документ описывает угрозы **самой платформе**, а не угрозы почте, от которых она защищает.
Платформа обрабатывает контент, созданный атакующими, и хранит корпоративную переписку —
поэтому она сама является привлекательной целью.

Соответствует §38, §48 ТЗ.

---

## 1. Что защищаем

| Актив | Почему ценен для атакующего | Класс |
|---|---|---|
| Содержимое писем и вложения | корпоративная информация, реквизиты, персональные данные | критичный |
| Результаты анализа и правила детектирования | понимание того, что платформа обнаруживает, позволяет обойти детект | высокий |
| Список защищаемых идентичностей | готовая карта целей для BEC | высокий |
| Учётные данные и сессии аналитиков | доступ ко всей переписке организации | критичный |
| Право remediation | возможность удалить письма из ящиков организации | критичный |
| Журнал аудита | сокрытие следов | высокий |
| Ключи внешних провайдеров | использование чужой квоты, раскрытие индикаторов организации | средний |
| Доверие сотрудников к вердиктам | ложное «безопасно» приводит к успешной атаке | критичный |

## 2. Границы доверия

```text
   ┌──────────── НЕДОВЕРЕННОЕ ────────────┐
   │ Содержимое письма: заголовки, HTML,   │
   │ URL, имена файлов, архивы, вложения   │
   └───────────────┬───────────────────────┘
                   │  ← граница 1: разбор без исполнения, без сети, с лимитами
   ┌───────────────▼───────────────────────┐
   │ Факты и сигналы (структурированные)   │
   └───────────────┬───────────────────────┘
                   │  ← граница 2: правила из YAML, интерпретатор без eval
   ┌───────────────▼───────────────────────┐
   │ Вердикт и хранимые данные             │
   └───────────────┬───────────────────────┘
                   │  ← граница 3: RBAC + объектная авторизация + аудит
   ┌───────────────▼───────────────────────┐
   │ Аналитик, администратор, сотрудник    │
   └───────────────┬───────────────────────┘
                   │  ← граница 4: dry-run, согласование, подтверждение
   ┌───────────────▼───────────────────────┐
   │ Exchange (изменение ящиков)           │
   └───────────────────────────────────────┘
```

Полудоверенные: Exchange, AD, SMTP (внутренние, но могут быть скомпрометированы).
Недоверенные: провайдеры Threat Intelligence (их ответы — данные, не команды).

## 3. Угрозы и защита (STRIDE)

### 3.1. Подмена (Spoofing)

| Угроза | Защита |
|---|---|
| Подделка сессии | идентификатор подписан HMAC-SHA256 и проверяется до обращения к хранилищу; сессии серверные и отзываемые |
| Кража cookie через XSS | `HttpOnly`, CSP без `unsafe-inline` для скриптов, санитизация контента |
| CSRF из внешнего сайта | double-submit token + `SameSite=Strict`; обязателен для всех небезопасных методов |
| Перебор пароля | блокировка после 5 попыток с экспоненциальным ростом, rate limit на IP и на учётную запись |
| Перечисление учётных записей | единый ответ для неизвестного пользователя и неверного пароля |
| Подделка `X-Forwarded-For` | доверяется только заголовок, установленный собственным nginx |

### 3.2. Изменение (Tampering)

| Угроза | Защита |
|---|---|
| SQL-инъекция | только параметризованные запросы SQLAlchemy; проверено тестами с 4 видами полезной нагрузки |
| Инъекция в правила детектирования | условия разбирает собственный интерпретатор; `eval` не используется — проверено тестом |
| Path traversal при записи в хранилище | ключ строится из хеша содержимого, валидируется, путь проверяется на выход за корень |
| Path traversal через имя файла в архиве | имена нормализуются; `..`, абсолютные пути и symlink помечаются и не распаковываются |
| Подмена вердикта через повторную отправку | идемпотентность по (пользователь, содержимое) |
| Trojan Source в исходном коде | проверка отсутствия bidi-символов в CI |
| Изменение журнала аудита | модуль аудита не содержит операций изменения и удаления |

### 3.3. Отказ от ответственности (Repudiation)

| Угроза | Защита |
|---|---|
| Отрицание факта удаления писем | каждое действие реагирования фиксируется с автором, согласующими, областью и результатом |
| Отрицание доступа к переписке | просмотр письма и содержимого фиксируется отдельными событиями |
| Отрицание создания исключения | исключение имеет владельца, причину, срок и запись в аудите |
| Незаметное изменение правил | правила версионируются, изменение фиксируется, версия правила хранится в каждом сигнале |

### 3.4. Раскрытие информации (Information Disclosure)

| Угроза | Защита |
|---|---|
| Аналитик читает переписку без следа | каждый просмотр фиксируется |
| Администратор платформы читает переписку | Platform Admin по умолчанию не имеет такого права |
| Сотрудник видит чужой результат | объектная авторизация, ответ 404 |
| Утечка URL с токенами во внешний сервис | privacy gate: URL по умолчанию не отправляются, чувствительные параметры блокируются |
| Утечка корпоративных доменов наружу | блокируются policy gate |
| Секреты в логах | автоматическая очистка по именам полей в форматтере логов и в аудите |
| Секреты в ответах API | публичная конфигурация не содержит секретов, задание секретов через API отклоняется |
| Индикаторы в access-логах nginx | query string не логируется |
| Утечка внутренних деталей в сообщении об ошибке | 500 отдаёт только `request_id`; трассировка остаётся в логах |
| Раскрытие правил детектирования сотруднику | employee-проекция не содержит идентификаторов правил, весов и evidence |

### 3.5. Отказ в обслуживании (Denial of Service)

| Угроза | Защита |
|---|---|
| Zip-бомба | сверка реального размера распаковки, лимиты на файл, объём, количество, коэффициент сжатия |
| Бомба вложенности архивов | ограничение глубины |
| Гигантское или глубоко вложенное MIME | лимиты размера, глубины, числа частей и вложений |
| Письмо с десятками тысяч URL | ограничение числа извлекаемых URL |
| Медленный внешний провайдер блокирует анализ | отдельная очередь, таймаут, circuit breaker |
| Исчерпание квоты провайдера одним письмом | ограничение числа индикаторов на тип и rate limiting |
| Наплыв обращений сотрудников | rate limit на пользователя, очереди с backpressure |
| Переполнение хранилища | retention с автоматической очисткой и отдельной политикой для вредоносных образцов |
| Регулярные выражения с катастрофическим возвратом | шаблоны BEC имеют ограниченные квантификаторы `{0,N}` вместо `.*` |

### 3.6. Повышение привилегий (Elevation of Privilege)

| Угроза | Защита |
|---|---|
| Аналитик выполняет реагирование сам | право выполнения только у Security Admin |
| Администратор удаляет письма без контроля | второй согласующий при массовых операциях, запрет самоутверждения |
| Компрометация платформы приводит к правам в Exchange | remediation-аккаунт по умолчанию отключён, права ограничены |
| Компрометация платформы приводит к изменению AD | AD только для чтения, операций записи в коде нет |
| Выход из контейнера | непривилегированный пользователь, минимальный образ, отсутствие лишних прав |
| Доступ к БД из сети пользователей | БД, Redis и хранилище в сети `internal: true` |

## 4. Специфические угрозы предметной области

### 4.1. Ложное «безопасно» как главный риск

Самая опасная ошибка платформы — не пропуск атаки, а **создание ложной уверенности**. Сотрудник,
увидевший «безопасно», теряет обычную осторожность.

Защита заложена в модель данных: уровня `SAFE` не существует. Минимальный вердикт — `LOW_RISK`
с явной формулировкой «признаков атаки не обнаружено, это не гарантирует безопасность».
При неполных данных возвращается `UNKNOWN`. Недоступность провайдера, шифрование содержимого,
превышение лимитов парсера и неподдерживаемый формат всегда попадают в `missing_evidence`.

### 4.2. Атака на сам детект

Атакующий может изучать вердикты, чтобы подобрать обход.

| Приём | Защита |
|---|---|
| Изучение правил через ответы платформы | сотруднику не показываются идентификаторы правил и evidence |
| Обход одного детектора | вердикт строится на совокупности; hard-signals независимы |
| Массовая отправка для калибровки | корреляция кампаний, история отправителя, rate limiting |
| Использование легитимного сервиса как посредника | `NO_NEGATIVE_REPUTATION` не понижает риск; проверяется совпадение имени с защищаемыми идентичностями |

### 4.3. Злоупотребление исключениями

Исключение — это официально разрешённый обход детекта, поэтому это привилегированная операция.

Защита: обязательные владелец и причина, срок действия с проверкой «в будущем», запись в аудит
при создании и отзыве, счётчик срабатываний, уведомление владельца об истечении, отображение
подавленных сигналов в карточке письма (аналитик видит, что именно было подавлено).

### 4.4. Компрометация аналитика

Учётная запись аналитика даёт доступ ко всей переписке.

Защита: короткие сессии (30 минут для привилегированных ролей), простой 20 минут, MFA для
привилегированных роле́й при подключённом IdP, аудит каждого просмотра, немедленный отзыв всех
сессий, разделение прав просмотра и выполнения реагирования.

### 4.5. Вредоносный контент против аналитика

Аналитик открывает письма атакующих в своём браузере.

Защита: двойная санитизация (при приёме и при отдаче), sandbox-iframe без скриптов и без
`same-origin`, собственный CSP `default-src 'none'` внутри iframe, отсутствие кликабельных
ссылок, вложения только как `application/octet-stream` с `nosniff` и `CSP: sandbox`, имя файла
заменяется хешем, опасные типы требуют отдельного подтверждения.

## 5. Принятые остаточные риски

| Риск | Почему принят | Компенсация |
|---|---|---|
| 7z и RAR не разбираются статически | нет безопасной in-process библиотеки в v1 | помечаются как непроверенные, попадают в `missing_evidence` |
| Запароленный архив невозможно проверить | таково свойство шифрования | отдельный сигнал и запись в `missing_evidence`, но не автоматический вердикт «вредоносно» |
| Локальный сканер — не enterprise-защита | ClamAV один не эквивалентен полноценной AV-защите | явно документировано, недоступность сканера не даёт «чисто» |
| Отсутствие динамического анализа | вне области v1 | предусмотрен интерфейс `SandboxProvider`, статических сигналов достаточно для триажа |
| BEC-детект основан на шаблонах | ML вне области v1 | двуязычные шаблоны, комбинация с фактами идентичности; опциональный семантический провайдер |
| Один узел в пилоте | допустимо по §34 | требования HA зафиксированы для inline-режима |
| Возможны ложные срабатывания | неизбежно для эвристик | объяснимость каждого вердикта, механизм исключений с аудитом, метрика ложных срабатываний |

### Новые угрозы и меры

| # | Угроза | Мера | Проверка |
|---|---|---|---|
| T-30 | Отправитель добавляет заголовки шлюза, чтобы письмо выглядело проверенным | Заголовок учитывается только при подтверждении цепочкой `Received`; неподтверждённый — сам по себе сигнал | `TestSpoofedGatewayHeader` |

| T-35 | Принуждение к вердикту `MALICIOUS` подделанным обнаружением — перегрузка очереди аналитика | Жёсткий сигнал требует **доверенного** обнаружения | `test_forged_detection_cannot_force_a_malicious_verdict` |
| T-36 | SSRF через адаптер API шлюза | Путь присоединяется к базовому URL и перепроверяется; редиректы не выполняются; loopback отклоняется | `TestGatewayApi` |
| T-37 | Потеря сообщения при падении worker | Подтверждение ящику — последняя операция, после фиксации транзакции | `TestCrashPoints`, 5 точек падения |
| T-38 | Обход анализа письмом чрезмерного размера | Письмо сверх лимита не анализируется и не усекается; вердикт `UNKNOWN` | `TestOversizedMessages` |
| T-39 | Обход анализа многоуровневым архивом или множеством ссылок | Каждый лимит даёт отдельный сигнал и запись в `missing_evidence` | `TestParserLimitSignals` |
| T-40 | Доступ к данным другой организации через реестр шлюзов | Реестр и evidence привязаны к `organization_id` | `TestCrossOrganisationIsolation` |

### Что остаётся вне модели

* **Скомпрометированный шлюз.** Его вердикты подтверждены и ложны. Поэтому вердикт шлюза —
  сигнал, а не замена собственного анализа.
* **Внутренний злоумышленник в цепочке доставки.** Контроль над сервером организации даёт
  возможность написать подтверждающий заголовок; дальше работают контроль доступа и аудит.
* **Неизвестный формат вердикта вендора.** Нераспознанный статус становится `UNKNOWN` —
  безопасное направление ошибки, но обновление шлюза стоит сопровождать проверкой метрики
  `msp_gateway_event_parse_errors_total`.

## Дополнения этапа MSP 1.0.3B

1.0.3B добавил вокруг движка контур управления — обратную связь, кандидатов, выпуски,
переоценку. Контур управления детектированием сам становится поверхностью атаки: кто может
влиять на правила, тот может решать, что платформа перестанет видеть.

| № | Угроза | Защита | Проверка |
|---|---|---|---|
| T-41 | Подавление сигнала через обратную связь: получатели массово помечают письма волны как «не фишинг» | Обратная связь измеряется, но не меняет правила и не создаёт исключений; здоровье правила ничего не выключает | `TestFeedbackIsNotAuthority` |
| T-42 | Выпуск правила в обход ревью автором изменения | Самосогласование критического изменения отклоняется; сравнение адресов нечувствительно к регистру и пробелам | `TestSelfApproval` |
| T-43 | Публикация аналитиком, у которого есть право править правила | `PUBLISH_RULES` и `REVIEW_RULES` не следуют из `EDIT_RULES` | `TestPermissionsAreNotImplied` |
| T-44 | Тихое удаление правила «как незначительное изменение» | Любое удаление считается критическим изменением и требует второго человека | `releases.CRITICAL_CATEGORIES`, §44.3 |
| T-45 | Исполнение кода через файл правила | Загрузчик отклоняет `!!python/...`; условия ограничены словарём фактов | `TestRuleFilesCannotRunCode` |
| T-46 | Правило-пустышка: условие ссылается на несуществующий факт и выглядит покрытием | Словарь фактов проверяется разбором AST правил в CI | `unknown_condition_keys`, задача `rule-safety` |
| T-47 | Разбор пикселей из недоверенного письма в основном воркере | Декодер QR — отдельный процесс, необязательный компонент, лимиты по времени, пикселям и байтам | `tests/unit/test_qr_decoding.py` |

T-52 попал в модель угроз не из рассуждения, а из дефекта: два эндпоинта качества корреляции
были недостижимы с 1.0.3, отвечали 404 и показывались в консоли пустой панелью. Пустая панель
читается как «нарушений нет». Это тот же класс, что и «отсутствие детекта как безопасность», —
просто в транспортном слое.
