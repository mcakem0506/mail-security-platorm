## 1. §4.1 Устойчивый приём из security mailbox

### Что изменилось

Было:

```text
FETCH → пометить \Seen → обработка
```

Стало:

```text
FETCH
  → запись о приёме            (платформа знает, что письмо существует)
  → сохранение содержимого     (содержимое переживает сбой)
  → создание задания анализа   (работа поставлена в очередь)
  → COMMIT
  → подтверждение / Processed  (только теперь сообщаем ящику)
```

Порядок и есть свойство. Сообщение, подтверждённое до фиксации транзакции, теряется при падении
worker; сообщение, зафиксированное до подтверждения, в худшем случае будет прочитано дважды — а
дедупликация делает это безвредным.

Подтверждение выполняется **вне транзакции** намеренно: перемещение по IMAP не может быть частью
транзакции БД, поэтому одно из двух неизбежно идёт вторым.

### Реализация

| Свойство | Как обеспечено |
|---|---|
| письмо не теряется при падении worker | запись о приёме фиксируется до подтверждения |
| `\Seen` не является подтверждением | выборка `UNDELETED`, чтение через `BODY.PEEK` |
| `Processed` / `Failed` | `ack()` / `fail()`, папки создаются при первом использовании |
| дедупликация | UID + Message-ID + SHA-256 содержимого |
| повторное сообщение не создаёт второй инцидент | дубликат связывается с оригиналом |
| идемпотентность | повторная выборка того же UID продолжает или подтверждает, не дублируя |
| счётчик попыток | `retry_count`, порог `MAX_INTAKE_RETRIES = 3` |
| dead-letter | состояние `DEAD_LETTER`, перемещение в `Failed` |
| метрики | `intake_success`, `intake_retry`, `intake_failed`, `duplicate_report`, `intake_backlog` |

Три ключа дедупликации нужны потому, что ни одного не достаточно: UID уникален только в пределах
одного поколения ящика (UIDVALIDITY), Message-ID может отсутствовать или быть подделан, а хеш
содержимого не различает двух сотрудников, сообщивших об одном письме, — и это должно дать один
инцидент, а не два.

### Проверка (критерий приёмки §4.1)

`tests/integration/test_durable_intake.py::TestCrashPoints` моделирует падение в пяти точках:

| # | Точка падения | Результат |
|---|---|---|
| 1 | после FETCH | письмо остаётся в ящике, будет получено снова |
| 2 | после сохранения содержимого | приём продолжается, второй записи не создаётся |
| 3 | после создания задания | второго задания не создаётся |
| 4 | до подтверждения | работа сохранена, подтверждение выполняется после фиксации |
| 5 | после подтверждения | повторная обработка не происходит |

Ни в одном сценарии сообщение не теряется.

## 2. §4.2 Крупные и усечённые сообщения

Анализ усечённого письма как полноценного **запрещён**. Письмо сверх лимита не загружается вовсе:
проверяется `RFC822.SIZE` до загрузки тела.

| Требование | Реализация |
|---|---|
| не выполнять `raw[:max_size]` с обычным анализом | размер проверяется до загрузки; содержимое не сохраняется |
| сохранить метаданные | запись о приёме с реальным размером |
| выставить `LIMIT_EXCEEDED` / `UNSCANNABLE` / `UNKNOWN` | `ScanCompleteness` на задании и результате |
| указать `missing_evidence` | каждый лимит добавляет запись |
| сохранить фактический размер | `IntakeRecord.size_bytes` |
| уведомить аналитика | уведомление `unscannable` |
| не показывать сотруднику «письмо проверено» | `employee_view` отдаёт `scan_completeness`; проверяется тестом |

### Отдельные настраиваемые лимиты

| Настройка | Сигнал |
|---|---|
| `MSP_LIMIT_MESSAGE_SIZE` | `LIM-001` |
| `MSP_LIMIT_ATTACHMENT_SIZE` | `LIM-002` |
| `MSP_LIMIT_ATTACHMENT_COUNT` | `LIM-003` |
| `MSP_LIMIT_DECOMPRESSED_TOTAL` / `_FILE`, `MSP_LIMIT_ARCHIVE_DEPTH` | `LIM-004` |
| `MSP_LIMIT_MIME_PARTS`, `MSP_LIMIT_MIME_DEPTH` | `LIM-005` |
| `MSP_LIMIT_URL_COUNT` | `LIM-006` |
| `MSP_LIMIT_PARSE_TIMEOUT_SECONDS` | `LIM-007` |

Каждое превышение — **отдельный объяснимый сигнал** и запись в `missing_evidence`, что не даёт
вердикту опуститься до `LOW_RISK`.

> При реализации обнаружена и исправлена ошибка того же класса: ограничение на число ссылок
> применялось молча — список усекался, и усечённый список был неотличим от короткого. Теперь
> количество считается до извлечения, и превышение даёт сигнал.

## 3. §4.3–4.4 Цепочка доверенных заголовков

Настройки `MSP_TRUSTED_GATEWAYS=ksmg` недостаточно: она говорит, какой шлюз используется, и
ничего не говорит о том, проходило ли через него конкретное письмо.

| Требование | Реализация |
|---|---|
| проверять цепочку `Received` | `msp_mail_gateway.received` — разбор без обращений к DNS |
| известные IP/имена шлюза | `TrustedMailHop.hostname`, `ip_networks` |
| последний внешний hop | `last_external_hop()` по `MSP_INTERNAL_MAIL_NETWORKS` |
| доверенный relay Exchange | `hop_type=exchange_edge` / `exchange_mailbox` |
| `authserv-id` | `TrustedMailHop.authserv_ids` |
| `Received-SPF` | разбирается как и прежде |
| заголовки шлюзов, KSMG, EOP, `X-Spam-*`, `X-Virus-*` | провайдеры `ksmg`, `eop`, `spamassassin`, `generic_av` |
| сущность `TrustedMailHop` | таблица `trusted_mail_hops`, CRUD в консоли |
| `X-KSMG-Antivirus-Status: Clean` учитывается только при подтверждённой цепочке | `decide_header_trust()` |
| отрицательный вердикт может повысить риск | `GW-001`, `GW-004` |
| `clean` / `not detected` / `passed` не снижают риск | `GatewayVerdictType.lowers_risk` всегда `False` |

### Допустимые способы подтверждения

| Способ | Достаточен сам по себе |
|---|---|
| следующая машина записала приём **от** узла (`from` / IP) | да |
| узел заявил о себе сам (`by`) | **нет** — нужно подтверждение соседом сверху |

Заявление узла о себе подделывается тривиально; заголовок соседней машины — нет, потому что эта
машина принадлежит организации. Проверяется тестом `test_a_hop_invented_below_the_real_chain`.

### §4.4 Authentication-Results

Читаются только заголовки подтверждённого сервера. Остальные разделяются:

* **untrusted** — сервер не объявлен организацией (пересылка, список рассылки). Результаты не
  читаются, и только.
* **forged** — заголовок называет **наш собственный** объявленный сервер, заявляет `pass`, а
  цепочка прохождение через него не подтверждает. Сигнал подделки `GW-013`.

Разделение обязательно: легитимное пересланное письмо выглядит как первый случай, и если считать
подделкой и его, платформа начнёт помечать значительную долю обычной почты.

> Эта ошибка была допущена в первой реализации и найдена валидацией на корпусе: обычная
> внутренняя переписка получала `HIGH_RISK`. Исправлено разделением категорий.

Подробно — [`GATEWAY_TRUST_MODEL.md`](GATEWAY_TRUST_MODEL.md).

## 4. §4.5 Ужесточение аутентификации EWS

| Требование | Реализация |
|---|---|
| порядок AUTO: Kerberos, NTLM | `MSP_EWS_AUTH_PREFERENCE=kerberos,ntlm` по умолчанию |
| `allow_basic_auth=false` | `MSP_EWS_ALLOW_BASIC_AUTH=false` |
| Basic только по явному включению | Basic отфильтровывается из порядка перебора, если не включён |
| только HTTPS | конфигурация отклоняет Basic с HTTP-endpoint |
| проверка TLS обязательна | конфигурация отклоняет Basic с отключённой проверкой |
| событие в аудите | подключение по Basic пишется на уровне WARNING |
| `/health/dependencies` показывает предупреждение | `basic_auth_in_use` держит состояние `degraded` |
| готовность degraded до отдельного согласования | блокер в `blockers()` и в проверке готовности |
| молчаливый откат к Basic запрещён | развёртывание, где настроен только Basic и он не включён, получает **пустой** список методов и явный отказ |

Последняя строка существенна: отказ лучше молчаливого понижения. Пустой список — это ошибка,
которую видно, а не пароль, ушедший по сети незаметно.

## 5. §4.6 Проверка совместимости среды

`scripts/probe_exchange.py` определяет endpoint, Autodiscover, доверие TLS, способы
аутентификации, версию и сборку Exchange, работу EWS, доступ к служебному ящику, доступ к ящику
пилота на чтение, поиск, получение MIME, вложения, **возможность** реагирования без её выполнения
и предпосылки надстройки.

Результат — JSON и Markdown, решение `READY` / `READY_WITH_WARNINGS` / `NOT_READY` с перечнем
блокеров. Код возврата позволяет использовать проверку как шаг регламента.

Проверка **ничего не меняет**. Реагирование проверяется как право доступа и не выполняется.

Подробно — [`EXCHANGE_PROBE_GUIDE.md`](EXCHANGE_PROBE_GUIDE.md).

## 6. §5 Интеграция с Active Directory

| Требование | Реализация |
|---|---|
| только LDAPS | конфигурация отклоняет LDAP без TLS |
| discovery через RootDSE | base DN определяется автоматически, если не задан |
| учётная запись каталога только на чтение | соединение `read_only=True`; операций записи в коде нет |
| аутентификация пользователя через bind | `ActiveDirectoryAuthenticator` |
| роли через группы AD | `MSP_AD_GROUP_ROLE_MAP` |
| локальная аварийная учётная запись | локальные учётные записи работают при недоступном каталоге; использование аудируется как break-glass |
| fail-closed при недоступности AD | обычные пользователи получают `503`, вход не выполняется |
| синхронизация защищаемых идентичностей | `MSP_AD_PROTECTED_GROUPS`: группа → категория[:класс риска][:vip] |

Хранимые атрибуты идентичности: `display_name`, `mail`, `aliases[]`, `department`, `title`,
`risk_class`, `protected`, `vip`.

Класс риска отделён от категории намеренно: рядовой сотрудник финансового отдела и финансовый
директор относятся к одной категории, но последствия подмены у них разные. Правило `SND-038`
взвешивает подмену критической идентичности отдельно.

Идентичность, выпавшая из групп, **отключается, а не удаляется**: история того, почему письмо
когда-то было признано подменой, должна оставаться читаемой. Идентичность, заведённая аналитиком
вручную, синхронизацией не перезаписывается.

| `npm audit` блокирует High/Critical | блокирующий шаг |
| gitleaks | задача `security-scan` |
| bandit medium/high | блокирующий шаг, `-ll` |
| поиск секретов | проверка отсутствия файлов секретов и `.env` в индексе |
| согласованность lock-файлов | `npm ci --dry-run`, разрешение зависимостей Python |

## 9. §8–§12 Пилот: что зависит от организации

Следующее **не может** быть подтверждено кодом и остаётся открытым до реального пилота:

| Пункт | Что требуется |
|---|---|
| подключение реального Exchange | сервисная учётная запись, доступ |
| подключение реального AD | учётная запись только на чтение, группы |
| TLS внутренней PKI | сертификаты либо экспорт самоподписанных |
| установка надстройки группе пилота | согласование и развёртывание |
| 14 дней наблюдения | время |
| метрики FP/TP на реальной почте | разбор аналитиком |
| отчёт о пилоте | [`PILOT_REPORT.md`](PILOT_REPORT.md) |

План — [`PILOT_PLAN.md`](PILOT_PLAN.md), критерии завершения — §8 того же документа.

## 10. Решение по этапу

Реализация §4–§7 завершена и покрыта автоматическими проверками. Валидация детектирования на
синтетическом корпусе выполняется в CI.

```text
Готовность кода:                       ✔ выполнено
Проверка на реальной среде:            ожидает пилота
Итоговое решение этапа 1.0.1:          определяется по PILOT_REPORT.md
```

Переход к MSP 1.0.2 по §39 требует решения `READY_FOR_CONTROLLED_ROLLOUT` либо явно утверждённого
`READY_WITH_WARNINGS` в отчёте о пилоте.

> Реализация 1.0.2 в репозитории уже присутствует — этого требовал объём работ, переданный
> одним заданием. Это **не** отменяет условие §39: запускать многошлюзовой пилот до получения
> результатов теневого пилота 1.0.1 нельзя. Что именно реализовано — в
> [`MSP_1_0_2_ACCEPTANCE.md`](MSP_1_0_2_ACCEPTANCE.md).
