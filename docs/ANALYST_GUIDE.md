# Руководство аналитика ИБ

Как читать вердикты платформы и не ошибаться в их интерпретации.

---

## 1. Главное о вердиктах

Платформа не выдаёт «оценку опасности» числом. Вердикт — это классификация плюс перечень причин,
источников и того, чего не хватило для полной проверки.

| Класс | Что означает | Чего **не** означает |
|---|---|---|
| `LOW_RISK` | известных признаков атаки не найдено | что письмо безопасно |
| `SUSPICIOUS` | есть настораживающие признаки | что это точно атака |
| `HIGH_RISK` | признаков много или они весомы | |
| `MALICIOUS` | есть подтверждённый признак (hard-signal) | |
| `UNKNOWN` | данных недостаточно для вывода | что письмо чистое |

**Уровня `SAFE` в платформе не существует.** Это сделано намеренно: отсутствие обнаружения
не является доказательством безопасности (§49.9).

### Всегда проверяйте `missing_evidence`

Если в вердикте есть записи о недостающих данных — вердикт неполный. Типичные причины:
содержимое зашифровано, внешний источник был недоступен, сработал лимит парсера, формат архива
не поддержан статическим разбором. Закрывать такое письмо как безвредное нельзя.

---

## 2. Как читать аутентификацию отправителя

Платформа использует результаты, записанные почтовой инфраструктурой, и **не вычисляет свой
SPF-вердикт постфактум** — без реального SMTP-конверта и адреса подключения такой результат был
бы обманчивым (§9.2).

| Наблюдение | Правильная интерпретация | Неправильная |
|---|---|---|
| `spf=pass` | отправитель имел право использовать конверт | «письмо безопасное» |
| `dkim=none` | подписи нет | «это фишинг» |
| `dmarc=fail` | домен не подтвердил право на From | «это точно атака» — бывает у плохо настроенных легитимных сервисов |
| Все три провалены одновременно | весомый признак подделки | |
| Заголовков нет вообще | проверок не было; это попадёт в `missing_evidence` | «проверки пройдены» |
| Внутренний домен и провал проверок | **сильный признак подделки внутреннего отправителя** | |

## 3. Сигналы детектирования

В карточке письма каждый сигнал показывает: идентификатор и версию правила, категорию, важность,
объяснение и доказательства.

### Hard-signals

Некоторые сигналы поднимают класс риска напрямую:

- известный вредоносный хеш вложения;
- подтверждённо вредоносный URL или домен;
- обнаружение локальным антивирусом;
- совпадение с подтверждённой активной кампанией;
- отправитель ранее подтверждён как вредоносный.

У каждого hard-signal сохраняются источник и время наблюдения — важно, потому что данные
провайдеров устаревают.

### Подавленные сигналы

Если в карточке есть раздел подавленных сигналов — значит, действует исключение. Там же указано,
какое именно. Проверяйте: исключение могло быть создано для другой ситуации.

### Категории правил

| Префикс | Область |
|---|---|
| `SND-` | целостность и идентичность отправителя, подмена, lookalike-домены |
| `URL-` | ссылки, домены, сбор учётных данных |
| `ATT-` | вложения, архивы, макросы |
| `BEC-` | финансовое мошенничество, социальная инженерия |
| `TI-` | внешние источники угроз, кампании |

Правила с флагом `internal` не показываются сотруднику — это слабые технические сигналы,
полезные аналитику, но сбивающие с толку пользователя.

## 4. Особенности отдельных проверок

### Lookalike-домены

Сравнение идёт по «скелету» строки: кириллические и греческие символы, похожие на латинские,
приводятся к общему виду, поэтому `аррӏе.com` и `apple.com` дают совпадение.

Признак омоглифов выставляется только при **смешении алфавитов**. Полностью кириллическое имя
или домен `сбербанк.рф` — нормальное явление и само по себе сигналом не является.

Для коротких доменных имён (менее 6 символов) сравнение по расстоянию редактирования
не применяется: одна замена в коротком имени — это обычное совпадение, а не typosquatting.

### Архивы

| Признак | Значение |
|---|---|
| `ENCRYPTED_ARCHIVE` | содержимое невозможно проверить; **не является** доказательством вредоносности |
| `ZIP_BOMB`, `EXCESSIVE_COMPRESSION_RATIO` | аномальные параметры распаковки |
| `PATH_TRAVERSAL`, `ABSOLUTE_PATH`, `SYMLINK` | архив пытается записать файлы вне каталога распаковки |
| `NESTED_ARCHIVE` | архив в архиве; часто используется для обхода проверок |
| `UNSUPPORTED_ARCHIVE_FORMAT` | 7z или RAR: статически не разобран, попадает в `missing_evidence` |

### Вложения

`EXTENSION_MISMATCH` — содержимое не соответствует расширению. `DOUBLE_EXTENSION` — например
`договор.pdf.exe`. `RTLO_FILENAME` — в имени файла управляющий символ смены направления текста,
который в интерфейсе визуально меняет расширение. `HTML_SMUGGLING_PATTERN` — HTML-вложение
собирает файл на стороне клиента.

### BEC

Признаки намерения (смена реквизитов, срочный платёж, запрос кода, просьба обойти согласование)
сами по себе имеют умеренный вес. Значимыми они становятся в сочетании с фактами идентичности:
подмена защищаемого лица, внешний отправитель без аутентификации, подменённый Reply-To.

Отдельно отмечается `payload_free_request` — письмо без вложений и ссылок с финансовым или
парольным запросом. Такие атаки не обнаруживаются антивирусной проверкой в принципе.

## 5. Порядок работы

Детальный порядок — в [INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md). Кратко:

1. прочитать причины, а не только класс;
2. проверить `missing_evidence`;
3. проверить подмену защищаемой идентичности;
4. проверить принадлежность к кампании — от этого зависит масштаб;
5. решение: подтвердить, признать ложным срабатыванием или продолжить расследование;
6. при подтверждении — предложить реагирование, проверить dry-run, получить согласование.

## 6. Чего платформа не делает

Понимание границ так же важно, как понимание возможностей.

| Не делает | Следствие для работы |
|---|---|
| Не фильтрует почту inline | опасное письмо уже доставлено; реагирование — по факту |
| Не открывает ссылки из писем | конечная страница неизвестна; редиректы не раскрываются |
| Не выполняет динамический анализ | поведение вложения неизвестно, только статические признаки |
| Не разбирает 7z и RAR | помечает как непроверенные (пробел GAP-003) |
| Не проверяет запароленные архивы | содержимое недоступно |
| Не заменяет корпоративный антивирус | локальный сканер — дополнительный сигнал |
| Не извлекает QR-коды из PDF-вложений | пробел GAP-004; текст письма про сканирование кода сигнал даёт |

Ссылки из office-документов и признаки HTML smuggling платформа извлекает с MSP 1.0.3, а
содержимое QR-кодов читает с MSP 1.0.3B — **если установлен необязательный компонент**. До
MSP 1.0.4 в таблице выше стояло обратное утверждение: оно устарело на полтора этапа и могло
стоить расследования, потому что аналитик из-за него не стал бы искать ссылку.

## 7. Исключения: как не навредить

Исключение отключает детект. Перед созданием проверьте, нет ли более точного решения:

| Ситуация | Лучше исключения |
|---|---|
| Отличается только Return-Path у легитимной рассылки | добавить домен в доверенную инфраструктуру |
| Внешний сервис легитимно пишет от имени руководителя | добавить его в разрешённые внешние системы этой идентичности |
| Делегированный помощник пишет от имени руководителя | добавить в разрешённых делегатов |
| Сработало одно конкретное правило | исключение с указанием `rule_id`, а не отправителя целиком |

Всегда указывайте срок. Бессрочное исключение — это постоянная дыра в детекте, о которой через
полгода никто не помнит.

## 8. Очередь, граф и связанный поиск

Подробно — [ANALYST_QUEUE.md](ANALYST_QUEUE.md). Что важно держать в голове:

**Приоритет — не уровень риска.** В очереди рядом стоят два числа, и они о разном: риск — про
письмо, приоритет — про последствия. Единственный получатель и обратимое последствие понижают
приоритет даже при высоком риске. В колонке «Почему именно так» видно, из чего сложился балл;
если непонятно — это повод спросить, а не повод доверять числу.

**Граф ограничен и честно об этом говорит.** Триста узлов и шестьсот связей — предел. При
достижении ответ помечен `truncated`, и это значит «связей больше, чем показано», а не «связей
больше нет». На массовой волне смотрите не граф, а кампанию.

**Связанный поиск взвешен.** Совпадение по хешу вложения или Message-ID — почти доказательство,
совпадение по теме — почти ничего (самый слабый из двенадцати признаков). Результаты
упорядочены по весу, а не по дате, именно чтобы эти утверждения не путались.

**Кампанию решает аналитик.** Корреляция предлагает, вы присоединяете или отклоняете, и оба
действия попадают в аудит. Доля отклонений выше нескольких процентов — сигнал не про вас, а про
настройку корреляции: сообщите инженеру детектирования.

## 9. Обратная связь: что с ней происходит

Подробно — [DETECTION_FEEDBACK.md](DETECTION_FEEDBACK.md).

Ваше решение **измеряется, но не меняет правила само**. Это сделано нарочно: правило, которое
подстраивается под обратную связь, подстраивается и под обратную связь, которую организовал
атакующий — достаточно нескольких писем, по которым получатели нажмут «не фишинг».

Что от вас требуется, помимо класса:

- **по каждому сигналу отдельно**: `CORRECT`, `INCORRECT` (признак определён неверно),
  `IRRELEVANT` (определён верно, но к делу не относится), `TOO_SEVERE` (верно, но вес завышен).
  `TOO_SEVERE` **не** портит точность правила — это задача на вес, а не заявление об ошибке.
  Не используйте его вместо `INCORRECT`, когда правило действительно ошиблось;
- **причина ложного срабатывания** — обязательна. Без неё запись невозможно адресовать:
  неизвестно, чинить правило, нормализацию или список доверенных отправителей. Форма откажет;
- **осуждённый сигнал** — тоже обязателен. «Вердикт неверен, но все сигналы верны» означает, что
  неверна агрегация, а это другой дефект и другой адресат.

Пропуск (письмо, которое платформа не поймала) требует больше: ожидаемая категория, минимальная
классификация, серьёзность, **владелец** и целевой выпуск. Без владельца запись не принимается —
пропуск без адресата это не задача, а напоминание о неприятности.

**Исключение вы не создаёте разметкой.** Клик «ложное срабатывание» не делает исключения, и это
не недоработка формы: исключение делает платформу слепой намеренно, и ему нужны владелец, срок
пересмотра и второй согласующий.

## 10. Что аналитик может сам, а что нет

| Действие | Аналитик | Почему так |
|---|---|---|
| Классифицировать инцидент, разметить сигналы | да | это ваша работа |
| Прогнать правило на сохранённом письме (симулятор) | да | прогон ничего не меняет |
| Править файл правила, предложить кандидата | да | предложение — не выпуск |
| **Согласовать** кандидата, **опубликовать** выпуск | нет | решает, чем защищена вся организация |
| Запустить канареечный выпуск | нет | то же решение, меньшего радиуса |
| Применить повторный анализ к вердикту | нет | переписывает запись о прошлом решении |
| Управлять массовой переоценкой истории | нет (видеть — да) | затрагивает десятки тысяч писем |
| Предложить реагирование | да | с обязательным dry-run |
| **Согласовать** реагирование | нет | второй человек на необратимом действии |

Отказ приходит с причиной, а не общим «нет прав». Если причина кажется неверной — это повод
обратиться к администратору, а не искать обход.

## 11. Симулятор, повтор и переоценка

Три похожих инструмента, которые отвечают на разные вопросы:

| Инструмент | Вопрос | Что меняет |
|---|---|---|
| **Симулятор** ([RULE_SIMULATOR.md](RULE_SIMULATOR.md)) | сработает ли правило на этом письме | ничего |
| **Повтор анализа** ([REPLAY_ANALYSIS.md](REPLAY_ANALYSIS.md)) | что решила бы платформа сегодня | добавляет ревизию, вердикт оставляет |
| **Переоценка истории** ([HISTORICAL_REEVALUATION.md](HISTORICAL_REEVALUATION.md)) | что мы уже пропустили | ничего при пробном прогоне; реагирования не делает никогда |

Если исходное письмо удалено по политике хранения, симулятор и повтор отвечают отказом с прямой
причиной, а не пустым результатом. Пустой результат читался бы как «правило не сработало» — то
есть как знание, которого прогон не дал.

Правка, проверенная симулятором на том письме, из-за которого её сделали, проверена ровно на
нём. Дальше — прогон по золотому корпусу, и только потом ревью.

## 12. Короткие похожие домены: новый условный сигнал

С MSP 1.0.4 платформа замечает домены, отличающиеся от короткого домена организации **одной
правкой** — вставкой, удалением, заменой символа или перестановкой двух соседних. Это закрывает
пробел GAP-001, но сигнал устроен иначе, чем остальные:

- **с подкреплением** (SND-024) — учитывается в вердикте. Подкреплением считается второй
  независимый признак: провал аутентификации, заявленный проход DKIM без подписи, несовпадение
  Reply-To, запрос платежа или реквизитов, запрос учётных данных, отрицательный вердикт шлюза и
  ещё несколько;
- **без подкрепления** (SND-025) — показывается с **нулевым весом** и на вердикт не влияет.

Увидев SND-025, не считайте письмо подозрительным только из-за домена: на четырёхбуквенной метке
одна правка — это ещё и «core», «carp», «corps», и у каждого из них есть настоящий владелец. На
золотом корпусе этот сигнал встречается у 92 легитимных писем из 241.

Обратное тоже верно: SND-025 — хорошая причина посмотреть на письмо внимательнее, чем обычно,
особенно если речь о деньгах.

## 13. Реальный поток: разбор настоящей почты

`Детектирование → Реальный поток`. Это набор писем организации, собранный для одной цели:
измерить, как детектирование ведёт себя на настоящей почте. Золотой корпус на этот вопрос не
отвечает — он содержит ровно те случаи, которые мы придумали.

### Чего в наборе нет

Ни темы, ни текста письма. Для измерения они не нужны, а список открывает всякий, кто смотрит
метрики. Если нужно содержимое — письмо открывается обычным путём, через расследование, и
просмотр фиксируется в аудите.

### Почему письмо попало в выборку

Причин может быть несколько сразу, и они перечислены:

| Причина | Что это значит для вас |
|---|---|
| высокий риск, вредоносное | решение платформы здесь дороже всего; разбирайте первым |
| обращение сотрудника | человек увидел то, чего не увидела платформа, или наоборот |
| расхождение со шлюзом | платформа и шлюз не согласны; кто-то из двух ошибается |
| QR-код | GAP-002 на подтверждении: нужен живой материал |
| правило-кандидат | кандидат измеряется до включения |
| проверено не до конца | есть пробел, а не вердикт |
| случайная доля легитимной почты | 2% обычных писем; ищем то, чего никто не заметил |

Последняя строка — самая полезная и самая скучная. Ложные срабатывания, которых никто не
заметил, иначе не попадут в набор никогда: в него попадает то, на что обратили внимание.

### Ваш разбор — единственная истина здесь

Пока письмо не разобрано, оно не «верное». Точность на реальном потоке показывается как «—»
ровно потому, что знаменателя нет: ноль читался бы как «платформа всегда ошибается».

Классификации те же, что в обычной работе, и спам по-прежнему стоит отдельно: отметить спам —
не ошибка платформы, но и не обнаруженная атака.

Ваш разбор **ничего не продвигает** и не меняет правила. Он фиксирует факт. Всё остальное —
отдельные решения отдельных людей.

### Очередь неопределённых писем

Отдельная от обычной, а не фильтр для удобства. По такому письму нет вердикта, который можно
подтвердить или опровергнуть: шифрование, пароль на архиве, нераспознанный QR-код. Есть пробел.

Решение здесь принимается по контексту отправителя, а не по разбору содержимого, которого нет.
Если такие письма накапливаются систематически — это повод не для разбора по одному, а для
разговора о том, чего не хватает: формата, компонента, лимита.

### Нагрузка правил: как читать

Числа даны на тысячу писем, а не в штуках: абсолютное число срабатываний растёт вместе с
объёмом почты и о правиле молчит.

Смотрите колонку «разных писем». Правило, сработавшее сто раз на одном письме, скорее всего
видит одну рассылку; правило, сработавшее сто раз на ста разных — системную особенность потока.
Это разные задачи.

Платформа не выставляет `PRODUCTION_NOISY` сама. Вывод «правило шумит» делает человек, глядя на
эти числа, — и правило, впервые столкнувшееся с новой кампанией, не должно выключать себя в
самый неподходящий момент.

### Если нашли пропуск

Не «подкручивайте порог». Пропуск, закрытый повышением чувствительности правила, обменивает один
вид ошибки на другой, и обмен делается глазами: цена ложного срабатывания в разрыве потока —
недоставленное письмо. Заведите пробел в реестре; это и есть способ сказать «мы про это знаем».

## 14. Показатели, за которыми стоит следить

| Показатель | О чём говорит рост |
|---|---|
| Доля ложных срабатываний | пороги или правила требуют настройки |
| Время до триажа | не хватает ресурсов либо слишком много шума |
| Число обращений сотрудников | обычно хорошо: люди вовлечены |
| **Падение** обращений при росте детектов | возможная потеря доверия к платформе — стоит разобраться |
| Ошибки провайдеров | проблемы с внешними источниками; вердикты становятся менее полными |
| Размер кампаний | масштаб атак на организацию |
