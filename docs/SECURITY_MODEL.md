# Модель безопасности

Платформа обрабатывает недоверенный контент (письма атакующих) и хранит чувствительные данные
(переписка сотрудников). Документ описывает, как это разграничено. Соответствует §23–§25, §28–§30.

---

## 1. Принципы

1. **Недоверенный вход не получает привилегий.** Письмо разбирается в компоненте без исходящего
   сетевого доступа, ничего не исполняется, все операции ограничены по времени и объёму.
2. **Least privilege на всех уровнях.** Отдельные сервисные аккаунты, отдельные роли, отдельные
   сети, непривилегированный пользователь в контейнере, read-only доступ к AD.
3. **Доступ к содержимому писем — отдельное право.** Администрирование платформы и чтение
   переписки разделены.
4. **Каждое действие с данными оставляет след.** Аудит неизменяем, без секретов и без тел писем.
5. **Опасное действие требует подтверждения.** Реагирование — только через dry-run и согласование.

## 3. Авторизация объектного уровня (§30)

Прав роли недостаточно — проверяется также право на конкретный объект.

Сотрудник видит только свои проверки. Если он запрашивает чужое задание, возвращается
**404, а не 403**: иначе сам код ответа подтверждал бы существование чужой проверки.

```text
can_access_job(role, actor, job):
    если роль видит все расследования  → разрешить
    если нет права на свои результаты  → отказать
    если владелец задания == actor     → разрешить
    если ящик actor == ящик задания    → разрешить
    иначе                              → отказать (404)
```

Все объекты дополнительно ограничены `organization_id` актора.

## 4. Аутентификация (§24)

| Механизм | Реализация |
|---|---|
| Хеширование пароля | Argon2id, `time_cost=3`, `memory_cost=64 MiB`, `parallelism=2` |
| Минимальная длина | 12 символов; пароля по умолчанию не существует |
| Сессии | серверные, в Redis, с подписью HMAC-SHA256 идентификатора в cookie |
| Cookie | `HttpOnly`, `SameSite=Strict`, `Secure`, без доступа из JS |
| Срок сессии | 60 мин обычная, **30 мин для привилегированных ролей**, простой 20 мин |
| CSRF | double-submit token, сравнение в постоянное время, обязателен для всех небезопасных методов |
| Блокировка | 5 неудач → блокировка 15 мин, далее экспоненциально до 24 ч |
| Перечисление учётных записей | невозможно: неизвестный пользователь и неверный пароль дают идентичный ответ |
| Смена пароля | отзывает все остальные сессии этого пользователя |
| Отзыв сессии | немедленный, по идентификатору или для всех сессий пользователя |

Приоритет источника аутентификации — корпоративный AD/LDAP или существующий IdP; локальная
аутентификация предназначена для первичной настройки и аварийного доступа.

Подпись идентификатора сессии проверяется **до** обращения к Redis, поэтому подделанные
идентификаторы не создают нагрузку на хранилище.

## 5. Обработка недоверенного контента

| Угроза | Защита |
|---|---|
| XSS через тело письма | санитизация `nh3` по allowlist при приёме **и** повторно при отдаче; просмотр в sandbox-iframe без `allow-scripts` и `allow-same-origin`, с собственным CSP `default-src 'none'` |
| Переход по вредоносной ссылке из консоли | ссылки в просмотре физически не кликабельны: атрибут `href` удаляется санитайзером, URL выводятся отдельным копируемым списком |
| Загрузка внешних ресурсов (трекеры) | удаляются все `src`, `style`, `url()`; в iframe `img-src data:` |
| Zip-бомба | сверяется **реальный** размер распаковки, а не заявленный в заголовке; лимиты на файл, суммарный объём, количество и коэффициент сжатия |
| Path traversal в архиве | имена нормализуются, `..`, абсолютные пути и symlink помечаются и не распаковываются |
| Бесконечная вложенность | ограничение глубины архивов и глубины MIME |
| Исчерпание ресурсов парсером | лимиты размера, числа частей, вложений, URL и кооперативный таймаут |
| Trojan Source в именах файлов | bidi-символы обнаруживаются и удаляются при нормализации имени |
| Исполнение вложения | не происходит: анализ только статический, содержимое никогда не передаётся ОС для открытия |
| Опасное вложение в браузер аналитика | отдаётся как `application/octet-stream` с `nosniff`, `Content-Disposition: attachment`, `CSP: sandbox`, имя заменяется на хеш; опасные типы требуют отдельного подтверждения |
| SSRF через URL из письма | URL не запрашиваются; включение резолвинга требует отдельной egress-зоны и явной настройки |
| Billion laughs / XML | XML-парсеры для контента писем не используются |

Проверено тестами: парсер не открывает сокет ни на одной фикстуре корпуса, разбор доменов
не выполняет DNS-запросов.

## 6. Защита данных при обращении к внешним сервисам (§2.4, §14.4)

Каждый запрос наружу проходит policy gate **до** отправки:

| Тип индикатора | По умолчанию | Примечание |
|---|:--:|---|
| SHA-256 вложения | разрешён | не раскрывает содержимое |
| Домен | разрешён | кроме корпоративных доменов |
| IP-адрес | разрешён | |
| URL | **запрещён** | часто содержит токены и идентификаторы получателя |
| URL с путём/query | **запрещён** | дополнительно к запрету URL |
| Адрес отправителя | **запрещён** | |
| Корпоративные домены | **запрещён** | раскрывает внутреннюю структуру |
| Файл целиком | **запрещён** | только через Private Scanning после отдельного согласования |

Дополнительно блокируются URL, содержащие адрес электронной почты или параметры с именами
вида `token`, `session`, `code`, `email`, `user` и подобными.

Блокировка политикой возвращает статус `POLICY_BLOCKED` — он **не равен** «чисто» и не понижает
риск.

## 7. Управление секретами (§28)

| Запрещено | Как сделано вместо этого |
|---|---|
| Секреты в Git | `.gitignore` на каталоге секретов и `.env`; проверка в CI |
| Секреты во фронтенде | `/api/v1/auth/config` отдаёт только несекретные значения; проверено тестом |
| Ключ VirusTotal в add-in | add-in не содержит ключей, работает через сессию пользователя |
| Пароль AD в открытом конфиге | только через `*_FILE` из Docker secrets или Vault |
| Задание секретов через API | эндпоинт провайдеров отклоняет поля с секретами (400) |

Ротация: замена файла секрета и перезапуск сервиса. Ротация `msp_secret_key` инвалидирует все
сессии — это ожидаемое поведение.

## 8. Аудит (§25)

Фиксируется: вход и выход, неудачный вход, отзыв сессии, смена пароля, просмотр письма, просмотр
содержимого, доступ к вложению и скачивание, постановка анализа, сообщение о фишинге, изменение
правил, создание и отзыв исключений, изменение защищаемых идентичностей, изменение конфигурации
провайдеров и политик, создание и смена статуса инцидента, предложение, согласование, отклонение,
выполнение и отказ реагирования, экспорт, изменение пользователей, синхронизация AD, retention.

Не записывается: секреты, токены, cookie, полные тела писем. Очистка выполняется автоматически
по именам полей, даже если вызывающий код передал лишнее.

Модуль аудита не предоставляет операций изменения и удаления — только добавление.

## 9. Ограничения и лимиты (§30)

| Лимит | Значение |
|---|---|
| Размер тела запроса | 30 МБ (nginx) и 26 МБ (приложение) |
| Вход | 1 запрос/с (nginx) и 10/мин на IP и на учётную запись (приложение) |
| Постановка анализа | 30/мин на пользователя |
| Прочий API | 20 запросов/с (nginx), 300/мин (приложение) |
| Одновременных соединений | 32 на IP |
| Идемпотентность | для постановки анализа и для реагирования |
| Валидация | строгая, неизвестные поля отклоняются (`extra="forbid"`) |

Rate limiting работает через Redis, а при его недоступности — в процессе: отказ Redis не снимает
ограничения.

## 10. Заголовки безопасности

Для консоли:

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-src 'none';
  frame-ancestors 'none'; form-action 'self'; base-uri 'none'; object-src 'none'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()
```

Для add-in: `X-Frame-Options` не выставляется, поскольку панель встраивает Outlook. Вместо него
допустимые источники встраивания ограничены через `frame-ancestors` в CSP.

Важно: в nginx `add_header` в блоке `location` **отменяет** заголовки уровня `server`, поэтому
общий набор подключается через `security_headers.conf` в каждом location, где задаются
собственные заголовки.

## 11. Реагирование (§20, §49.10)

```text
Analyst предлагает
   │  автоматически считается dry-run: сколько писем, какие ящики,
   │  возможен ли откат, предупреждения
   ▼
Security Admin согласовывает
   │  автор предложения не может согласовать сам
   │  > порога ящиков (по умолчанию 10) — нужен второй согласующий
   ▼
Security Admin выполняет
   │  требуется явное confirm=true
   │  в режиме dry-run-only выполнение отклоняется независимо от согласований
   ▼
Аудит + токен откатa (для карантина)
```

По умолчанию `MSP_REMEDIATION_ENABLED=false` и `MSP_REMEDIATION_DRY_RUN_ONLY=true`: платформа
может **предложить и согласовать** действие, но не выполнить его, пока это не разрешено явно.

## 12. Проверенные утверждения

Каждое утверждение ниже подтверждено тестом в `tests/security/`:

- незащищённый доступ к API невозможен (401 на всех защищённых эндпоинтах);
- сотрудник не получает чужой результат анализа (404);
- сотрудник не может отправить письмо от имени другого ящика (403);
- Platform Admin не имеет доступа к расследованиям (403);
- аналитик не может согласовать реагирование (403);
- автор предложения не может согласовать его сам (403);
- запрос без корректного CSRF-токена отклоняется (403);
- перебор паролей приводит к блокировке (429);
- неизвестный пользователь и неверный пароль дают одинаковый ответ;
- фильтры поиска не подвержены инъекциям;
- секреты нельзя задать через API провайдеров (400);
- в публичной конфигурации нет секретов;
- readiness не зависит от VirusTotal;
- 12 вариантов XSS не проходят санитизацию;
- traversal в ключе хранилища невозможен;
- в модуле AD отсутствуют операции записи.

## Дополнения этапов MSP 1.0.1 и 1.0.2

### Доверие к внешним источникам

Появление интеграции со шлюзом добавляет три канала данных, и у каждого своя проблема
происхождения:

| Канал | Кто может в него писать | Доказательство подлинности |
|---|---|---|
| заголовки письма | **отправитель** | цепочка `Received` |
| syslog | всё, что видит порт | список адресов, TLS-сертификат клиента |
| API вендора | владелец адреса | TLS с проверкой, фиксированный базовый URL |

Общее у них одно: **ни один не может понизить вердикт платформы**. Закреплено типом
`GatewayVerdictType.lowers_risk`, который всегда возвращает `False`, и проверяется тестом,
перебирающим все значения перечисления.

Подробно — [GATEWAY_TRUST_MODEL.md](GATEWAY_TRUST_MODEL.md) и
[MULTI_GATEWAY_SECURITY_MODEL.md](MULTI_GATEWAY_SECURITY_MODEL.md).

### Аутентификация EWS

Basic-аутентификация передаёт пароль служебной учётной записи при каждом запросе. Поэтому:

* она отсутствует в порядке перебора по умолчанию;
* молчаливый откат к ней невозможен — метод отфильтровывается, если не разрешён явно;
* при включении обязательны HTTPS и проверка TLS;
* подключение по Basic пишется в журнал и держит готовность в состоянии `degraded`.

### Break-glass

При `MSP_AUTH_BACKEND=ldap` локальные учётные записи продолжают работать: иначе недоступность
каталога заблокировала бы службе ИБ доступ к собственной консоли. Каждый такой вход
записывается как break-glass-событие. Ожидаемые аварийные учётные записи перечисляются в
`MSP_EMERGENCY_LOCAL_ACCOUNTS` — это не ограничение, а признак ожидаемости.

Обычные пользователи при недоступном каталоге получают отказ (`503`): fail-closed.

### Секреты в конфигурации шлюза

Поля с именами `password`, `secret`, `token`, `api_key`, `credential`, `key` в настройках шлюза
**отклоняются с объяснением**, а не отбрасываются молча: иначе администратор считал бы, что ключ
сохранён. Доступ к API настраивается ссылкой на хранилище секретов (`secret_ref`).

### Неполный анализ

Письмо, которое не удалось разобрать целиком, не может получить вердикт `LOW_RISK`: каждое
превышение лимита добавляет запись в `missing_evidence`, а `ScanCompleteness` доходит до
представления для сотрудника. Формулировки, читающиеся как «письмо проверено», в этом состоянии
не показываются — это проверяется тестом.

## Дополнения этапа MSP 1.0.3B

### Права не выдаются по смежности

| Право | Аналитик | Администратор ИБ |
|---|---|---|
| `CLASSIFY_INCIDENT`, `SIMULATE_DETECTION`, `EDIT_RULES` | да | да |
| `REVIEW_RULES`, `PUBLISH_RULES` | **нет** | да |
| `MANAGE_CANARY`, `EXECUTE_REPLAY` | **нет** | да |
| детальное качество детектирования | да | да |
| что-либо из перечисленного для сотрудника | **нет** | — |

Аналитик предлагает и симулирует, но не выпускает. Публикация решает, чем защищена вся
организация; право её выполнить не следует из права править файл правила.

### Четыре глаза и самосогласование

Автор критического изменения не может его одобрить. Критическим считается изменение жёсткого
правила, правила категории `malware`, `credential_theft`, `impersonation`, `payment_fraud` —
и **любое удаление правила**: удалённое правило не шумит, поэтому его отсутствие никто не
заметит.

Сравнение адресов идёт по нижнему регистру с обрезанными пробелами. Проверка, которую обходит
заглавная буква, не является проверкой — это отдельный тест.

То же правило действует для исключений: автор исключения не может его согласовать.

### Обратная связь не является полномочием

Разметка письма как ложного срабатывания **не создаёт исключение**. Исключение делает платформу
слепой намеренно, и ему нужны владелец, срок пересмотра и второй согласующий. Если бы клик
«ложное срабатывание» создавал исключение, достаточно было бы нескольких писем, по которым
получатели нажмут «не фишинг», чтобы погасить сигнал — то есть обратная связь стала бы входом
для атакующего.

По той же причине здоровье правила ничего не выключает: `NOISY` — повод для правки, а не
команда. Контроль, отключающий себя при странных данных, выключается неудачной неделей или тем,
кто эту неделю устроит.

### Файл правила не может исполнить код

Загрузчик отклоняет YAML с тегами `!!python/...` и `!!binary` — проверяется не только тем, что
в пакете их нет, но и тем, что загрузчик на них падает. Условие правила может называть только
факты из словаря движка: правило, ссылающееся на несуществующий факт, никогда не сработает и
при этом будет выглядеть покрытием на каждой карте.

### Массовая переоценка не реагирует

Задание переоценки не рассылает уведомлений, не создаёт действий реагирования и не открывает
инцидентов — ни в пробном прогоне, ни без него. Проверяется разбором синтаксического дерева
модуля (импорты и вызовы), а не поиском по тексту: первая версия этой проверки совпала с
собственным комментарием модуля, обещавшим именно это.

Прогон по семи дням истории затрагивает десятки тысяч писем. Массовое реагирование по его
результату — это сценарий, где одна ошибка в правиле удаляет почту организации.

### Граф и поиск ограничены

`MAX_NODES = 300`, `MAX_EDGES = 600`; при достижении границы ответ помечен `truncated`. Запрос
без границы — это и отказ в обслуживании базе, и обрезанный граф, выданный за полный.
