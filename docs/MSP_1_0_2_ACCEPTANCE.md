## 1. §14 Контракт `MailGatewayProvider`

Пакет `providers/mail-gateway/` создан. Protocol реализован полностью:

```python
class MailGatewayProvider(Protocol):
    provider_id: str
    def health() -> ProviderHealth: ...
    def capabilities() -> set[GatewayCapability]: ...
    def parse_message_headers(...) -> list[GatewayEvidence]: ...
    def get_message_trace(...) -> MessageTrace | None: ...
    def get_verdict(...) -> GatewayEvidence | None: ...
    def get_quarantine_status(...) -> QuarantineStatus | None: ...
    def search_related(...) -> list[GatewayMessageRef]: ...
    def propose_quarantine(...) -> GatewayActionPlan: ...
    def execute_quarantine(...) -> GatewayActionResult: ...
    def release_message(...) -> GatewayActionResult: ...
    def block_sender(...) -> GatewayActionResult: ...
```

Реализовывать всё не требуется. `BaseGatewayProvider` отказывает честно: метод, который не
реализован, возвращает план с перечнем блокеров, а не результат об успехе.

## 2. §15 `GatewayCapability`

Все 15 значений определены. Возможности **проверяются**, а не выводятся из названия продукта;
результат хранится в `gateway_capability_states` с отметкой времени.

Capability probing доступен и backend, и UI: `GET /api/v1/gateways/capabilities`.

Возможность, которая исчезла, записывается как недоступная, а не удаляется: её потеря —
эксплуатационное событие, которое стоит видеть.

---

## 3. §16 Нормализованная модель evidence

`GatewayEvidence` содержит все поля ТЗ: `provider_id`, `provider_type`, `message_id`,
`timestamp`, `verdict`, `category`, `confidence`, `score`, `threat_name`, `engine`, `policy`,
`source`, `trusted`, `trust_reason`, `raw_reference`, `normalized_detail`.

Дополнительно введено `trust_state` — четыре различимых причины недоверия, потому что «не
доверяем» и «это подделка» требуют разной реакции аналитика.

`raw_reference` — указатель (имя заголовка, идентификатор syslog, request id), а не полный ответ
вендора: иначе появилась бы вторая копия содержимого письма под другой политикой хранения.

---

## 4. §17 Семантика вердиктов

Семь значений: `MALICIOUS`, `PHISHING`, `SPAM`, `SUSPICIOUS`, `CLEAN_OBSERVED`, `UNKNOWN`,
`ERROR`.

`CLEAN_OBSERVED != SAFE` закреплено в типе, а не в комментарии:

```python
@property
def lowers_risk(self) -> bool:
    return False
```

Проверяется тестом `test_no_verdict_type_lowers_risk`, перебирающим все значения перечисления.
Вердикт шлюза может повысить риск, добавить evidence и повлиять на confidence — и не может
понизить собственный вердикт MSP ни при каком уровне доверия.

## 5. §18 Адаптер KSMG

Production-grade разбор заголовков: `X-KSMG-*` в трёх движках (антивирус, антиспам, антифишинг),
имя угрозы, оценка, метаданные политики. Набор заголовков читается тот, что присутствует, — он
различается между версиями KSMG.

Доверие только при подтверждённых узле, цепочке `Received`, сети источника и соответствии
топологии.

Нераспознанный статус даёт `UNKNOWN`, а не `CLEAN_OBSERVED`: вердикт, который не удалось
прочитать, не сказал, что письмо в порядке.

API KSMG, если конкретная конфигурация его предоставляет, выносится в отдельный адаптер на базе
`api_base` и не смешивается с разбором заголовков — иначе доверие к заголовкам стало бы зависеть
от доступности API. На этапе 1.0.2 не реализован.

Подробно — [`KSMG_INTEGRATION.md`](KSMG_INTEGRATION.md).

## 6. §19 Настраиваемый провайдер заголовков

`generic_header` управляется конфигурацией: отображение заголовков на вердикт, оценку, имя
угрозы и политику, плюс необязательный `verdict_map`. Формат ТЗ поддержан, включая сокращённую
запись доверенных узлов одной строкой.

Профили загружаются из каталога `*.yaml` либо задаются через API. Новый шлюз не требует кода.

Подробно — [`GENERIC_GATEWAY_INTEGRATION.md`](GENERIC_GATEWAY_INTEGRATION.md).

## 7. §20 Провайдер syslog

| Требование | Реализация |
|---|---|
| UDP / TCP / TLS, приоритет TCP и TLS | `SyslogListener`; UDP отклоняется в production |
| список разрешённых источников | обязателен; пустой = не принимается ничего |
| идентичность клиента по TLS | клиентский сертификат, где шлюз поддерживает |
| разбор | RFC 5424 и RFC 3164 |
| нормализация | в `GatewayEvidence` |
| корреляция по Message-ID / queue-id / времени / отправителю / получателю | `get_verdict()`, `message_traces` |
| защита от повтора | окно приёма; событие без отметки времени отклоняется |
| дедупликация | ключ из источника, узла, идентификаторов и времени |
| dead-letter для неизвестного формата | таблица `syslog_dead_letters`, видна в консоли |

Приём устроен так, чтобы **отказывать по умолчанию**: у обычного syslog нет аутентификации, и
всё, что видит порт, может выдать себя за шлюз.

Подробно — [`SYSLOG_INTEGRATION.md`](SYSLOG_INTEGRATION.md).

## 8. §21 Каркас адаптера API

Базовый URL, схема аутентификации, секреты через хранилище, таймаут, повторы, предохранитель,
ограничение частоты, кэширование, проверка TLS, прокси, аудит — всё в `GatewayApiClient`.

Три запрета реализованы кодом:

| Запрет | Как обеспечен |
|---|---|
| ключи API в UI и журналах | `describe()` и журналы выдают **ссылку** на секрет; текст исключения не логируется |
| `verify_tls=false` в production | конструктор выбрасывает `ApiConfigurationError` |
| произвольный URL без проверки SSRF | путь присоединяется к базовому URL и перепроверяется; редиректы не выполняются; loopback и link-local отклоняются |

## 9. §22 Модель топологии

Добавлены: `MailGateway`, `MailGatewayNode`, `MailRoute`, `TrustedHop` (это `TrustedMailHop` из
ТЗ 1.0.1 §4.3), `GatewayCredential`, `GatewayCapabilityState`.

Платформа понимает разрешённую топологию вида

```text
Internet → KSMG-01 → KSMG-02 → EXCH-EDGE-01 → EXCH-MBX-01
```

`GatewayCredential` хранит **ссылку** на секрет (`secret_ref`), никогда значение. Поля с именами
`password`, `token`, `api_key` в настройках шлюза отклоняются с объяснением, а не отбрасываются
молча — иначе администратор считал бы, что ключ сохранён.

Подробно — [`TRUSTED_MAIL_FLOW.md`](TRUSTED_MAIL_FLOW.md).

## 10. §23 Корреляция трассировки

Ключи: RFC Message-ID, queue-id, отправитель, получатель, хеш темы, SHA-256 содержимого, SHA-256
вложения, время доставки. Хранятся в `message_traces`.

Цепочка: интернет-сообщение → событие шлюза → сообщение Exchange → анализ MSP → сообщение
сотрудника → инцидент.

## 11. §24 Upstream Protection в консоли

Карточка письма содержит блок со шлюзом, временем, вердиктом, движком, угрозой, оценкой,
состоянием доверия и временем последнего обновления.

Неподтверждённый вердикт рисуется **зачёркнутым**, рядом — причина. Важен не столько заявленный
вердикт скопированного заголовка, сколько тот факт, что подтвердить его не удалось.

`GET /api/v1/gateways/messages/{message_id}`

## 12. §25 Настройки → Почтовые шлюзы

Страница `/gateways`: добавление и отключение шлюза, состояние, возможности, доверенные сети,
имена узлов и `authserv-id`, отображение заголовков, состояние syslog и API, время последнего
события, последняя ошибка.

Шлюз без доверенных узлов сопровождается явным предупреждением: его заголовки будут
показываться и не будут учитываться. Это различие между «настроено» и «работает».

## 13. §26 Корреляция между провайдерами

Один инцидент объединяет evidence от KSMG, Exchange, VirusTotal, правил MSP, контекста AD и
сообщения сотрудника. Отдельный инцидент на каждый источник не создаётся.

## 14. §27 Risk Engine с учётом шлюза

| Состояние | Поведение |
|---|---|
| upstream malicious | жёсткий сигнал `upstream_malware_detection` (`GW-001`) |
| upstream spam | сигнал низкого веса (`GW-002`) |
| upstream clean | `GW-011`, **вес 0** — только для полноты картины |
| шлюз отсутствует | `NOT_PRESENT`, штатная конфигурация |
| шлюз недоступен | `health()` сообщает; отсутствие evidence не трактуется как «чисто» |
| противоречивые вердикты | `ProviderConflict` |

`KSMG=clean + MSP=HIGH_RISK` — нормальное состояние, показывается явно.
`KSMG=malware detected + MSP=LOW_RISK` повышает итоговый вердикт жёстким сигналом.

Жёсткий сигнал требует **доверенного** обнаружения: иначе любой отправитель мог бы принудительно
поднять вердикт до `MALICIOUS` и завалить очередь аналитика.

## 15. §28 Обнаружение конфликтов

`ProviderConflict` для четырёх случаев: `GATEWAY_MALICIOUS_PLATFORM_LOW`,
`GATEWAY_CLEAN_PLATFORM_HIGH`, `GATEWAY_DISAGREEMENT`, `HEADER_API_MISMATCH`.

Конфликт виден аналитику явно и хранится до закрытия
(`POST /api/v1/gateways/conflicts/{id}/resolve`).

---

## 16. §29 Абстракция реагирования

`RemediationProvider` с целями `EXCHANGE`, `MAIL_GATEWAY`, `MSP` и последовательностью
`propose → dry-run → approve → execute → verify → audit`.

Шаг `verify` реализован и обязателен: без него платформа сообщала бы о том, что запросила, а не о
том, что произошло, и частично применённое реагирование выглядело бы как полное.

## 17. §30 Реагирование на шлюзе

**Только чтение на всём этапе 1.0.2.** Возможные будущие действия (карантин, выпуск, блокировка
отправителя, домена, URL, индикатора) объявлены контрактом возможностей и не реализованы.

Отключено **не настройкой**: запись не реализована, и включить её конфигурацией нельзя. План при
этом формируется — знать, что было бы сделано, полезно при разборе.

## 18. §31 Exchange без внешнего шлюза

Пустой реестр даёт `gateway_state=NOT_PRESENT`. Это не ошибка. Ядро продолжает анализ, работу с
EWS, security mailbox, AD, TI, надстройкой и инцидентами без зависимости от провайдера шлюза.

Проверяется тестом `test_no_gateway_is_a_valid_state`.

## 19. §32 Несколько шлюзов

Поддерживается произвольное число шлюзов; направление задаётся полем `direction`
(`inbound`, `outbound`, `both`).

## 20. §33 Аудит

Записываются: добавление и отключение шлюза, изменение доверенных сетей и политик, ротация
секретов, изменение возможностей, предложение/согласование/выполнение реагирования, жизненный
цикл конфликтов.

Изменение доверенного узла аудируется **отдельно** от изменения конфигурации: оно меняет, каким
заголовкам платформа верит.

## 23. §36 Матрица провайдеров

| Провайдер | Требование | Состояние |
|---|---|---|
| KSMG | production-grade разбор заголовков | ✔ |
| Generic Header Gateway | production-grade | ✔ |
| Generic Syslog Gateway | production-grade | ✔ |
| EOP | разборщик | ✔ SCL, BCL, PCL, CAT |
| SpamAssassin | разборщик | ✔ включая Rspamd и `X-Spam-Level` |
| generic AV | разборщик | ✔ |
| FortiMail, Proofpoint, Mimecast, Cisco ESA | skeleton, контракт возможностей, руководство | ✔ разбор заголовков **работает**; API объявлен и не реализован |

Для четырёх последних формат заголовков документирован публично, поэтому разбор реализован и
пригоден к работе. API не реализован, пока нет реальной среды для проверки: заявлять работающей
непроверенную интеграцию нельзя, потому что «шлюз молчит» и «адаптер ничего не вернул» выглядят
одинаково.

Что требуется от организации для каждого — в `skeleton.prerequisites` и в консоли.
