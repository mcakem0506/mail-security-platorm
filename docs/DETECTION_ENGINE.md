# Движок детектирования

ТЗ 1.0.3 §6–§8, §12, §15, §16, §48. Как устроен путь от письма до вердикта и почему именно так.

## Четыре слоя, которые нельзя смешивать

```
письмо  →  разбор  →  факты  →  правила  →  агрегация риска  →  вердикт
          (parser)   (facts)   (rules)      (risk engine)
```

Разделение не формальное. Каждый слой отвечает на свой вопрос, и путать их опасно:

| Слой | Вопрос | Где живёт |
|---|---|---|
| Разбор | что в письме есть | `packages/mail-parser` |
| Факты | что из этого значимо | `packages/detection-engine/msp_detection/facts.py` |
| Правила | какие комбинации фактов тревожны | `rules/**/*.yaml` |
| Агрегация | что из этого следует | `packages/risk-engine` |

Главное следствие: **правило не умеет извлекать данные, а парсер не умеет делать выводы**.
Когда правило ошибается, исправляют правило — файл, который можно посмотреть в pull request.
Когда что-то не извлечено, исправляют парсер. Если бы правила умели парсить, любая настройка
детектирования превращалась бы в правку кода, а любая правка кода — в риск для разбора.

## Факты

Факт — это именованное утверждение о письме: `sender_external`, `attachment_executable`,
`intent_bank_details_change`. Всего словарь содержит более 200 имён; он собирается из исходного
кода движка модулем `msp_detection/vocabulary.py`.

Словарь существует по конкретной причине. Правило, в условии которого опечатка, **загружается
без ошибок, проходит валидацию и не срабатывает никогда**. Оно занимает строку в карте
покрытия и не защищает ни от чего — хуже, чем отсутствующее правило, потому что выглядит так,
будто кто-то смотрит. Поэтому `tests/unit/test_rule_vocabulary.py` проверяет, что каждое
условие и каждый ключ доказательств из пакета правил есть в словаре, и этот тест вынесен в
отдельную задачу CI.

Факты несут с собой доказательства: `fs.flag("attachment_executable", filename=..., sha256=...)`.
Доказательства попадают в сигнал, в карточку аналитика и в граф — поэтому в них нельзя
складывать тело письма или что-либо, чего не должно быть в журнале.

## Правила

Правила — данные, а не код (§12). Формат — YAML, 122 правила в семи областях:

```yaml
- id: ATT-040
  version: 1
  status: ACTIVE
  owner: detection-attachment@corp.example
  name: Документ загружает удалённый шаблон
  category: suspicious_attachment
  severity: high
  confidence: 0.85
  weight: 45
  conditions:
    - attachment_remote_template
  evidence: [attachment_remote_template, document_autoload_reference]
  explanation: >-
    Документ во вложении настроен на загрузку шаблона с внешнего сервера…
  recommendation: Не открывайте документ. Передайте письмо в службу ИБ.
```

Условия — это `all`, `any`, `not`, `count` над именами фактов, и ничего больше. **Запрещены**
`eval`, произвольный исполняемый код и динамические импорты из файлов правил (§12). Запрет не
декоративный: файл правил проходит более короткий путь ревью, чем код, и исполняемое выражение
в нём означало бы, что путь ревью кода можно обойти.

Поля `weight` и `confidence` разделены намеренно. `weight` — сколько правило добавляет к риску,
`confidence` — насколько движок уверен в самом срабатывании. Правило может быть уверенным и
маловажным (`info`-правила) или важным и неуверенным.

### Распределение

| По статусу | | По серьёзности | |
|---|---:|---|---:|
| ACTIVE | 121 | critical | 20 |
| SHADOW | 1 | high | 46 |
| | | medium | 35 |
| | | low | 16 |
| | | info | 5 |

У всех 122 правил указан владелец — критерий выхода §60. Владельцы распределены по семи
направлениям (`detection-sender`, `detection-url`, `detection-attachment`, `detection-bec`,
`detection-ti`, `detection-gateway`, `detection-core`).

### Где лежит пакет правил

Правила вынесены из Python-пакета в каталог `rules/` в корне репозитория. Поиск выполняется
функцией `find_rule_pack()` в порядке: `MSP_RULE_PACK_PATH` → `/app/rules` → корень
репозитория. Это позволяет подменить пакет правил при развёртывании, не пересобирая образ, и
проверить правило до коммита.

## Агрегация риска

Баллы складываются не линейно: см. `packages/risk-engine`. Три свойства, важные для понимания
вердикта:

1. **Жёсткие сигналы** (`hard: true`) задают нижнюю границу вердикта независимо от суммы.
   Исполняемое вложение не может быть «низким риском» из-за того, что остальные признаки
   чистые.
2. **Неполная проверка не опускается до LOW_RISK.** Если что-то не прочитано — шифрование,
   пароль на архиве, превышение лимита, нераспознанный QR-код, — вердикт не может оказаться
   чистым. Отсутствие детекта не является безопасностью (§3).
3. **Вердикт шлюза никогда не снижает риск.** Свойство `lowers_risk` в контракте шлюза
   возвращает `False` методом, а не комментарием, чтобы будущий адаптер не мог тихо решить
   иначе.

## Объяснимость

Каждый сигнал несёт `rule_id`, `rule_version`, `severity`, `weight`, `confidence`, условие
правила в читаемом виде (`Condition.render()`) и доказательства. Аналитик видит не «сработало
правило BEC-014», а то, что именно правило спросило и что оказалось верным (§15).

Граф доказательств (§16) собирается из сохранённого результата, а не пересчитывается:
`письмо → факты → правила → вердикт`, плюс узлы того, что проверить не удалось. Теневые
правила на графе показаны и подписаны как не дающие баллов — скрывать их означало бы
расхождение между графом и отчётом по теневым правилам.

## Воспроизводимость

С каждым вердиктом сохраняются (§48):

| Версия | Что фиксирует |
|---|---|
| `ruleset_version` | отпечаток пакета правил (id и версия каждого правила) |
| `risk_engine_version` | алгоритм агрегации |
| `parser_version` | версия разбора MIME |
| `ti_policy_version` | какие внешние обращения были разрешены политикой |

Политика попадает в список не для полноты: вердикт, полученный при выключенных обращениях по
URL, несопоставим с вердиктом после их включения. Без этой записи сравнение двух вердиктов
молча сравнивало бы разные конфигурации.

Эндпоинт `GET /api/v1/detection/versions` возвращает все четыре плюс состав пакета правил.

## Производительность

Бюджет локального анализа — 5 секунд на письмо, без внешних обращений (§43). Измеренное
значение на золотом корпусе: медиана 0,9 мс, P95 1,8 мс. Бюджет не формальность: он проверяется
тестами `tests/security/test_parser_robustness.py` на больших письмах, тысячах ссылок, глубоко
вложенном HTML и потоке вложений — вместе с проверкой, что достигнутый лимит виден в
`limits_hit`, а не приводит к молчаливому пропуску.
