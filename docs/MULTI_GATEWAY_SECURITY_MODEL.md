# Модель безопасности интеграции со шлюзами

**Относится к:** ТЗ 1.0.2 §21, §33, §34, §35
**Тесты:** `tests/security/test_gateway_security.py`

---

## 1. Что меняет появление шлюза

До 1.0.2 платформа получала данные из двух источников, которым можно было доверять по
построению: собственного разбора письма и собственной базы. Интеграция со шлюзом добавляет три
канала, и у каждого своя проблема происхождения:

| Канал | Кто может в него писать | Чем доказывается подлинность |
|---|---|---|
| заголовки письма | **отправитель** | цепочка `Received` |
| syslog | всё, что видит порт | список адресов, TLS-сертификат клиента |
| API вендора | владелец адреса, на который мы идём | TLS с проверкой, фиксированный базовый URL |

Каждый канал требует **собственного** доказательства происхождения. Общего у них только одно:
ни один не может понизить вердикт платформы.

---

## 2. Заголовки

Подробно — [`GATEWAY_TRUST_MODEL.md`](GATEWAY_TRUST_MODEL.md). Кратко:

* заголовок учитывается только при подтверждении прохождения цепочкой `Received`;
* заявление узла о самом себе (`by`) требует подтверждения соседом сверху, которого
  злоумышленник написать не может;
* неподтверждённый заголовок — сам по себе сигнал, но не источник вердикта;
* `Authentication-Results` читается только от подтверждённого сервера; заголовок, называющий
  **наш** сервер на неподтверждённом пути, считается подделкой.

---

## 3. Syslog

Подробно — [`SYSLOG_INTEGRATION.md`](SYSLOG_INTEGRATION.md). Защиты:

| Угроза | Защита |
|---|---|
| подмена источника | список адресов; пустой список = не принимается ничего |
| повтор захваченного события | окно приёма по отметке времени; событие без отметки отклоняется |
| дублирование | ключ дедупликации; повтор не порождает второго evidence |
| исчерпание ресурсов | лимит размера события (32 КиБ), окна дедупликации и dead-letter |
| незаметная потеря событий | dead-letter с причиной; метрика последнего принятого события |

## 4. API шлюза (ТЗ 1.0.2 §21)

Три запрета реализованы кодом, а не документацией.

### Секрет не покидает модуль

`GatewayApiClient.describe()` и каждая строка журнала выдают **ссылку** на секрет, а не значение:

```json
{"provider_id": "vendor-api", "credential": "file:/run/secrets/vendor_token", "verify_tls": true}
```

Секрет читается из файла — тот же механизм, что у Docker secrets и Vault (ТЗ 28). Текст
исключения в журнал не попадает, только его тип: сообщение об ошибке HTTP-клиента способно
повторить запрос вместе с заголовком авторизации.

### `verify_tls=false` в production отклоняется

Конструктор выбрасывает `ApiConfigurationError`. API несёт вердикты, меняющие действия аналитика;
принимать любой сертификат — значит позволить их подменить.

Простой HTTP отклоняется тоже. Нестандартные схемы (`file:`, `gopher:`, `ftp:`, `dict:`, `ldap:`)
отклоняются отдельным списком.

### Произвольный URL невозможен

Каждый путь присоединяется к настроенному базовому URL и **перепроверяется** перед отправкой:

```python
build_url("https://gw.corp.example/api/v1/", "messages/42")  # ок
build_url("https://gw.corp.example/api/v1/", "https://evil/x")  # ApiConfigurationError
build_url("https://gw.corp.example/api/v1/", "../../../admin")  # ApiConfigurationError
build_url("https://gw.corp.example/api/v1/", "x\r\nX-Injected: 1")  # ApiConfigurationError
```

Это SSRF-шлюз: значение пути может происходить из письма. Дополнительно:

* **редиректы не выполняются** (`follow_redirects=False`) — типовой способ обойти такую проверку;
* адреса loopback, link-local и зарезервированные отклоняются.

### Устойчивость

| Механизм | Поведение |
|---|---|
| таймаут | на запрос, настраивается |
| повторы | с экспоненциальной задержкой |
| предохранитель | открывается после N отказов, полуоткрытое состояние для пробы |
| ограничение частоты | локальное, до обращения к сети |
| кэш | с TTL, не применяется к записи |
| прокси | поддерживается |

При открытом предохранителе `health()` возвращает `unavailable`, и это видно в консоли: провайдер,
который «ничего не находит», потому что к нему не ходят, не должен выглядеть как провайдер,
который ничего не нашёл.

## 5. Изоляция организаций

`build_registry` загружает шлюзы и узлы **одной** организации. Evidence, конфликты и трассировки
привязаны к `organization_id`. Проверяется тестами `TestCrossOrganisationIsolation`.

## 6. Реагирование

| Цель | 1.0.2 | Проверка |
|---|---|---|
| Exchange | выполняется после согласования, только обратимые действия | `verify` перечитывает письма |
| Шлюз | **только чтение** | план сообщает, что запись не реализована |
| Платформа | выполняется, обратимо | почта не затрагивается |

Реагирование на шлюзе отключено **не настройкой**. Запись не реализована, и включить её
конфигурацией нельзя. План при этом формируется: знать, что было бы сделано, полезно при
разборе, и контракт возможностей должен существовать раньше адаптера.

Область ящиков проверяется **до** обращения к Exchange, поэтому выйти за неё нельзя даже при
ошибке в вызывающем коде. Конфигурация отклоняет включение реагирования без явно заданной области.

Шаг `verify` обязателен: без него платформа сообщает о том, что запросила, а не о том, что
произошло. Частично применённое реагирование сообщается как неполное.

## 7. Аудит (ТЗ 1.0.2 §33)

| Событие | Действие в журнале |
|---|---|
| шлюз добавлен | `gateway.added` |
| шлюз изменён / отключён | `gateway.updated`, `gateway.disabled` |
| изменение доверенного узла | `gateway.trusted_hop_changed` |
| ротация секрета | `gateway.credential_rotated` |
| изменение возможностей | `gateway.capability_changed` |
| закрытие расхождения | `gateway.conflict_resolved` |
| предложение/согласование/выполнение реагирования | `remediation.*` |

Изменение доверенного узла записывается **отдельно** от изменения конфигурации: оно меняет, каким
заголовкам платформа верит, и это не то же самое, что переименовать шлюз.

Журнал не содержит секретов и тел писем — общая политика ТЗ 25 распространяется и на записи о
шлюзах.

## 9. Что остаётся вне модели

* **Скомпрометированный шлюз.** Его вердикты подтверждены и ложны. Поэтому вердикт шлюза —
  сигнал, а не замена собственного анализа.
* **Внутренний злоумышленник в цепочке.** Контроль над сервером организации даёт возможность
  написать подтверждающий заголовок. Дальше работают контроль доступа и аудит.
* **Ошибки нормализации вендора.** Новый статус, которого разборщик не знает, становится
  `UNKNOWN`. Это безопасное направление ошибки, но оно означает, что обновление шлюза стоит
  сопровождать проверкой `msp_gateway_event_parse_errors_total`.
