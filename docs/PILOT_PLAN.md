# План теневого пилота

**Относится к:** ТЗ 1.0.1 §8, §9, §12
**Длительность:** не менее 14 дней
**Режим:** только наблюдение, почта не изменяется

---

## 1. Что такое теневой пилот

Платформа анализирует реальную почту и **ничего с ней не делает**. Запрещены:

* автоматическое удаление;
* автоматический карантин;
* изменение правил Exchange;
* изменение mail flow;
* отклонение на уровне SMTP.

`dry_run_only=true` на всё время пилота. Платформа не стоит на пути доставки и не может стать
точкой отказа почты — это условие, а не настройка по умолчанию.

Цель пилота — получить **фактические** цифры качества детектирования на почте этой организации,
а не подтвердить, что продукт работает в принципе.

---

## 2. Состав группы

5–10 пользователей, обязательно включая:

| Роль | Зачем |
|---|---|
| не менее 1 сотрудника ИБ | оценивает вердикты и ведёт разбор |
| не менее 1 VIP / руководителя | цель подмены имени; проверяет защиту критических идентичностей |
| не менее 1 сотрудника бухгалтерии или финансов | цель BEC; получает письма о платежах и реквизитах |

Остальные — обычные сотрудники из разных подразделений. Группа только из ИБ измерит удобство для
аналитика, но не поведение обычного получателя.

---

## 3. Подготовка

### 3.1. Проверка готовности

```bash
docker compose exec api python scripts/probe_exchange.py \
  --markdown /tmp/readiness.md --pilot-mailbox pilot1@corp.example
```

Решение должно быть `READY` либо `READY_WITH_WARNINGS` с явно принятыми замечаниями.
Подробно — [`EXCHANGE_PROBE_GUIDE.md`](EXCHANGE_PROBE_GUIDE.md).

### 3.2. Топология почтового потока

Описать шлюзы и серверы Exchange. Без этого заголовки шлюза и результаты проверки подлинности
не подтверждаются. См. [`TRUSTED_MAIL_FLOW.md`](TRUSTED_MAIL_FLOW.md).

Проверить: `probe_exchange.py --section mailflow` не должен сообщать «шлюз настроен, но ни один
узел не описан».

### 3.3. Защищаемые идентичности

Задать `MSP_AD_PROTECTED_GROUPS` и дождаться синхронизации каталога, либо внести идентичности
вручную. Группа пилота должна быть покрыта: руководитель и финансист из состава пилота обязаны
попасть в список.

```bash
curl .../api/v1/admin/protected-identities | jq '.[] | {email, risk_class, vip, source}'
```

### 3.4. Надстройка Outlook

Установить группе пилота. Требуется HTTPS и доверенный на клиентских машинах сертификат.

### 3.5. Исходное состояние

Зафиксировать до начала:

```bash
docker compose exec api python scripts/generate_acceptance_snapshot.py --out docs/pilot-start.md
```

## 4. Сценарии проверки (ТЗ 1.0.1 §9)

Проверяются на синтетических письмах из корпуса **до** начала работы с реальной почтой:

```bash
python scripts/export_corpus.py --out /tmp/corpus
```

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | обычное внутреннее письмо | не помечается |
| 2 | обычное внешнее письмо | не помечается |
| 3 | рассылка / newsletter | не помечается |
| 4 | письмо внешнего подрядчика | не помечается |
| 5 | подмена отображаемого имени | обнаружено |
| 6 | похожий корпоративный домен | обнаружено |
| 7 | punycode-домен | обнаружено |
| 8 | поддельная страница входа Microsoft | обнаружено |
| 9 | поддельная страница входа OWA | обнаружено |
| 10 | BEC: счёт | обнаружено |
| 11 | смена банковских реквизитов | обнаружено |
| 12 | CEO fraud | обнаружено |
| 13 | поддельный документ отдела кадров | обнаружено |
| 14 | вложение с имитацией вредоносного (EICAR) | обнаружено |
| 15 | архив | разобран, лимиты соблюдены |
| 16 | зашифрованный архив | помечен как непроверяемый |
| 17 | очень крупное письмо | **не анализируется**, вердикт UNKNOWN |
| 18 | битый MIME | частичный разбор, вердикт не LOW_RISK |
| 19 | Threat Intelligence недоступен | анализ завершается, вердикт не LOW_RISK |
| 20 | AD / EWS / VirusTotal недоступны | платформа продолжает работать |
| 21 | подделанные заголовки `X-KSMG-*` | вердикт шлюза не учитывается, сигнал подделки |
| 22 | подделанный `Authentication-Results` | не читается, сигнал подделки |

Сценарии 17–22 — те, где неправильное поведение опаснее всего: во всех письмо выглядит
проверенным, не будучи проверенным.

## 5. Ход пилота

### Ежедневно

* просмотр очереди расследований;
* разбор сообщений от сотрудников;
* перевод подтверждённых инцидентов в статус, отражающий решение — именно он даёт
  `confirmed_tp` / `confirmed_fp` для статистики правил.

### Еженедельно

```bash
curl .../api/v1/reports/pilot-metrics?days=7 | jq '{total_analyzed, by_verdict, top_noisy_rules}'
```

Если правило попало в `top_noisy_rules` — разобрать: это ошибка правила или особенность почты
организации. Исключение (`DetectionException`) заводится с владельцем, причиной и сроком, а не
навсегда.

### Что не делать во время пилота

* не включать реагирование;
* не менять пороги на основании первых дней — выборка мала;
* не отключать правило, вместо того чтобы завести исключение: отключённое правило перестаёт
  измеряться, и статистика по нему теряется.

## 6. Метрики (ТЗ 1.0.1 §11)

```bash
curl .../api/v1/reports/pilot-metrics?days=14 > pilot-metrics.json
```

| Группа | Показатели |
|---|---|
| объём | `total_analyzed`, `employee_reports`, `by_verdict` |
| полнота | `unknown`, `unscannable`, `ti_unavailable` |
| качество | `true_positive`, `false_positive`, `false_negative_discovered` |
| задержка | медиана, P95, P99 |
| правила | `top_noisy_rules`, `top_effective_rules`, полная таблица |
| контекст | `top_impersonated_identities`, `top_suspicious_domains`, `campaigns_detected` |
| приём | `intake` по состояниям |

Две метрики читаются иначе, чем выглядят, и это существенно:

* `precision_estimate` равен `null` у правила, которое никто не разбирал. Непроверенное правило
  не имеет precision, а не имеет идеальную.
* `false_negative_discovered` — нижняя оценка, а не recall: учитываются только пропуски, которые
  кто-то обнаружил.

## 7. Проверка устойчивости приёма

Хотя бы один раз за пилот проверить, что сообщения не теряются:

```bash
# Остановить worker во время обработки
docker compose stop worker-mail
# Отправить письмо в security mailbox, затем запустить worker
docker compose start worker-mail
```

Письмо должно быть обработано после перезапуска ровно один раз. Состояния приёма:

```bash
curl .../api/v1/reports/pilot-metrics?days=1 | jq .intake
```

`DEAD_LETTER` требует разбора: это сообщения, которые платформа не смогла обработать за
отведённое число попыток и переместила в папку `Failed`.

## 8. Критерии завершения (ТЗ 1.0.1 §12)

| # | Критерий | Проверка |
|---|---|---|
| 1 | подключён реальный Exchange | probe, раздел Exchange |
| 2 | подключён реальный AD | probe, раздел Active Directory |
| 3 | security mailbox работает | probe + метрика `intake` |
| 4 | EWS read-only работает либо принят документированный отказ | probe |
| 5 | надстройка установлена группе пилота | опрос участников |
| 6 | TLS внутренней PKI настроен | probe, отсутствие замечаний по TLS |
| 7 | цепочка доверенных заголовков работает | probe, раздел mailflow; сценарии 21–22 |
| 8 | крупное письмо не анализируется как полноценное | сценарий 17 |
| 9 | приём устойчив и идемпотентен | §7 выше |
| 10 | CI зелёный на HEAD | статус сборки |
| 11 | документ приёмки соответствует HEAD | `generate_acceptance_snapshot.py` |
| 12 | пилот длится не менее 14 дней | даты |
| 13 | собраны метрики FP/TP | `pilot-metrics` |
| 14 | автоматическое разрушающее реагирование отсутствует | probe, раздел «Режим пилота» |
| 15 | сформирован отчёт | [`PILOT_REPORT.md`](PILOT_REPORT.md) |

Решение: `READY_FOR_CONTROLLED_ROLLOUT`, `READY_WITH_WARNINGS`, `NOT_READY`.

---

## 9. После пилота

Успешный пилот **не означает** включения реагирования. Контролируемое развёртывание — отдельное
решение, требующее закрытых замечаний, согласованной области ящиков и порядка согласования
действий (ТЗ 20).

MSP 1.1 не начинается до получения фактических результатов пилота (ТЗ 1.0.2 §38).
