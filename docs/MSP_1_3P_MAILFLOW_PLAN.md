# MSP 1.3P — почтовые топологии и план маршрута

**Относится к:** ТЗ MSP 1.3P §3, §6, §10, §18, §22

> Основной MX и транспорт Exchange не изменяются без отдельного изменения. Все контроли остаются `DISABLED`/`SHADOW` до решения по P4.
> Платформа DNS и Exchange не меняет.

## Что в репозитории реализовано, а что нет

| Возможность | Статус | Где |
|---|---|---|
| Разбор журнального отчёта Exchange, извлечение оригинала из вложения `message/rfc822` | `IMPLEMENTED` (1.3P) | `msp_mail_parser/journal.py` |
| Надёжный приём (`IntakeRecord`), анализ, запись набора валидации с источником и дедупликацией | `IMPLEMENTED` (1.3P) | `services/real_flow_feed.py`, `POST /api/v1/pilot/intake/journal` |
| Ящик безопасности (EWS, чтение, перемещение после записи) | `ALREADY_IMPLEMENTED` | воркер `msp.poll_security_mailbox` |
| Теневая копия шлюза (SMTP, `always_bcc`) | `ALREADY_IMPLEMENTED` (1.1) | `gateway-agent/shadow` |
| Постоянный сборщик журнального ящика по EWS | `BLOCKED_EXTERNAL`: нужен настоящий Exchange; сегодня журнальные отчёты подаются в `intake/journal` | — |
| Приём `EWS_READONLY` по произвольным ящикам | `BLOCKED_EXTERNAL`: то же | — |
| Изоляция пилотного маршрута, два узла, SMTP-канарейка | `ALREADY_IMPLEMENTED` на стенде (1.3); на реальной среде `NOT_TESTED` | `tests/enforcement` |

Поэтому постоянный сбор реальных писем сегодня требует внешней подачи (скрипт или сборщик организации, вызывающий `intake/journal`) —
это зафиксировано как внешний блокер приёмки, а не скрыто.

## Топология A — существующий шлюз (KSMG/другой SEG), основная

```text
Internet → KSMG / SEG → Exchange → пользователи
                │             └─ журнальная копия разрешённой группы → MSP intake → REAL_FLOW_SHADOW
                └─ вердикт SEG остаётся независимым свидетельством
```

Основной MX не меняется. Вердикт SEG не понижает риск MSP. Анализ Rspamd возможен для отдельного контролируемого повтора; контекст
SMTP-сессии (настоящий IP клиента, результаты Milter) при повторе отсутствует, и это не выдаётся за полноценную проверку внешнего входа.

## Топология B — Exchange без внешнего SEG

Проверка после доставки (журнал или EWS только для чтения). Защиты до доставки схема не даёт, это записывается отдельным ограничением.
Нативные антиспам и антивирус Exchange документируются отдельно, не предполагаются включёнными.

## Топология C — изолированный SMTP-пилот (только P4)

```text
Контролируемый источник / пилотный поддомен → Узел A / Узел B (Postfix + Rspamd) → отдельный Receive Connector → пилотные получатели
```

Предпочтительно отдельный поддомен со своим MX либо тестовый домен с приёмником; альтернатива — явно изолированный маршрут через
существующий SEG при отсутствии циклов. Пересылка письма вместо SMTP-доставки — другой канал и другие доказательства.

Перед отправкой: два узла с независимыми очередями; открытый ретранслятор отсутствует; Receive Connector ограничен адресами узлов;
карта получателей актуальна; пороги диска в мониторинге; общий токен выключен; ключ карантина восстановлен; выключатель, обход, откат,
срок политики проверены на обоих узлах; письма с несколькими получателями безопасны; журнальные служебные получатели исключены из области.

Сначала канарейка на 1–2 тестовых получателей (не VIP/финансы), затем расширение только по новому решению.

## Источник письма и происхождение

В записи хранятся: источник (`JOURNAL_COPY`, `EWS_READONLY`, `GATEWAY_EVIDENCE`…), направление, идентификатор сообщения оригинала,
хеш оригинала и отчёта, версии правил и разборщика, момент приёма. Содержимого, темы и адресов в наборе валидации нет.

### Идентичность и дедупликация

Идентичность письма в выборке — структурный отпечаток (устойчив к обезличиванию) вместе с `Message-ID` оригинала. Одно письмо,
пришедшее из журнала, из ящика и из другого отчёта, остаётся **одной записью**; два типовых письма одного отправителя с разными
`Message-ID` — две. **Ограничение:** письмо без `Message-ID` определяется только структурой, и однотипные письма без идентификатора
склеиваются; выборка в этом случае занижается, а не завышается.

### Что не анализируется и не считается чистым

Оригинал сверх предела размера не усекается и не анализируется; отчёт без вложения, не отчёт и отчёт в отчёте (защита от петли)
записываются как `UNKNOWN/UNSCANNABLE` без вердикта и входят в долю непроверенного на 1000 писем.
