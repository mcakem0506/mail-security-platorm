# Политика спама и симулятор кандидата

**Относится к:** ТЗ MSP 1.2 §6, §28, §34
**Код:** `msp_antispam/policy.py`, `apps/api/msp_api/services/antispam.py`; консоль — «Анти-спам и аутентификация» → «Симулятор политики»

## Политика

`SpamPolicy`: режим, пороги (`suspected`, `spam`, `high_confidence`, `suggest_reject`), включённые модули, провайдеры, Bayes,
greylisting, `enforcement_enabled`, версия. **`enforcement_enabled` на этапе 1.2 всегда `false`**: модель отказывается создаваться
иначе, а API не принимает поле вообще (HTTP 422). Режимы действий `RspamdActionPolicy`: `SHADOW`, `PILOT_HEADER_ONLY`,
`ENFORCEMENT_DISABLED`; режима, который что-то исполняет, нет. Предложение сканера (`greylist`, `soft reject`, `reject`, `add header`)
сохраняется как `suggested_action`, реальное действие — `OBSERVE_ONLY`.

## Кандидат

```text
DRAFT → SHADOW → VALIDATION → APPROVED → ACTIVE_SHADOW
```

Состояния `ACTIVE_ENFORCING` не существует. Шаги нельзя пропускать и возвращать. Одобряет (`APPROVED`) **не тот, кто правил
кандидата** и обладающий правом `spam:policy:approve` (четыре глаза); отказ пишется в аудит. Действующим может быть один
кандидат (`ACTIVE_SHADOW`): он определяет, как MSP классифицирует *новые* письма и какие пороги передаёт сканеру; поток
почты не меняется ни в одном состоянии.

## Симулятор

Показывает для уже принятых писем: символы Rspamd, оценку, аутентификацию, репутацию, предложенное действие, класс спама
MSP, вердикт безопасности и **гипотетическое действие при кандидате**. Применённое действие везде `OBSERVE_ONLY`; симулятор ничего
не записывает в поток. Строки, где действие изменилось бы, выделены. Права: симулировать вправе аналитик
(`spam:simulate`), править — администратор ИБ (`spam:policy:edit`).
